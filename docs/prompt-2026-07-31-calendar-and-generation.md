## 1. カレンダーの未実施セッションを確実に削除できるようにする

**現状**: `deletePlannedSession`（`src/lib/service.ts:2530-2546`）・APIルート（`app/api/plan-edit/route.ts`、`pwa/api-shim.ts:507-511`）・削除ボタン（`app/components/session-edit-sheet.tsx:145-149`）は既に存在する。
問題は導線: `app/calendar/page.tsx`の`DayRow`は行の**長押し**でしか個別セッションの編集シートを開けず（iOSで長押しは取りこぼされることがあるとコード内コメントにも明記済み）、✎ボタンはその日の**最初の非固定セッションしか対象にしない**（`app/calendar/page.tsx:539`の`sessions.find((s) => !s.isFixed)`）。2件目以降のセッションは長押し以外に触る手段が無い。

**やること**:
- 各セッション行に、長押しに頼らず確実にタップできる削除導線を追加する（例: 行の右側に小さい「⋯」または削除アイコンを常時表示し、タップで`session-edit-sheet.tsx`の削除確認ダイアログを直接開く）。
- ✎ボタンは維持してよいが、2件目以降のセッションにも届くようにする（新しい削除導線が行ごとに独立していれば自然に解決する）。
- 既存の確認ダイアログ（「記録済みの結果は消えません。予定だけを消します。」）・`isFixed`セッションの削除禁止はそのまま使う。
- `completed`ステータスのセッションも削除できてしまう点（`deletePlannedSession`に状態チェックが無い）は今回のスコープ外。気づいたら別途報告するだけでよい（実施済みメニューを消す動線を新設しないこと）。

**確認方法**: E2Eで、同じ日に2件セッションがある状態を作り、2件目を新しい導線から削除できることを確認する。T-4（導線を無効化して赤に戻す）。

## 2. 曜日ごとの優先設定で複数カテゴリに対応し、ジョグ＋神経系の複合メニューを自動分割する

**背景**: 以下2つの要望は同じ原因だったので1つの変更にまとめる。

- 「曜日の優先設定でジョグ＋神経系のような複数種目に対応してほしい」
- 「ジョグ＋坂ダッシュ／流しの複合メニューを、1つのセッションではなく別々に出してほしい」

**現状の事実**:
- `WeekTemplate.slots`（`src/lib/core/weekTemplate.ts:53`）は`Partial<Record<Dow, WeekdaySlot>>`で、1曜日につき`WeekdaySlot`（`SessionCategory | "auto" | "point"`）を1つしか持てない。UIも単一`<select>`（`app/plan-settings/page.tsx:171`）。
- `periodization.ts`の週生成ループ（605-861行目）は1日につき`sessions.push(session)`を**必ず1回だけ**呼ぶ。1日に複数セッションを生成する分岐は存在しない。
- `hillSprints()`（`periodization.ts:126-138`）・`strides()`（140-152行目）は、ジョグ部分と坂ダッシュ／流し部分を**1つの`prescription`文字列**に結合して1セッションとして生成している（例: `"坂ダッシュ8〜10秒×5本 + ジョグ30分"`）。
- カレンダー側（`app/calendar/page.tsx:166-170`の`sessionsByDate`）は元々1日に複数セッションを表示・保存できる構造。手動追加（AddSheetの「同じ日に午前と午後の2本を残す」機能）は既に動いている。**足りないのは生成側だけ**。

**やること**:
1. `periodization.ts`の週生成ループが、条件に応じて1日に2セッションをpushできるようにする（`hillSprints`/`strides`のような「ジョグ＋短い刺激」系テンプレートに限定してよい。全カテゴリを任意に組み合わせ可能にする汎用化はしない）。
   - `hillSprints()`・`strides()`のプリスクリプション文言からジョグ部分を分離し、ジョグは`category:"aerobic"`の別セッション、坂ダッシュ／流しは`category:"neural"`のセッションとして、同じ日付で2件生成する。
   - タイミング（午前/午後）は既存の`timeOfDay`の使い方に合わせる。
   - テーパー期の「刺激入れ（流し）」（`periodization.ts:648-653`）も同じパターンなら合わせて分割する。
2. `WeekTemplate`の型を拡張し、1曜日に「主」と「副」の2枠まで持てるようにする（配列汎用化はしない。ユーザーの実例が「ジョグ＋神経系」の2択なので、それ以上に複雑にしない）。
   - 例: `WeekdaySlot`はそのまま維持し、`WeekTemplate`に`secondarySlots?: Partial<Record<Dow, SessionCategory>>`のような形で追加する（既存`slots`との後方互換を保つ）。
   - `app/plan-settings/page.tsx`のUIに、既存の`<select>`の下に「もう1種目追加」的な任意の第2`<select>`を追加する。
   - 週生成ループが`secondarySlots`を見て、該当曜日に2件目のセッションを生成する。
3. 上記1と2は同じ「1日に複数セッションを生成する」土台を共有するので、先に1（テンプレート由来の自動分割）を実装してから、2（曜日設定の複数種目）をその上に乗せる順番で進める。

**変更しないこと**: 生成の決定性（同じ入力から同じ結果が出ること）、1枠1種類というSession/SessionResultのデータモデル自体（複数セッションで表現する。1セッション内にsegments概念を持たせない——これは過去の監査で明示的に見送った設計判断のまま維持する）。

**確認方法**:
- `hillSprints`/`strides`が生成される週で、カレンダーに2件（有酸素＋神経系）が別々に出ることをユニットテスト・E2Eで確認。
- 曜日設定で第2種目を設定した週で、その曜日に2件生成されることを確認。
- T-4（分割ロジックを無効化して1件に戻り、テストが赤くなることを確認して復元）。

## 3. カンマ区切り入力欄でカンマが打てない

**原因確定**: `app/results/page.tsx`の「実施タイム（本数分をカンマ区切り）」欄に`inputMode="decimal"`が付いており、iOS等の数値専用キーボード（カンマキーが無い）を呼び出している。JS側の文字除去処理は無い。

**やること**: この欄の`inputMode="decimal"`を外す（通常のテキストキーボードにする）。他の単一の数値欄（`avgHr`の`inputMode="numeric"`等）には触らない。

**確認方法**: E2Eでこの欄にカンマを含む文字列を入力し、そのまま反映されることを確認する（今回のバグはE2Eでは検出できていなかった可能性が高いので、テスト自体もこの機会に追加する）。

## 4. FIT取込でランニングダイナミクスも取得する

**現状**: `src/lib/core/fitParse.ts`は心拍以外（ピッチ・ストライド・上下動・接地時間・気温）を一切抽出していない。`humidityPct`は完全に手入力経路のみでFITとは無関係——**湿度はFITから取れないので今回も手入力のまま**。

**やること**:
1. `fitParse.ts`を拡張し、FITのrecord/lap/sessionメッセージから以下を読めれば読む（無ければ`undefined`のままにする。推測で埋めない）:
   - ピッチ（cadence）
   - ストライド長（あれば。無ければ無理に計算しない）
   - 上下動（vertical oscillation）
   - 接地時間（stance time / ground contact time）
   - 気温（temperature）
   - デバイスが対応していない場合はこれらのフィールド自体がFITに存在しないので、その場合は今まで通り警告や空欄で扱う（`developer_fields_ignored`と同様の既存パターンに合わせる）。
2. `fitToSession.ts`が、取れた値をlap単位・セッション平均単位で保持できるようにする（`RepResult`/`SessionResult`への追加フィールド。既存の`avgHr`と同じ扱い方に揃える）。
3. 表示は今回は最小限でよい: 既存のFIT取込確認カード（`pwa/entry.tsx`の`FitImportCard`）に値を追加表示する、および`samePrescription.ts`の同一処方比較表に列を足す程度に留める。新しい分析画面・新しい傾向判定ロジックは作らない。

**確認方法**: `tests/fixtures/fitEncoder.ts`にこれらのフィールドをエンコードするケースを追加し、`fitParse.ts`が正しく読み取ることをユニットテストで確認。デバイスがフィールドを送ってこないケース（フィールド無し）でも`undefined`のまま壊れないことも確認。T-4。
