# FORGE — 800m Performance System

**Built Through Training.**

800m専門ランナーが目標タイムと現在地を入力すると、生理学的根拠に基づいた練習メニューを自動生成し、練習結果のフィードバックによって以降のメニューを自動補正するツールです。

中核は**ルールエンジンによる制約チェック**（RULE-01〜22）です。メニューを「出す」ことではなく、危険な・非効率な組み方（高乳酸の過頻度、質練習の過密、有酸素偏重、テーパー破壊など）を機械的に検出して弾くことを最優先に設計されています。コアロジックは完全ルールベースで、同じ入力に対して常に同じ出力を返します。

> **手元のPCに移す場合は `MIGRATION.md` を参照。作業時の約束事は `CLAUDE.md` にまとめてある。**
> **障害対応・リリース手順・ロールバックは `OPERATIONS.md` を参照。**

### PWAのビルドに bun が要る理由

`app/` 配下の画面は Next.js と PWA の両方で使い回している。
そのため import は `next/link` / `next/navigation` のままにしてあるが、
PWA は Next.js のサーバーを持たないので本物の Next.js は動かない。
`scripts/build-pwa.mjs` がビルド時だけ `pwa/shims/` の実装に差し替える。

tsconfig の `paths` で解決していないのは、Next.js 側のビルドにも効いてしまい、
`npm run dev` で本物の `next/link` が使われなくなるため。
差し替えは「PWAをビルドするときだけ」に限定する必要がある。

データは `data/train800.db`（SQLite）に保存されます。

ヘッダーのマークは400mトラック。走路2本と、中央の切れ目（スタート／フィニッシュ）だけで構成します。
アプリアイコンは別用途なので、黒背景・白いFORGEワードマーク・蛍光グリーンのトラック光跡を使います。

（画像ライブラリを増やすとネイティブビルドが要るものが混ざり、Windowsで入らないことがあります）。

| 原本 | 書き出し | 用途 |

| `pwa/icon-master.png` | `icon-32.png` | favicon |

左右2本のパスに分けて描いています。

**iOSのホーム画面アイコンは、追加した時点で焼き付けられます。**
アイコンはアプリの一部ではなくショートカットの一部なので、
配信を差し替えても Service Worker を更新しても、既に置いてあるアイコンは変わりません。
**一度削除して追加し直す以外に方法がありません。**

そのうえ Safari は `icon-180.png` 自体もキャッシュしているため、追加し直しても
古い画像のままになることがあります。これを避けるため、`build-static.mjs` が
`index.html` と `manifest.webmanifest` のアイコン参照に `?v=<VERSION>` を付けます。
手で書くと上げ忘れるので `sw.js` の `VERSION` から自動で入れています。
`sw.js` の precache も同じクエリ付きURLにしてあります
（素のファイル名のままだと、オフライン時にアイコンだけ取れなくなる）。

デザイントークンは `app/globals.css` の `:root` に集約してあるので、
色を変えたい場合はそこだけ触れば全画面に反映されます。

`design/mockup.html` と `design/screens.html` は実際にブラウザでレンダリングして確認した
デザイン仕様です（ダブルクリックで開けます）。実装の参照元であり、アプリの動作には不要です。

全9画面はPC幅(1280px)とスマホ幅(390px)の両方で、**実際のReactコンポーネントを実データで
レンダリングして検証済み**です（`harness/` が検証用ハーネス。開発補助であり配布物の動作には不要）。
検証内容: JSランタイムエラーゼロ / 横スクロールはみ出しゼロ / 全ページ描画成功。

配色の設計方針:

- カテゴリの識別は**文字（A/H/R/N/T/C/M）が主エンコード**で、色は補助。色覚特性に依存しません。
- チャートのカテゴリ配色は暗色サーフェス上でCVD分離・輝度帯・コントラストを検証済みのセットです。

### 過去データの遡り入力（現在地の再測定）

CFEの初期値は「800mPB + 1.5秒」で置かれる。PBが古く走力が落ちている場合、
基準タイム = CFE×(1−w) + 目標×w が全ペースの親であるため、
設定ペース全体が実力を上回る。これを実測で測り直すのが `/past` 画面。

入力できるもの:

- レース / タイムトライアル（400・600・800・1000・1500・3000m）
- ポイント練習（カテゴリ・1本の距離・各本のタイム・レスト）
- ジョグ・持続走（距離・時間・平均HR）

換算の考え方（`src/lib/core/backfill.ts`）:

- 他距離 → 800m は**本人のPB関係**を優先する。
  400m は「800m = 400m×2 + 本人の換算差」、1500m は「800m = (1500m − 本人の差) ÷ 2」。
  一般式（Riegel）は本人PBが無い場合のフォールバック。800m選手は同じ800mタイムでも
  型によって400m/1500mとの関係が大きく違うため、一般式を当てると型の分が丸ごと誤差になる。
- ポイント練習 → 800m は生成側の式（距離 × GRP × カテゴリ比率）を逆算する。
  RPE6未満は「全力ではない」として能力推定に使わない（負荷には反映する）。
  標準より長いレストは過大評価になるため穏やかに割り引く。
- ジョグ・持続走は**800m能力の推定には使わない**。LT推定とACWRの下地になる。
- 重み = 信頼度 × 直近性（半減期28日）。12週より古いデータは対象外。
- 暑熱下のデータは実力を過小評価するため除外する。ただし判定は件数ではなく
  **重みの合計**で行う（件数で見ると、涼しい日の800mレース1本が
  暑熱下の練習からの外挿と同列に扱われ、平均に引きずられる）。

守っている制約:

- 過去データを通常の結果記録ループ（`processResult`）に流さない。
  CFE更新は1回±1.5秒（レース±3秒）のガードレールを持つため、
  過去3ヶ月ぶんを順に流すとガードレールが件数ぶん適用されて意味を失う。
  現在地の算出は全件を入れ終えてから1回だけ行う。
- 算出結果は自動適用しない。どの実測が何秒として効いたかの内訳を出し、
  本人が承認して初めてCFEに反映する。
- 過去データから作られたセッションはルールエンジンの評価対象外
  （過ぎた日の構成は今から直せない）。ただし負荷（ACWR）には算入し、
  過去の構成そのものは `diagnosePastStructure` が別枠で診断する。

#### 一括入力ぶんが「入るところ」と「入らないところ」（P-2 / P-3）

一括入力から作られた `SessionResult` に構造化記録（`interval` / `continuous`）が
入っていなかったため、**それを前提にした下流が、エラーも出さずに空になっていた**。
消費側で条件を緩めるのではなく、`backfill.ts` の `toSessionAndResult` が
通常の記録と同じ構造を持たせるように直した。1か所直せば下流はすべて直る。

あわせて `rowToPastEntry` が落としていた設定タイムとレストも運ぶようにした。
設定タイムが無いと「設定に対してどうだったか」が出せず、
本数だけ数えても週次レビューにもM-2にもならない。

| 消費側 | 一括入力ぶん | 理由 |
| --- | --- | --- |
| 週次レビュー（M-11） | **含める** | その週にやったことの要約。入力経路で変わってはいけない |
| 同一処方の経時比較 | **含める** | 同じ処方を何回こなしたかの比較。過去ぶんが無いと2回に届かない |
| 設定の調整（M-2 / executionSamples） | **含める** | 直近3回の実測が材料。過去ぶんを外すと材料が空になる |
| ジョグの心拍（M-2 / jogEfficiency） | **含める** | 同じペース帯の心拍比較。ベースライン側はほぼ過去ぶん |
| 負荷・ACWR | **含める**（従来どおり） | 体にかかった負荷は入力経路と無関係 |
| 600m通過（M-8） | **含める**（従来どおり） | `PastEntry` を直接見ているので元から効いていた |
| 制限因子（M-7） | 影響なし | プロフィールとPBから判定しており、結果を見ていない |
| ルールエンジンの評価 | **外す**（意図的） | 過ぎた日の構成は今から直せない。診断は `diagnosePastStructure` が別枠で行う |
| CFEの逐次更新 | **外す**（意図的） | ガードレールが件数ぶん適用されて意味を失う。`assessFitness` で1回だけ算出する |

「外す」の2つは設計判断なので変えない。それ以外で空になっていたら不具合。
`tests/backfillStructured.test.ts` が **実際に一括入力を通してから** 下流を確かめている
（コードがあるかではなく、実データで発火するかを見る）。

#### 変換を直しても、既に入っているデータは直らない（Q-3）

`toSessionAndResult` は**取り込んだ瞬間にしか走らない**。
セッションと結果は取り込み時に作って保存するので、変換の中身を直しても
すでに端末に入っているぶんは古い形のまま残る。
上の修正を入れたあとも「週次レビューが0本のまま」だったのはこれが理由で、
コードは直っていたが、既存データには届いていなかった。

`rebuildPastDerived` が、保存済みの `PastEntry` からセッションと結果を作り直す。

- ホームを開いたときに1度だけ自動で走る（KVの `migration:past-derived` で管理）。
  本人が設定画面を開くまで壊れたままなのは、直っていないのと同じなので自動にした。
  実測値を書き換えないので、この作り直しについては確認を取らない。
- 「データ管理」からいつでも実行できる。何件作り直したかを出す。
- **設定タイムだけは戻らない。** 取り込み時に捨てていたので、元の本文が残っていない。
  推測で埋めないため、戻せない件数を数えて画面に出す。
  設定に対する評価が要る練習は入れ直してもらう。

変換の中身を変えたときは `PAST_REBUILD_VERSION` を上げること。上げないと作り直しが走らない。

### S-7 / S-8 生成の漸進モデル

**以前はカテゴリごとに固定の文面を返していた。** 高乳酸なら常に `300m × 5 r5分` で、
変わるのは設定タイムだけ。週が進んでも、直近の出来がどうでも同じ内容が出ていた。
`src/lib/core/progression.ts` が内容そのものを組み立てる。

採用した原則（出典ではなく、このアプリが採る方針）:

1. **量 → 密度 → 強度 の順に上げる。** 3つを同時に上げると、
   何が効いたのかも何がきつかったのかも分からなくなる
2. **3週上げて1週落とす（3:1）。** 4週目は本数を戻す
3. **レースに近づくほど特異的にする。** 高乳酸は Base で200m、Build以降で300m。
   レストは Build 5分 → Specific 4分と詰め、レース終盤の状況に近づける
4. **土台期に高乳酸を積まない。** 深く入る種目なので、Base では短く少なく

直近の実行状況を**内容そのもの**に反映する（M-2は設定タイムだけを動かす）:

| 直近の傾向 | 生成の動き |
| --- | --- |
| 設定より遅い（ease） | 本数 −1・レスト +15%。**量を増やさず実行できる形に戻す** |
| 設定より速い（tighten） | 有酸素高強度は本数 +1。高乳酸・中距離特異的は本数を据え置く |
| ACWR > 1.3 ＋ 疲労・未達の実測あり | 本数を戻す。ACWR単独では内容を変えない |

**テーパー期は漸進モデルの対象外。** レース前の量は M-6 と RULE-09 が決めており、
ここで別の根拠から本数を動かすと、2つの仕組みが同じ週の量を取り合う。

#### 同じ刺激内のセッション形式

`threshold / cv / high_lactate / race_economy / modeling` は、カテゴリごとに複数の
決定的な候補を持つ。ランダムには選ばず、フェーズ、進行段階、選手タイプ、
直近28日の同カテゴリ履歴、完遂・RPE・翌日の脚、直近負荷を点数化して選ぶ。
選手タイプは候補を除外する固定ラベルではなく、同程度の候補を並べる小さな重みだけに使う。

同一テンプレートの14日以内の再使用には減点を付けるが、比較や進行確認に同じ処方が必要なら
理由つきで再使用できる。14日・28日は安全性の理想値ではなく、短期の単調な反復を避けつつ
4週間の履歴を判断材料にする運用窓である。同形式で未達・RPE 9以上・翌日の脚が重い状態が
2回続けば、段階を上げず別形式を優先する。安定完遂が2回続いた場合だけ次段階を優先する。
形式を切り替えた週は、本数・速度・レストの漸進を同時に掛けない。一度に変える変数を
原則1つにして、次の実施結果から何が影響したかを追えるようにする。

選択結果は `Session.generation` にテンプレートID、`variationGroup`、進行段階、理由、
代替候補、信頼度として保存する。任意フィールドなので旧データをそのまま読め、
SQLite / IndexedDB / exportBackup / Supabase snapshot に同じSession JSONとして流れる。
セッション詳細は保存された理由を表示するため、説明文と実際の判定がずれない。

### S-9 進め方を2案出す

次のポイント練習について、**どちらも成立する2案**を出して選ばせる。
片方が明らかに劣る案だと選ぶ意味が無く、「おすすめ」を押すだけの操作になる。
状態によって2案の中身そのものを変える:

| 直近の傾向 | 2案 |
| --- | --- |
| 守れていない | 「本数を減らす」／「レストを伸ばす」（どちらも引く方向） |
| ちょうど良い | 「量を増やす」／「密度を上げる」 |
| 余裕がある | 「1本増やす」／「レストを詰める」 |

推奨は制限因子（M-7）で決める。後半の維持が課題なら密度側
（不完全回復での反復が終盤に直接効く）、そうでなければ量側（失敗しにくい）。
**推奨しない側も理由つきで出す。**

**案そのものは保存しない。** 選んだ結果を既存の `Session` に書き込むだけにする。
案を保存すると「どの案が生きているか」という状態が増え、
M-2・M-6・ルールエンジンと取り合いになる。書き込みは `editSession` を通すので、
ルール検査は従来どおり効く。

「量を増やす」は選択日から**14日間**を対象にし、最大3件までの未実施・自動生成メニューへ
保存反映する。ジョグ/ロング走はペースを変えず5分追加し、CV・閾値・神経系は
本文から本数を確実に読める場合だけ1本追加する。週全体の距離・時間増加は10%以内に抑える。
14日は次の2週間へ行動を反映しつつ、次の回復週やフェーズまで設定を持ち越さないため。
10%は「安全な理想比」の断定ではなく、既存RULE-17の15%注意域へ一度の操作で入らないための
操作上限である。完了済み、過去、手動変更、固定、回復、Taper、
`high_lactate / modeling / race_economy` は対象外。高乳酸・中距離特異的の本数は
「量を増やす」で機械的に増やさない。

置き場所はTODAY。今日がポイント練習でなければ次のポイント練習を対象にし、
対象の決め方は「設定の調整案」と同じにする（別々に決めると2枚のカードが
違うセッションの話を並べることになる）。

### S-6 他の選手のメニューを取り込む

トップ選手のメニューをそのまま真似ると、**構造は正しいのに設定だけ速すぎる**という
一番まずい形になる。守れない設定を繰り返しても、狙った刺激は入らない。

`src/lib/core/athleteConvert.ts` が、その選手の**相対強度**を自分に当て直す。

```
自分の設定 = 相手の設定 × (自分のCFE ÷ 相手の800mPB)
```

カテゴリの標準比（`GRP_RATIOS`）を使わないのはなぜか。
標準比は「そのカテゴリなら普通このくらい」という一般値で、
その選手が実際にどの強度でやっていたかは分からない。
他人のメニューを借りる目的は**その人の組み立てを再現すること**なので、
実際にやっていた相対強度を保つほうが目的に合う。
換算した設定は `CustomMenu.targetSec` に入れ、生成時は標準比より優先する。

**限界を隠さない。** 次の場合は必ず画面に出す。

- 800mPBの差が10秒を超える（タイプも練習の意味も変わってくる）
- 100m未満・1200m超（800mから離れるほど比が当てにならない）
- 設定が書かれていない（構造だけ取り込む。**推測で埋めない**）

換算値は実測ではないことも併記する。1回やってみて合わなければ動かす前提の値。
誰のメニューかは `sourceAthlete` に残す。残さないと、あとで数字の出どころが分からなくなる。

### プラン再生成と予定の識別

自動生成セッションは `s-plan-YYYY-MM-DD-am|pm` の安定IDを使い、
`origin: "generated"` を保存する。ラウンド間回復もレースIDと日付からIDを決める。
毎回時刻ベースのIDを作ると、端末内のupsertにもスナップショット同期にも同じ予定だと
伝わらず、再生成のたびに別レコードとして増えるため。

再生成で置き換えるのは、本人が編集していない自動生成の未実施予定だけ。
`origin: "manual"`、`userEdited: true`、完了・中止済み、過去入力、旧固定枠は残す。
旧データには `origin` が無いため、`s-user-*` は手動として保護し、
それ以外の非固定 `planned` だけを旧自動生成予定として置き換える。
残した手動・本人編集予定と同じ日・時間帯には、新しい自動予定を重ねない。

目標とレースはサービス層で1つの保存単位として扱い、保存後にStoreから読んだ実体を
画面へ返す。通過点レースのIDは配列位置ではなく、追加時に決めたIDを維持する。
RaceのJSONには着順ボーダー `borderPlace` とタイムボーダー `borderTimeSec` を保存する。
どちらも任意フィールドなのでDB migrationは不要で、旧Race JSONもそのまま読める。

ボーダーの正規化（`normalizeRaceBorders`）は着順 `>= 1`・タイム `> 0` だけを残し、
それ以外は未入力に戻す。`Number.isFinite` は 0 と負を通すため、これが無いと 0 が保存される。
0 が入ると `planHeatPace` の `race.borderTimeSec ?? goalTargetSec + 2` が
0 を nullish と見なさず、予選の通過目安が0秒基準（−0.5秒）になる。
画面には値が出たまま中身だけ壊れるので気づけない。
着順を `Math.max(1, ...)` で1着へ丸めないのは、丸めると「0が入ってきた」のか
「1着通過」なのかが後から区別できなくなるため（読めなかったものは推測で埋めない）。

同じ規則を `importBackup` の races にも通す。復元は `saveGoalAndRaces` を経由せず
`repo.saveRace` を直接呼ぶので、他端末が書いた壊れた値やSupabaseのpullが素通りするため。

### 統合（merge）で本人のデータを守る

`mergeById` は同じIDを無条件で上書きしていた。同期のpullも競合時の「両方を残す」も
この経路を通るので、クラウドに残っていた古い自動生成予定が、この端末の
完了済み・本人編集・固定枠・手動追加・遡り入力を消していた。
「両方を残す」と書いてあるボタンが片方を消すのは、表示と挙動の食い違いでもある。

`mergeById` に `keepExisting` を渡せるようにし、`importBackup` の sessions では
`isOwnedByAthlete`（`completed` / `skipped` / `userEdited` / `isFixed` / `backfilled` /
`origin === "manual"` / `s-user-*`）に当たるものを残す。判定の材料は `regeneratePlan` の
置き換え判定と同じで、旧データに `origin` が無いため `s-user-*` を手動として保守的に扱う。
**迷ったら守る側に倒す。** 消えたデータは取り返せないが、残ったものは後から消せる。

`replace` では保護しない。本人が競合画面で「クラウドを優先」を選んだ経路だから。

残した件数は `RestoreReport.kept` で返し、`warnings` にも文章で入れる。
**守ったことを黙っていると「同期したのに反映されない」ように見える。**
データ管理画面と同期画面の両方で表示する（`/api/backup` の応答は `{ ok, report }` の形で、
`report.warnings` を取り違えると黙って空になる）。

### OAuth 復帰は `?sync=1` の残存を前提にしない

実機で「サインインは成功するがホーム画面に戻ったまま同期画面へ遷移しない」を確認した。
`app-shell.tsx` の受け取りは、戻り先の `?sync=1` というクエリが残っていることを前提に
同期画面へ戻す判断をしていたが、このクエリは自前では守れない。
Supabase の **Redirect URLs** にこのアプリのURLを登録していないと、Supabase は
指定した `redirect_to` を無視して **Site URL** へ飛ばすため、クエリごと落ちる
（横取り耐性のための仕様で、FORGE側の不具合ではなく設定依存の外部要因）。
結果、トークンは保存されるのに画面だけホームに居座っていた。

`captureAuthRedirect` が何か拾えた時点で、それは必ず `signInWithGoogle` が発行した
`redirect_to` からの戻りである（他にこのURLへ来る経路が無い）。したがって
`?sync=1` の有無を問わず同期画面へ戻してよい。判断を `sync.ts` の
`authRedirectLanding` という純関数に集約し、`app-shell.tsx` はそれを呼ぶだけにした
（判断を通信・DOM操作から切り離してテストできるようにするため）。

### Supabase Storage の保存先を利用者ごとに分ける

以前は全利用者が同じ `forge/snapshot.json` を共有していた。Google OAuthでサインイン
できる者（想定外の第三者を含む）が同じファイルを読み書きできてしまうため、
利用者ごとに `forge/<uid>/snapshot.json` へ分ける。

`uid` はセッションの `accessToken`（Supabaseが発行したJWT）の `sub` クレームから
取り出す（`sync.ts` の `jwtSubject`）。署名検証はしない。ここでの用途は保存先パスの
組み立てだけで信頼境界には使わないため——実際の可否は Storage 側の RLS
（`(storage.foldername(name))[1] = auth.uid()`）が、リクエストごとに検証済みの
トークンで判断する。改ざんされた `sub` を渡されても、他人のフォルダには RLS が拒否する。

`accessToken` から `uid` が取り出せない場合（壊れたセッション等）は、通信せず
明確なエラーにする。共有パスへの黙ったフォールバックは、分離の意味を失わせるため
絶対にしない。

RLSポリシー（Supabase側で適用）は `docs/FORGE_REQUIREMENTS.md` の 2.2.4 を参照。

#### 「未作成」判定は複数のコードを受け入れる

新しい個人用パス（`forge/<uid>/snapshot.json`）への初回push（実機・2026-07-30）で、
実際のSupabaseは `code: "NoSuchKey"`（S3互換のオブジェクト未存在コード）を含む本文を
返した。`isMissingSnapshot` は `payload.code` を最優先で見て `"not_found"` とだけ
比較していたため、`"NoSuchKey"` と一致せず「初回同期」ではなく本物のエラーとして
扱ってしまっていた（`error` フィールドには従来どおり `"not_found"` が入っていたが、
`code` を優先していたため見なかった）。

`code` と `error` のどちらかが未存在を示していれば十分とし（`isNotFoundCode` が
`"not_found"` と `"nosuchkey"` の両方を認める）、`message`（`"Object not found"`）を
主な決め手として残した。テスト環境で使っていた仮のレスポンス形（`code`フィールドが
無い）では気づけなかった不具合で、実機での初回pushで初めて顕在化した。

### 3-1 曜日の優先・固定設定

既存の `slots` と `enabled` を残したまま、曜日ごとの `modes` を追加する。
旧データに `modes` が無い指定枠は従来どおり `fixed` として読む。

1. レースと競技日程
2. 故障・体調・安全性
3. テーパーと回復
4. 高負荷練習の間隔
5. 週全体の負荷
6. `fixed`
7. `preferred`
8. 自動生成

`preferred` は週のメニュー数を増やさず、同じ週の既存枠と交換する。
交換後に高負荷が連日になる場合は希望を見送り、自動配置を残す。
`fixed` は原則その曜日を保持し、生成したSessionにも固定元を残すが、
レース前・テーパーの安全処理で内容が変わった場合は固定扱いにしない。
固定同士が安全ルールを破る場合は、設定画面とルールエンジンが警告・変更案を出す。

### 高負荷分類と「質練習」の扱い

「質練習」は画面上のポイント練習という総称に留め、安全判定では一括カテゴリとして
使わない。保存形式の `SessionCategory` は後方互換性のため維持し、
`trainingClassification.ts` で次の主負荷へ変換する。

- `high_lactate` → 高乳酸・解糖系
- `race_economy` / `modeling` → 中距離特異的
- `cv` / `threshold` → 有酸素高強度
- `neural` → 神経・スプリント
- `aerobic` → 低〜中強度有酸素
- `off` → 完全休養・回復
- 補強は `StrengthSession` のまま筋力・補強として別管理

通常週は「2回まで」と一律に止めない。高乳酸・中距離特異的が週3日以上、
または全高負荷が週4日以上ならERROR、全高負荷が週3日ならWARNとする。
同日の複数セッションは週回数を水増しせず、高負荷「日」で数える一方、
同日・連日の配置はRULE-03で個別に検出する。

RULE-04の回数・レベルは予定構成から決めるが、実施済みの対象セッションがある場合は、
RPE・主観強度・未達/中止・翌日の脚の状態と、その週の日次疲労シグナルを警告理由へ
併記する。未実施の予定を実績として扱わない。RPE 8と疲労4/5は新しい理想値ではなく、
既存の設定調整・伝播処理と同じ運用境界であり、警告回数の基準自体は変えない。

短い完全回復の坂ダッシュ・流しは高負荷日に数えない。ただし `neural` として
保存されていても、300m反復、合計1200m超、10秒超の反復、または完全回復でない
10本超が本文から明示的に読める場合は、カテゴリ名だけで軽負荷にせず警告対象にする。
200m・1200m・10秒・10本は安全な理想値ではなく、自動生成している短い神経刺激と
スピード持久系の取り違えを検出するための運用境界である。

## FIT取込（Garmin等）Phase 1: ファイル選択と安全な受信

**Garmin Connect のiPhoneアプリには FIT を書き出す・共有シートへ渡す機能が無い**
（個別アクティビティの書き出しは Garmin Connect の **Web版**でのみ可能。
[Garmin Forums](https://forums.garmin.com/apps-software/mobile-apps-web/f/garmin-connect-web/421060/exporting-individual-activity-raw-data)）。
さらに **iOS Safari は Web Share Target API 未対応**で、PWA を共有先に登録できない
（[MDN](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Manifest/Reference/share_target)）。
この2つはコードで回避できないプラットフォームの制約なので、`share_target` は
実装しない（実現できない共有方式を動くように見せない）。現実的な導線は
「Safariで connect.garmin.com を開く → Web版でFITを書き出す（ファイルアプリに保存）
→ FORGEで通常のファイル選択」。

`validateFitBytes`（`src/lib/core/fitImport.ts`）は拡張子ではなくFITプロトコルの
ヘッダー（`.FIT`シグネチャ、`header_size`が12/14、宣言された`data_size`と実サイズの
整合）を確認する。CRC値そのものの検証はしない——Phase 2で実際の解析ライブラリ
（`fit-file-parser`、MIT、Node/ブラウザ両対応）を導入した際にデコード結果として
自然に検出できるため、Phase 1で重複実装しない。

サイズ上限は5MB。800m特化の練習記録という用途上、1ファイルは通常数十〜数百KB
（長時間の耐久種目のような大量サンプルにならない）。Web Workerはこの想定サイズ
（同期処理で数十ms以内に終わる）ではPhase 1で見送り、サイズ上限超過時の拒否と
読み込み前のサイズ確認で画面の固まりを防ぐ。

ラップ・心拍等の解析、二重登録防止、既存予定との紐付け、分析への反映はPhase 2以降。

## FIT取込 Phase 2: 解析（file_id / session / lap / record / event を区別）

`parseFitFile`（`src/lib/core/fitParse.ts`）は `fit-file-parser` のデコード結果から
FORGEの単位（km・秒/km・UTC ISO文字列）へ変換する。ライブラリの `lengthUnit: "km"` /
`speedUnit: "km/h"` オプションで単位変換自体はライブラリに任せ、ここでは
「km/h → 秒/km」の変換と、NaN・Infinity・負数・ゼロ除算の排除だけを行う
（`safeNumber`。速度0は `paceSecPerKm` を未確定にする。ゼロ除算でInfinityにしない）。

**FITのfield番号はメッセージ種別ごとに異なる**（例: `avg_heart_rate` はsessionが
field 16、lapはfield 15）。これは実際に `FitEncoder` で組み立てて `FitParser` で
デコードし、`node_modules/fit-file-parser/dist/cjs/garmin_profile.generated.js` の
プロファイル定義と突き合わせて確認した値であり、当初の想定（session/lap共通で
16番）は誤りだった。ライブラリ自身が読み解いた後の名前付きフィールド
（`avg_heart_rate` 等）を使う限り、この差異は呼び出し側では意識しなくてよい
——テスト用フィクスチャ（`tests/fixtures/fitEncoder.ts`）を作る際にだけ注意が要る。

**タイムゾーン**: FITの `timestamp` はUTC。`activity` メッセージの
`local_timestamp`（存在する場合のみ）はデバイス側のローカル時刻を表すため、
両者の差からUTCオフセットを求める。`local_timestamp` が無ければ**推測せず
未確定のまま**にする（iPhoneの現在タイムゾーンで代用しない。記録デバイスの
タイムゾーンとFORGE利用者の現在地は別物になりうるため）。

**bundleサイズへの影響と対策（コード分割）**: `fit-file-parser` はGarmin公式の
FIT SDKプロファイル定義（数千メッセージ・フィールドの定義）を丸ごと含み、
単純に読み込むとPWAの `bundle.js` が約873KB→約1307KB（+約434KB）に増える。
FIT取込は毎日使う画面ではないため、使わない利用者にまでこの増分を負わせない
よう、`scripts/build-pwa.mjs` で `splitting: true` / `format: "esm"` を有効にし、
`pwa/entry.tsx` の `FitImportCard` から `fitImport.ts` / `fitParse.ts` を
**動的import**（`await import(...)`。ファイルを実際に選んだ時だけ）にした。
結果、`bundle.js` は約873KB→約880KB（+約7KB、実質ほぼ増えない）に収まり、
FIT関連コード（約415KB）は別chunkに分離される。

ESM出力になるため `pwa/index.html` の `<script>` は `type="module"` にした。
chunkのファイル名にはハッシュが入るため（`chunk-[hash].js`）、内容が変われば
ファイル名も変わる。`pwa/sw.js` の `isAppShell()`（network-first対象）には
含めていない——ハッシュ付きファイル名は「同じ名前なのに中身が古い」が
原理的に起きないため、cache-first（同一origin向けの既定の分岐）で問題ない。

**新たに生まれた制約**: 一度もFIT取込を開いたことが無い状態でオフラインだと、
chunkがまだキャッシュされていないため使えない（起動そのものは影響しない。
FIT取込を開こうとした時だけ失敗する）。一度オンラインで開けば、以後は
Service Workerのキャッシュ経由でオフラインでも使える（E2Eで確認済み）。

## FIT取込 Phase 3: ラップ→区間の自動分類（ウォームアップ／メイン／リカバリー／レスト／クールダウン）

`classifyLaps`（`src/lib/core/intervalClassify.ts`）は、Phase 2で抽出したlap列を
区間種別に分類し、信頼度（0〜1）とともに返す。**ルールベースのみ（LLM不使用）。
同じlap列からは必ず同じ結果になる。保存時は元ファイル／自動解析／手動修正／
結果確認を分離し、「自動判定した結果を見せて、本人が判断・修正できる」
ところまでに留めている。

**使う信号はペース（`elapsedSec / distanceKm`）と列内の位置だけ。** 心拍は
個人差・当日のコンディションで変動が大きく、閾値を機種・体調に依存させたくない
ため使っていない。

判定手順:
1. 距離0のlap（手動lap・一時停止）は問答無用で「レスト」（固定信頼度0.85）
2. 距離または時間が欠けているlapは推測せず「不明」（信頼度0.15）
3. 残りのlapのペースを昇順に並べ、**隣り合う値の比が最も大きいところ**で
   速い群と遅い群に切る。その比が **1.20（20%）未満**なら
   （`MIN_GROUP_SEPARATION`）2つの群に分かれていないと見なし、切らない——
   800m系インターバルはメインがリカバリーより明確に（体感でも数値でも20%以上）
   速いので、ここを下回る差しかないものはインターバル構成ではない
   （ビルドアップ走・ペース走を誤ってメイン扱いしないため）
4. 「速い」lapが1つも無ければ、インターバル構成があるとは判定できないため
   **推測せず全て「不明」**にする（低信頼度0.3。単なる継続走をメインだと
   決めつけない）
5. 「速い」lapが見つかれば、最初の「速い」lapより前は「ウォームアップ」、
   最後の「速い」lapより後は「クールダウン」、間に挟まれた「速い」lap以外は
   「リカバリー」、「速い」lap自体は「メイン疾走」

信頼度は「遅い群の中で最も速いもの」（＝休息側の下限）からのペース差の大きさに
応じて連続的に決まる（境目に近いlapほど信頼度が低い）。
比較対象のlapが1件以下の場合は分類自体をせず「不明」＋警告。

### なぜ中央値をやめたか（2026-08-01）

当初は「全lapのペースの中央値より7%以上速い」（`FAST_RATIO = 0.93`）で切っていた。
これは**実運用で壊れた**。「fit読み込み自体はできたけどメニュー内容の読み取りが
うまくいってない」という報告の原因がこれ。

時計で「本」と「休み」だけラップを押すと、ウォームアップ・クールダウンのlapが
FITに入らない。すると疾走と休息がほぼ半々になり、**全lapの中央値が
「最も遅い疾走」の上に乗る**。中央値×0.93を通れるのは最も速い1本だけになり、
残りの本は「最後の速いlapより後ろ」＝クールダウンに落ちる。
`300m × 4`（39/40/41/42秒）が **`300m × 1`** として記録されていた。

中央値は、2つの母集団が混ざった列では境目の指標にならない。混合比（疾走と
休息の件数比）で位置が動いてしまうためで、W-upとC-downがあれば偶然うまく動き、
無いと壊れる。**ソートしたペース列の最大の隔たりで切れば、混合比に左右されない。**

副次的に、ビルドアップ走（1km を 300→285→270→255→240秒）の扱いも直った。
以前は最速の1kmだけが中央値×0.93を通り、実在しない「1km × 1」という
インターバルとして記録されていた。隣接比が最大でも約1.06しかないので、
今は `no_interval_structure` を返して**判定できないと正直に言う**
（読めなかったものを推測で埋めない）。

**「最初に閾値を超えた隔たり」ではなく「最大の隔たり」を選んでいる理由。**
前者だと、突っ込んで垂れた1本目（他の本より20%以上速い）でそこが切れてしまい、
残りの本を取りこぼす——今回直したのと同じ「本数が減る」不具合が別経路で戻る。
最大の隔たりなら、疾走と休息の差（この人の練習では2倍以上ある）が常に勝つ。
代償として、休息側の内部のばらつきが疾走と休息の差を上回る構成
（リカバリーが6:00/kmでクールダウンが歩き、など）では休息を本と数えてしまう。
ただし歩きは距離0のlapとして記録されることが多く、その場合は手前の
「レスト」判定で除かれるため、こちらの方が起きにくいと判断した。
どちらに転んでも取込画面のプルダウンで本人が直せる。

`pwa/entry.tsx` の `FitImportCard` に区間ごとの行（lap番号・ペース・種別の
プルダウン・信頼度%）を表示する。プルダウンでの変更はこの画面上だけの
一時的なものであり保存しない（保存対応はPhase 4）。`intervalClassify.ts` は
重い依存を持たないため、Phase 2の `fitImport.ts`/`fitParse.ts` と違って
動的importにはしていない（bundleへの影響は無視できるほど小さい）。

検証: T-4で分類の閾値を壊して赤に戻ることを確認して復元。E2Eに実際のFIT
（ウォームアップ→メイン→リカバリー→メイン→クールダウンの構成）を使い、
5行の分類結果・信頼度表示・プルダウンでの手動修正の反映を確認する経路を追加。

## FIT取込 Phase 4: 信頼層を分けたデータモデルでの保存

二重登録防止・既存予定との紐付けはPhase 5-6（ここではやらない）。

**4層**: ①元ファイル（生バイト。base64で保持）②自動解析（`FitParseResult` +
自動判定した`IntervalClassifyResult`）③本人が直した区間種別（`confirmedKinds`）
④FITには無い本人確認値（カテゴリ・RPE・達成状態・主観強度）。①〜③は
`FitImportRecord`（`src/lib/core/fitToSession.ts`）として確認前から保存する。
④が揃った後だけ`Session`/`SessionResult`を導く純粋関数が`fitToSessionAndResult`——
`PastEntry`の`toSessionAndResult`（`backfill.ts`）と同じ考え方で、
確認済み層だけから機械的に決まり、何度re-runしても同じ結果になる。
分類ロジックを直した後の再導出用に`rebuildFitDerived`も用意した
（`rebuildPastDerived`と同じ理由）。

**生バイトを保存するかどうか**は本人に確認して「保存する」を選択。理由:
将来解析ロジックを直したときに、Garmin Connectへ再度取りに行かずに
再解析できる。ストレージ・バックアップサイズは増えるが、800m特化・
月に数回の取込という前提では実害は小さいと判断した。

**メイン疾走→本、リカバリー→レスト**: 各メインlapの直後から、次の
「メイン」または「クールダウン」の**手前まで**のlapを合算してその本の
`restAfterSec`/`restAfterDistanceM`にする。クールダウンまで含めてしまうと
最後の本のレストが実際より長く出るバグを一度作り、T-4で検出して直した
（`fitToSession.ts`のコメント参照）。

**カテゴリ判定**: 目標（CFE）が設定されていれば、各メイン本の実測ペースを
GRP（設定ペースの基準）と比較する`categoryFromTarget`
（`bulkImport.ts`。一括入力の設定タイム判定と同じ関数）で決める。
CFE未設定なら距離だけの暫定値にし、その旨を警告として返す
（`推測で埋めない`が、必須項目なので「暫定であること」を明示して埋める）。
メインが1本も無ければ持続走として`category: "aerobic"`固定。

**日付・時刻**: 先頭lapの開始時刻＋`utcOffsetSec`から求める。
`utcOffsetSec`が無ければUTC基準の日付を暫定値として使い、
「タイムゾーン不明のため日付がずれている可能性がある」と警告する
（日付は必須項目なので空にはできないが、確定した値であるかのようには見せない）。

`backfilled: true`を立てる。既存の過去データ遡り入力と同じ扱いになり、
ルールエンジンの評価対象・自動生成の上書き対象から外れる
（`isOwnedByAthlete`が`backfilled`を見ているため、追加のコード変更なしで
バックアップのmerge時にも保護される）。

保存はAPI経由（`/api/fit-import`・`pwa/api-shim.ts`の両方に追加）。
クライアントで既に解析・分類済みのデータをそのままPOSTし、**サーバー側では
再解析しない**——本人が画面で確認・修正した内容と、実際に保存される内容を
一致させるため（重いfit-file-parserをサーバー側に持ち込む必要もなくなる）。

`saveFitImport`/`listFitImports`を`Store`に追加（SQLiteは`fit_imports`
テーブル、IndexedDBは`fitImports`配列）。バックアップの書き出し・復元
（M-12）にも対応（`ID_KEYED_COLLECTIONS`に追加）。

UIは`FitImportCard`に「この内容で登録する」ボタン。最初の保存後はボタンを引っ込め、
本人確認欄へ切り替える。確認欄は再読込後も保存済みFITから復元する。

検証: `fitToSessionAndResult`の単体テストに加え、本人確認前はSession/Result/CFEを
作らないこと、確認後だけ本人入力値で正式結果を作ること、正式結果の保存に失敗しても
元FITを確認待ちで保持し、不完全なSession/Resultはトランザクションで残さないことを
確認。E2Eは「解析保存→本人確認→記録画面への反映」まで通す。

**developer field**（機種独自の拡張フィールド）は検出のみ行い、内容は解析しない
（`hasDeveloperFields`）。ラップの区間復元（ウォームアップ／メイン疾走／
リカバリー等の分類）はPhase 3、信頼層を分けたデータモデルでの保存はPhase 4。

## FIT取込 Phase 5: 二重登録防止

同じFITファイルをもう一度選んで登録すると、Phase 4までは**完全に別の記録
として二重登録**されていた（`FitImportRecord.id`が`fit-${Date.now()}`で
毎回新規生成されていたため）。

**方針**: 元ファイル（`rawBytesBase64`）が既存の取込と**完全一致**すれば、
そのときのidをそのまま再利用する。`saveFitImport`/`saveSession`/
`saveResult`はどれも同じidへの`INSERT...ON CONFLICT DO UPDATE`
（IndexedDBでも同id上書き）なので、同じファイルの再登録は新規の二重登録では
なく**上書き**になる——一括入力（`pe-bulk-*`）やApple Health（`ah-*`）が
内容から決まるidで自然に二重登録を防いでいるのと同じ考え方（README「保存の
パターン」参照）。ハッシュ関数は使わず、生バイト列の文字列としての完全一致で
判定する（個人利用で件数も少なく、誤検知が原理的に起きないため）。

完全一致以外（同じ活動をGarmin Connectから2回書き出した場合など、生バイトが
変わりうるケース）は検知しない。**推測で「同じ活動だろう」と判定しない**——
別記録として扱われる。

副次的に見つかった問題: `id`の生成が`Date.now()`だけだったため、短時間に
**別の**FITファイルを続けて取り込むとミリ秒が衝突し、無関係な記録を
上書きしてしまう可能性があった（二重登録防止の前提が崩れる）。乱数を足して
衝突を避けるよう修正（`fit-${Date.now()}-${ランダム6文字}`）。

`importFitFile`の戻り値に`duplicate: boolean`を追加。`FitImportCard`は
`duplicate`に応じてメッセージを出し分ける
（「登録しました」 vs 「既に取り込み済みのファイルでした。内容を更新しました」）。

**検証**: 単体テストで、同じ生バイト列を2回登録するとidが再利用され件数が
増えないこと、1回目と分類を変えて2回目を登録すると実際に内容が更新される
こと、生バイト列が違えば別記録になることを確認。E2Eで実際のUI操作
（同じFITファイルを選び直す→文書ごと再読み込みしないとinputのchangeが
発火しないことが分かったため`about:blank`経由の再読み込みを挟む）から、
登録メッセージの出し分けと、記録画面に1件のまま留まることの両方を確認。
**T-4で一致判定を無効化し、両方の確認項目が赤に戻ることを確認して復元。**

## FIT取込 Phase 6: 既存の計画済みセッションとの紐付け

**通常の「結果を記録する」経路（`processResult`）を先に調べた。** 単に保存
するだけでなく、セッションの`status`を`planned`→`completed`にし、
**CFE（現在地の推定）を更新し、ルールエンジンを走らせ、以降の予定へ波及**
（再ペース配分）する。これに対し、Phase 1〜5のFIT取込は`backfilled: true`を
立てて直接保存するだけで、これら全部を意図的にスキップしている（過去データの
遡り入力と同じ「過去のことは今から直せない」という扱いのため）。

**方針**: 計画済み（`status: "planned"`）のセッションに紐付けた場合だけ、
正規の記録経路（`processResult`）を通す。「今日やる予定だった練習を、手入力の
代わりにFITで正確に記録する」ことと同じなので、手入力した場合と全く同じ扱いに
するのが筋が通っている。紐付けない場合（対応する予定が無い古いデータの取込
など）は、今まで通りbackfilled扱いのまま。

**画面の流れ**: 「この内容で登録する」を押すと、サーバー側で日付を確定し、
その日に計画済みのセッションがあるか調べる。
- 無ければ：今まで通りそのまま登録（見え方は変わらない）
- 1件あれば：保存せずに「◯月◯日に計画済みの練習があります。この記録として
  反映しますか？」を表示し、①この予定に記録する ②新しい記録として別に
  登録する のどちらかを選んでもらう
- 複数あれば：候補を全部出して選んでもらう

`src/lib/core/fitToSession.ts`を分割した:
`deriveFitActuals`（lap列からペース・カテゴリ・レストなどの実測データだけを
導く、Session/Resultの形にはしない）／`buildBackfilledSessionAndResult`
（従来通りの新規backfilledセッション）／`buildLinkedResult`（既存セッションの
idを使うSessionResultだけを作る。`backfilled`は立てない）。既存の
`fitToSessionAndResult`はこの2つの組み合わせとして後方互換のまま残した。

`importFitFile`（`src/lib/service.ts`）は`linkToSessionId`を受け取る:
省略時（1回目）は確認要否だけを判定して返す（`needsConfirmation: true` +
候補一覧）。文字列を渡すとそのセッションへ紐付け、`null`を渡すと紐付けず
新規登録する。APIルート（`app/api/fit-import`・`pwa/api-shim.ts`）は
`body`をそのまま渡す実装だったため、新しいフィールドの追加だけで両方に対応できた。

**FITから分からない値を埋めない**: RPE・主観強度・達成状態・本来の練習カテゴリは
FITに入っていない。以前は有酸素をRPE 3、それ以外をRPE 8、達成状態を`achieved`
として補完していたが、紐付けた予定ではそのまま`processResult`へ流れ、CFE・完遂率・
次回提案を推測値で動かしていた。現在は次の二段階に分けている。

1. 元FIT、解析結果、本人が直したlap分類だけを`resultConfirmation: pending`で保存する
2. 本人がカテゴリ・RPE・達成状態・主観強度を入力してからSessionResultを作る

確認待ちのFITは元ファイルを失わず、再読込後も確認欄へ戻れるが、CFE、ACWR、完遂率、
progression、adaptive proposalには入れない。旧形式の`FitImportRecord`には確認状態が
無いため、確認済みだったと推測せず同じく確認待ちとして扱う。旧SessionResultは削除せず
保持し、`trustedResults`で分析対象から隔離する。本人確認後は同じresultIdへ上書きし、
紐付け済みなら既存の`processResult`が以前のCFE寄与を取り消してから正しい値を入れ直す。

**検証**: 単体テストで、計画済みセッションが無ければ確認なしで従来通りに
なること、あれば保存せずに確認を返すこと（何も保存されていないことも確認）、
複数あれば全候補を返すこと、紐付けを選ぶと実際に`processResult`経由で
status変更・CFE計算が走ること（`backfilled`は立たない）、「新しい記録として
登録する」を選ぶと計画済みセッションはそのまま残り別記録になることを確認。
E2Eでは実際に計画済みセッションを作り、同じ日付のFITを取り込み→紐付け選択→
RPE・達成状態・主観強度の本人確認→カレンダー上のセッションが実際に`completed`に
なることまで確認
（このテスト専用に足したセッションは、後続の間隔違反テストに影響しないよう
テスト終了時に削除している）。**T-4で計画済みセッションの検出処理と、
`processResult`経由の保存をそれぞれ無効化し、両方とも赤に戻ることを確認して
復元。**

## Apple ヘルスケア連携

HealthKit の API は iOS ネイティブアプリ専用で、Safari / PWA からは呼び出せません
（プラットフォームの制約であり、コードで回避できません）。そのため本アプリでは
iPhone 標準の「すべてのヘルスケアデータを書き出す」で出力されるファイルを取り込む方式です。

取り込んだデータは表示のためではなく、次の変換のために使われます:

- 睡眠・安静時心拍・HRV → 疲労シグナル（4-5-8）
- ランニング（3km以上）→ 用途不明のFitnessMarkerとして保存（LTへは自動採用しない）

主観入力（脚の疲労・モチベーション）はセンサー値で上書きしません。
自転車・水泳などランニング以外のワークアウトはFitnessMarkerにしません。
ランニングもHealthKitだけでは閾値走・回復ジョグを区別できないため、距離だけでLT走と推測しません。

### R-2 起動画面

起動時の約2.8秒に、読める情報を**1つだけ**出します。
出すのは目標までの距離（レースまでの日数と、目標タイムとの差）。
起動のたびに見る場所なので、毎日少しずつ動く値が向いています。
蛍光グリーンの軌道が800mの2周を描き、ゴール発光、FORGE、サブタイトル、
動的なレース情報の順に出ます。発光はゴールの1回だけで反復させません。

技術的な制約が2つあります。

- **スプラッシュは `bundle.js` の読み込み前に描画されるので、その場ではDBを読めません。**
  前回の起動時に `app/components/splash-cache.ts` が localStorage へ書いた値をまず読みます。
  React起動後は `/api/dashboard` の最新値を同じ画面へ通知して差し替えます。
  文字列の組み立てはTS側（テストあり）に置き、`index.html` でやるのは
  「保存したレース日から今日までの日数を引く」だけにしています。
  何日も開かなかったときに古い日数をそのまま出さないためです。
- **`index.html` のスクリプトは `bundle.js` と同じスコープです。**
  どちらもクラシックスクリプトなので、トップレベルの `let/const` を共有します。
  素で `const t` と書くと minify後の1文字変数と衝突し、
  スクリプト全体が落ちてスプラッシュが消えなくなります（アプリは動いているのに真っ暗に見える）。
  必ずIIFEで囲み、変数名も1文字を避けます。

初回起動（保存が無い）では「データ読込中」、読込後もレースが無ければ「レース未設定」と出します。
E2Eが保存あり・なしの両方を確認しています
（`bundle.js` を止めてスプラッシュを固定し、スクリーンショットを `shots/` に残します）。

**アニメーション完了とアプリ初期化完了の両方を待ちます（S-1）。**
PWAはIndexedDB読込・API shim・React描画後に `forge:app-ready` を通知し、
通常時は最低2800msを確保します。4500msを超えたら認証・保存データを読込中だと明示し、
9000msで再読込ボタンを出すため、無言の永久ロードにはなりません。
初期化失敗時はエラー画面と再読込操作を出し、オフラインならその状態を説明します。
`prefers-reduced-motion` では軌道アニメーションを止め、650msの短い静止表示に切り替えます。
Next.js版は `LaunchSplash` が同じ表示とdashboard読込を担当します。

## S-11 同期（Googleログイン＋Supabase）と Appleヘルス

**設定しなければ何も起きません。** アプリはこれまでどおり端末の中だけで動きます。
同期は足すだけの機能で、使わない選択がそのまま成立します。

### 方式: スナップショット同期

M-12 の書き出し（`BackupFile`）をそのままクラウドに置きます。
レコード単位の同期にしないのは、全エンティティに更新時刻と削除の墓標が要り、
`Store` の51メソッド × 2実装に同じ変更を入れることになるためです。
利用者は1人・端末は1〜2台なので、そこまでの精度に見合いません。

**黙って上書きしません。** どちらが動いたかは「前回同期した状態」から判断します。
時刻の新しさだけで決めると、時計がずれた端末の古いデータで新しいデータを潰します。
両方が動いていたら必ず選ばせます（統合／この端末を優先／クラウドを優先）。
判断は `src/lib/core/sync.ts` にあり、**ネットワークを持ち込んでいません**（テスト可能）。

SDKを入れず REST を直接叩いています。使うのは「サインイン」と
「1つのファイルの読み書き」だけで、数百KBのSDKは起動時間に直接効くためです。

### Supabase の準備（1回だけ）

1. https://supabase.com でサインアップ → **New project**（無料枠で足ります）
   - Region は **Northeast Asia (Tokyo)**
2. **Storage** → New bucket → 名前を `forge`（Private のまま）
3. bucket のポリシーを追加（**自分のフォルダだけ**読み書きできるようにする）
   - Storage → forge → Policies → New policy → *For full customization*
   - 対象roleは `authenticated`
   - `SELECT`: `using (bucket_id = 'forge' and (storage.foldername(name))[1] = auth.uid()::text)`
   - `INSERT`: `with check (bucket_id = 'forge' and (storage.foldername(name))[1] = auth.uid()::text)`
   - `UPDATE`: 同じ条件を `using` と `with check` の両方に設定
   - `bucket_id = 'forge'`だけの条件（`(storage.foldername(name))[1] = auth.uid()`が無い版）は
     **絶対に使わないこと**。それだと同じSupabaseプロジェクトでサインインできた
     他の誰か（本人以外）が、他人の`<uid>/snapshot.json`を読み書きできてしまう。
     アプリのコード側は`forge/<uid>/snapshot.json`というパス規約に沿って保存先を
     組み立てるが（`app/components/supabase.ts`の`snapshotObjectPath`）、
     **実際にそれを強制しているのはこのRLSポリシーだけ**であり、パスの
     組み立ては利便性のためだけで信用の根拠にはならない。
   - 初回アップロードにも、Storage APIが保存した行を返すための`SELECT`が必要。
     `INSERT`だけでは「new row violates row-level security policy」で失敗する。
   - 上書き保存（`x-upsert: true`）には`SELECT`・`INSERT`・`UPDATE`の3つが必要。
   - `DELETE`ポリシーも同じ条件で作っておく（アプリのコードからは現状呼んで
     いないが、Supabaseダッシュボードから手動で古いオブジェクトを消す場合の
     安全のため。「データ削除とプライバシー」節を参照）。
   - bucketのMIME type制限を`application/json`、サイズ上限を50MB
     （`BACKUP_MAX_BYTES`と同じ）に設定しておく。
   - 上記すべてのSQLは`supabase/migrations/0001_forge_storage_rls.sql`に
     まとめてある。**自動適用はしない**——SupabaseのSQL Editorに手動で
     貼り付けて実行すること。既存ポリシーの確認・削除・新規作成・
     確認クエリ・手動テスト手順・ロールバック・既存データの移行注意点まで
     すべてそのファイルに書いてある。
4. **Authentication → Providers → Google** を有効化
   - Google Cloud Console で OAuth クライアントID（ウェブ）を作る
   - 承認済みリダイレクトURIに、Supabaseが表示する
     `https://xxxx.supabase.co/auth/v1/callback` を登録
   - クライアントIDとシークレットを Supabase に貼る
5. **Authentication → URL Configuration** を設定
   - Site URL: `https://rio01100801-gif.github.io/trainmiddle/`
   - Redirect URLsには、アプリの **設定 → 同期 → 接続診断** に表示される
     `OAuth redirectTo` をそのまま追加する
   - 現在のPWAでは、起動URLに応じて次のどちらかになる
     - `https://rio01100801-gif.github.io/trainmiddle/?sync=1`
     - `https://rio01100801-gif.github.io/trainmiddle/index.html?sync=1`
   - Next.js版も使う場合は、そのoriginの `/sync` も追加する
     （開発時の例: `http://localhost:3000/sync`）
   - Supabaseは許可されていない `redirect_to` を使わずSite URLへ戻すため、
     ここが不足するとサインイン後にFORGEホームへ戻る
6. **Settings → API Keys** から次の2つを控える
   - Project URL（`https://xxxx.supabase.co`）
   - **Publishable Key**（`sb_publishable_...`）

アプリの **設定 → 同期** に6の2つを入れて保存し、Googleでサインインします。

⚠️ **Secret Key / service_role キーは絶対に入れないこと。**
あればRLSを迂回してデータを読めます。Publishable Key（旧anon key）は
公開クライアント用なので端末に置いて構いません。

設定は練習データとは別に、現在の実行環境の `localStorage` へ保存します。
保存時に空白・改行・全角英数記号・URL末尾スラッシュを正規化し、
書いた値を再読込して一致した場合だけ成功表示にします。
接続先を変えた場合は、別プロジェクトのユーザーJWTを再利用しないよう、
サインイン状態と最終同期情報を解除します。REST通信は操作ごとに最新設定から作るため、
module scopeに古いSupabaseクライアントを保持しません。

「接続をテスト」は `/auth/v1/settings` のHTTP成功だけでなく、
Supabase Auth設定のJSONであることまで確認します。画面にはキーを出さず、
使用中ホスト・HTTP status・タイムアウト・CORS・DNS/通信失敗の種別を表示します。

⚠️ iOSのホーム画面から起動したPWAでは、サインインの遷移先がSafariで開いて
**PWAに戻ってこないことがあります**。PWAとSafariはストレージが別なので、
その場合はPWA側でもう一度設定・サインインが要ります。
Safariタブとホーム画面PWAの両方で **接続診断の実行環境・origin・使用中ホスト**
を確認してください。

URLを間違えたあとも古い値が疑われる場合は、**設定 → 同期 → 接続設定を消す**
を1回実行し、PWAを完全に閉じて開き直してから正しい値を保存します。
この操作が消すのはSupabase設定・サインイン状態・最終同期情報だけで、
IndexedDB内の練習データは消しません。Service Worker cacheにも設定値は入りません。

認証はクライアントだけで完結するSupabaseのimplicit flowです。
成功時のaccess token / refresh tokenはURL fragmentから受け取って直ちにURLから除きます。
PKCEの認可コードを使っていないため、サーバー側のcode交換処理はありません。
Storage通信の直前にaccess tokenの有効期限を確認し、残り60秒以下ならrefresh tokenで
更新してから通信します。60秒は認証の安全性を表す閾値ではなく、更新中の通信時間や
端末時計のわずかな差で、書き込み途中に期限切れになることを避けるための余裕です。
更新できない場合はローカルデータを変更せず、再サインインが必要だと表示します。

### 2026-08-04 データ完全性・処方安全性の追補

- PWA起動時にIndexedDB読込が失敗した場合、復旧用localStorageも読めなければ
  空データとして起動しない。起動エラーで書き込みを止め、既存データを空状態から
  上書きする経路を閉じた。初回起動（IndexedDB読込成功・保存行なし）は従来どおり。

  だけを初回起動として扱い、退避済みデータが消えたように見える経路を閉じた。
- プラン再生成と通常の結果登録を`Store.transaction`で包んだ。削除後の生成失敗、
  結果保存後のCFE更新失敗などが起きても操作前へ戻る。
- SQLiteは`session_results.session_id`を一意化し、旧重複は最終保存行を残して移行する。

## P0監査 対象6: 危険なトレーニング提案の防止

既存のルールエンジン（RULE-01〜22）は間隔・頻度・テーパー・固定枠保護などを
カバーするが、**「そもそも物理的にありえない数値」を弾く仕組みがどこにも

1. `addSession`（予定を手動で足す。カレンダーの＋）
2. `editSession`（予定を編集する。**`force`でも越えられない**——ルール違反は

3. `regeneratePlan`（自動生成）: 生成ロジックのバグで物理的にありえない

実際に拾う**ことを確認した——`checkPastEntry`が過去データで防いでいたのと

確認。生成ロジックにバグを注入する意味のあるテストは作れなかったため、

## P0監査 対象3: Next.js APIの認証・認可

配信されているPWA（gh-pages）はこのNext.jsサーバーを一切使わない
（`pwa/api-shim.ts`がIndexedDBに直接アクセスするため）。このAPIが動くのは
`npm run dev`/`npm run start`でのローカル動作確認時だけだが、30個の
`route.ts`全てが呼び出し元を一切確認せず、`app/api/backup`の
`?download`は**DB全体を誰にでも返す**状態だった。

**分かったこと**: `next dev`/`next start`は**ホスト指定なしだと`0.0.0.0`
（全ネットワークインターフェース）で待ち受ける**。つまり既定のままだと、
同じLAN上の別端末から`/api/backup?download=1`にアクセスするだけで
全データを読める状態だった。

**対応**:
1. `package.json`の`dev`/`start`スクリプトに`-H 127.0.0.1`を追加し、
   ローカルホストだけで待ち受けるよう明示的に固定した（実機で
   `next dev`のログの`Network:`が`127.0.0.1`になることを確認）
2. `middleware.ts`（新規）で、`FORGE_API_TOKEN`環境変数を設定した場合だけ
   全`/api/*`に共有シークレットの一致を要求する。1人利用のローカル
   開発ツールに本格的なログイン機構は過剰なので作らない。未設定
   （既定）ならローカル開発の摩擦を増やさないためチェックしない——
   ①の「ローカルのみ待受」という前提が崩れた場合（意図的なポート
   転送・将来のホスティング等）への備えとして、必要な人だけが有効化する

**検証**: 実際に`npm run dev`を起動し、`Network:`表示が`127.0.0.1`になる
ことを確認。`FORGE_API_TOKEN`を設定した状態と未設定の状態それぞれで、
ヘッダ無し・不一致・一致の3パターンをcurlで実行し、401/401/200になる
ことを確認。**このmiddlewareはNext.jsサーバー機能そのものであり、
配信されているPWA（IndexedDB＋api-shim経由、Next.jsサーバー不使用）には

この変更を継続的に検証する自動テストは無い。手動確認のみ）。

## 統合監査（入力→保存→同期→分析→提案→バックアップ）

FIT/Garmin取込（Phase 1〜6）が既存のサブシステムと正しく噛み合っているかを、
7つの結合点について確認した。**FIT由来のセッションは2種類ある**——
`backfilled: true`（対応する計画が無いときに作る新規セッション。過去データの
遡り入力と同じ扱い）と、紐付け済み（Phase 6。計画済みセッションに
`processResult`経由で記録するため`backfilled`は立たない）。両方が正しく
扱われるかを見る必要がある。

**PASSだった5点**: ACWR/負荷計算（`dailyLoads`は未フィルタの全セッションを
受け取っており、backfilledも負荷に数える——ルール評価から外すのとは別）、
週次レビュー（M-11）、カバレッジ確認、`fitImports`の同期ラウンドトリップ
（`app/sync/page.tsx`が`/api/backup`経由で`exportBackup`/`importBackup`を
通ることをコードで確認）、`isOwnedByAthlete`の保護（backfilled・紐付け済み
（`status: "completed"`）の両方がOR条件でカバーされている）。

### 見つかったバグ1: 週次サマリーから過去データが抜け落ちていた

`weeklySummary`（`src/lib/core/rules.ts`。ホームと分析画面の週間カテゴリ集計・
転移度スコア・高乳酸28日頻度）が`ctx.sessions`を使っていた。これは
`buildRuleContext`が**ルール評価用に`backfilled`を除いたリスト**であり、
「その週に実際に何をやったか」の集計としては過小評価になる。ACWR・週次
レビュー・カバレッジ確認はいずれも未フィルタの全セッションを使っており、
**ここだけが食い違っていた**。

`RuleContext`に`allSessions`（未フィルタ）を追加し、`weeklySummary`だけを
そちらに切り替えた。ルール評価そのものは今まで通り`sessions`（backfilled
除外）を使う——過ぎた日の練習構成は今から直せないため、ルール違反として
出してもノイズにしかならない、という既存の判断は変えていない。

これはFIT取込で新しく生まれた問題ではなく、一括入力（`PastEntry`）由来の
過去データでも同じことが起きていた**既存のバグ**。

### 見つかったバグ2: `rebuildFitDerived`が紐付け済みの取込を壊す

`rebuildFitDerived`（`src/lib/service.ts`）は保存済みのFIT取込から
Session/SessionResultを作り直す関数で、分類ロジックを直したときに既存の
取込ぶんへ反映するためのもの（`rebuildPastDerived`と同じ役割）。

これが全レコードを無条件に`fitToSessionAndResult`（＝
`buildBackfilledSessionAndResult`）へ通していたため、**紐付け済み（Phase 6）
のレコードを作り直すと、元の計画済みセッションではなく新規の
`fit-s-${record.id}`セッションを作ってしまう**。結果は新しい方に紐付き、
元の計画済みセッションは結果を失って孤立する。

`record.sessionId === \`fit-s-${record.id}\`` かどうかで「backfilledとして
作られたか」を判定し、紐付け済みなら取込時と同じ経路（`buildLinkedResult` +
`processResult`）で作り直すようにした。紐付け先のセッションが既に削除されて
いた場合は、**新規作成に化けさせず**`orphaned`として件数だけ報告する
（黙って別物を作らない）。

現状この関数はどのAPIルートからも呼ばれておらず（テストのみ）**潜在バグ**
だったが、READMEにも「分類ロジックを直した後に実行するもの」と書いてある
以上、いずれ実行した瞬間に紐付け済みの取込がすべて壊れるところだった。

**検証**: 両方のバグについて、直す前の状態に戻すとテストが実際に赤くなる
ことを確認（T-4）。バグ2は「紐付け済みを作り直しても新規セッションが
増えず元のセッションのまま更新される」「紐付け先が消えていたら新規作成
せず件数だけ報告する」の2件を追加し、`wasBackfilled`を常に`true`にする
改変で両方とも赤くなることを確認した。

### 指摘したが今回直していないこと

バックアップ・同期スナップショットには**FIT元ファイル（base64）が全件入る**
（`exportBackup`が`fitImports`をそのまま含めるため）。取込が増えるほど
サイズが際限なく膨らみ、Supabaseスナップショットのサイズとモバイル回線での
転送量に効いてくる。正しさの問題ではなく設計上の判断（保持期間・間引きの
方針）が要るため、今回は直さず記録に留める。

## トレーニングロジック統合監査（能力推定→負荷判定→安全制御→メニュー生成→警告→説明表示）

新しい理論への全面変更ではなく、**既存の実装が事実（生理学的・競技的な妥当性）と
矛盾していないか**、**同じ判断が画面によって食い違っていないか**を監査した。
新規理論の追加はしていない。見つかった3件を直し、直さなかった判断は理由つきで
残す。

### 見つかったバグ1: 目標タイムがCFE（能力推定）に混入していた

`baseTime(cfeSec, targetSec, phase)`はセッションの設定ペース（`targetPaces`）を
作るときに、フェーズが進むほど目標タイムを混ぜる（Base 0% → Taper 100%）。
これは設定ペースの生成としては正しい仕様。

問題は`updateCfeFromResult`（`src/lib/core/cfe.ts`）の未達幅（実測−設定の差を
800m換算する処理）が、この**目標混入済みの設定ペース**をそのまま基準にしていた
こと。同じ実測タイムでも、目標を厳しく設定しているセッションのほうが「未達幅」
が大きく計算され、CFE（現在の能力推定）がより大きく下がる。**目標を上げただけで
実力が下がった扱いになる**——CFEは能力の推定、設定ペースは今日出せる値、という
本プロジェクトの原則（このファイル冒頭）に反する、目標タイムから現在能力を
逆算する典型的な混入パターン。

**修正**: 未達幅の基準を「CFEのみから作った場合の設定ペース」に正規化してから
比較するようにした。`CfeUpdateContext.goalTargetTimeSec`（呼び出し側が
`repo.getGoal()?.targetTimeSec`を渡す）が指定された場合だけ、
`targetPerM *= cur / baseTime(cur, goal, phase)`で目標混入分を打ち消す。
`GRP_RATIOS`・未達幅の計算式そのもの・0.3×信頼度の更新率は変えていない
（変える根拠が無いため）。呼び出し箇所は`src/lib/service.ts`の
`processResult`一箇所のみ。

**検証**: 同じ実測（600mを87秒×3）に対し、緩い目標（111.0秒）と厳しい目標
（95.0秒）から生成した設定ペースで比較し、CFEの動きが完全一致することを確認
（`tests/cfe.test.ts`）。修正を外すと約0.45秒の差が出て再現することをT-4で確認
済み。

### 見つかったバグ2: 暑熱・疲労下の未達がCFEを悪化させていた

`hotOrFatigued`ガードレール（気温28℃以上 or 脚が重い2連続）は、好走方向
（`delta < 0`＝CFE改善）だけを止めており、未達方向（`delta > 0`＝CFE悪化）は
素通りしていた。実行できなかったこと（暑さ・寝不足・設定が高すぎた）は能力
低下ではないので設定だけを動かしてCFEは触らない、という本ファイル冒頭の原則に
反する——暑熱下の好走は「実力ではなく環境」として無視するのに、暑熱下の不振は
「実力低下」としてそのまま反映していた、非対称な扱いだった。

**修正**: ガードレールの条件を`delta < 0`から`delta !== 0`に変更。どちらの方向
でも反映しない。ガードレールノートのメッセージは方向ごとに分けて出す
（何が起きたか黙って握りつぶさない）。

**検証**: 同じ未達結果に対し、気温28℃・脚が重い2連続のどちらでも
`applied: false / deltaSec: 0`になることを確認（`tests/cfe.test.ts`）。
修正前の挙動（悪化方向は反映する）を検証するテストが元々あったため、それを
新しい仕様に合わせて更新し、T-4で退行を検出できることを確認済み。

### 見つかったバグ3: Coverage画面だけ「ロングラン」の基準が違っていた

`trainingClassification.ts`の`isLongRun`（正式な判定。距離12km以上 **または**
時間60分以上）と、`coverage.ts`（Q-2 足りていないカテゴリの提案）が独自に持って
いた`isLongRun`（距離12km以上 **のみ**。時間を見ない）とで基準がずれていた。
「解釈は1か所に集める」という原則に対する違反で、同じセッションが画面によって
「ロングラン」だったり「普通のジョグ」だったりする状態だった。

具体的には、距離は短いが60分を超えるジョグ（例: 5km・65分）が、Coverage画面の
置き換え候補ロジックでは「普通のジョグ」として、有酸素の土台を失う代償の警告
無しに入れ替え候補へ出ていた。

**修正**: `coverage.ts`が`trainingClassification.ts`の正式な`isLongRun`を
呼ぶように変更。「他に候補が無いときは週内で最も長いジョグを土台とみなす」
というCoverage画面固有の追加基準（意図的な設計）はOR条件として残した。

**検証**: 5km・65分（時間基準でロングラン）と15km（距離基準でロングラン）の
2枠を候補に含めたとき、両方に「ロングランが無くなります」の代償注記が付くことを
確認（`tests/coverage.test.ts`）。修正を外すと65分ジョグが無警告の候補になり
テストが赤くなることをT-4で確認済み。

### 指摘したが今回直していないこと

いずれも「どちらが正しいか」に競技的な判断が要る、または挙動を変えると本人の
実際のプランに影響する変更のため、監査の範囲（バグ修正）を超えると判断し、
コードは変えず記録だけ残す。

- **`diagnose()`と`assessLimiter()`が同じ3つのPBから逆方向の結論を出す**:
  `diagnosis.ts`の選手タイプ判定（セッション"形式"選択に使う）と`limiter.ts`の
  制限因子判定（カテゴリ"配分"の重み付けに使う）は、同じ400m/800m/1500mの
  PBから別々の計算式で判定している。実際のユーザー（400m 49.0 / 800m 109.51 /
  1500m 3:56）で計算すると、`diagnose()`は`primaryGap: "前半経済性"`
  （前半の経済性が課題）、`assessLimiter()`は`limiter: "endurance"`
  （後半の維持が課題）と、**レースの前半と後半で逆の結論**になる。両方とも
  同時にプラン生成へ効いている（`service.ts`の該当箇所参照）ため、生成される
  プランのセッション形式選択とカテゴリ配分が、内部的に矛盾した前提で動いている
  可能性がある。どちらの計算式を正とするか、または統合するかは競技的な判断が
  必要なため、次回の課題として残す。
- **故障ログの安全接続（2026-08-04修正）**: 部位ごとの最新記録を見て、
  `ongoing`は回復記録まで、追記のない`onset`は14日間だけ安全側に扱う。
  継続中の故障がある場合、自動生成の高負荷枠は理由付き回復ジョグへ変更する。
  手動・固定の高負荷予定は勝手に消さず、RULE-23で対象日・メニューを警告する。
  14日は治癒期間の断定ではなく、追跡記録が無い`onset`を永久制限にしない運用境界。
- **`readiness.ts`の回復間隔判定とRULE-03の基準が食い違う**: `readiness.ts`は
  高負荷練習の中1日（2日間隔）を-5点の減点対象にしているが、`RULE-03`
  （`rules.ts`）は2日以上の間隔を違反なしとして扱う。同じ「中1日」の状況で、
  readinessスコアは下がるのに`/warnings`には何も出ない、という食い違いが
  起きうる。閾値をどちらかに合わせるかは判断が必要なため記録のみ。
- **テーパー期の判定が2箇所に別実装である**: `periodization.ts`のプラン生成
  ループ内のインライン処理と、`taper.ts`の`planTaper`（生成済み・手動セッション
  のレビュー用）が、それぞれ別にテーパー境界（t14/t10/t7/t3など）を持っている。
  現状の値は整合しているが、片方だけ直すとズレる構造上のリスクとして記録。
- **LTの信頼度が結果0件→1件で"low"から"medium"へ一気に上がる**: 1件のラベル
  付きサンプルと2件の無ラベルサンプルが同じ信頼度になる粒度の粗さ。実害は
  小さいと判断し、今回は直さない。

### 調査して「問題なし」と確認できたこと

- **XSS**: `dangerouslySetInnerHTML`・`innerHTML`・`eval`・`new Function`・

- **バックアップ・書き出し**: `exportBackup()`はStoreのgetterのみから構築されて

- **ログ**: `src/lib/`・`app/`のどこにも`console.error`/`console.log`/`console.warn`

  保存・テストボタンは処理中`disabled`になり二重送信を防ぐ。
- **OAuth redirectTo**: `location.origin`/`location.pathname`からのみ組み立てて
  おり、クエリパラメータ等のユーザー入力からは作らない。実効的な許可境界は
  Supabase側のRedirect URL許可リスト（README「S-11」手順で設定）。
- **ファイル取込**: ZIPを解凍するコードはリポジトリに存在しない（Apple Health
  はexport.xmlを直接読む方式のため、ZIP bomb・パストラバーサル・シンボリック
  リンクの類はそもそも対象外）。Apple Health XMLは正規表現でパースしており
  DOMパーサ不使用のためXML外部実体参照（XXE）の対象にならない（既存のP0監査
  対象7で確認済み・今回再確認）。FIT（5MB）・バックアップJSON（50MB）・
  Health XML（500MB）はいずれも`File.size`の時点で上限を確認してから読み込む。

### 指摘したが今回直していないこと

- **バックアップJSONの深いネストによるスタックオーバーフローの理論的余地**:
  50MBの上限内でも、極端に深くネストしたJSON（`[[[[...]]]]`等）は`JSON.parse`
  でスタックオーバーフローしうる。単一利用者がローカルの自分のファイルでしか
  発生させられず、起きても該当タブが落ちるだけ（他者への影響・データ漏洩は
  無い）ため、深さ制限パーサの追加は見送った。
- **Supabase access/refresh tokenのlocalStorage平文保存**: Supabaseの
  implicit flow（PKCE不使用）を採用している設計上の帰結で、既存文書
  （「S-11」節）に記載済み。GitHub Pagesは他者が書き込めるオリジンではない
  ため、悪意あるブラウザ拡張か将来のXSSが無い限り現実的な脅威にはならない。
  PKCEへの移行やサーバー側セッション管理の導入は設計変更にあたるため、
  今回のバグ修正の範囲を超えると判断した。
- **Supabaseトークンのブラウザ保存**: 静的PWAだけでOAuthを完結するため、
  access/refresh tokenは引き続きブラウザストレージに置く。HttpOnly Cookie化には
  常設バックエンドが必要。XSS面を狭めるためPWAのCSPとNext.jsのCSP・基本
  セキュリティヘッダーを追加したが、ブラウザ拡張まで防げるものではない。

## 設計上の重要な仕様

- **ペースはすべて内部で秒として保持**し、表示時に整形します。
- **有酸素系の設定は実測（FitnessMarker）から算出**します。実測が無い間は「推定値」と明示されます。閾値走やペース走の結果を入力すると精度が上がります。
- **CFE（推定800mタイム）がすべてのペースの親**です。結果を入れるとCFEが更新され、未実施の全特異的セッションのペースが基準タイム（CFEと目標の中間・フェーズで重み変化）から自動で組み直されます。
- **下げる方向の指示は常に上げる方向に優先**します（オーバーリーチの代償 > 機会損失の代償）。
- **固定セッション（チーム練習等）はルールエンジンが動かしません**。回避不能な違反は「当日の対処案」つきで警告のみ出します。
- 疲労・赤信号・故障による質練習のスキップは**後ろ倒しせず削除**します（負債の二重化防止）。
- 「きつい練習＝良い練習」という評価軸は実装していません。経済走は「同じ設定でより楽になったか」で評価します。

### セッション準備度スコア（仕様書外の追加機能）

ダッシュボードの「今日のメニュー」に出る0〜100のスコアです。**その練習がどれだけキツいかではなく、
設定どおりの質を出せる条件が揃っているか**を表します。100点からの減点方式で、加点要素はありません
（RPEの高さや達成感を加点しない、という仕様書8の原則を崩さないため）。

減点は 疲労シグナル（黄 −10 / 赤 −45）、ACWR（1.3超 −4 / 1.5超 −10）、前回質練習からの間隔
（中1日未満 −15 / 中1日 −5）、直近3本の未達（各 −3〜−6）、暑熱（−8）、ERROR級違反（−25）。
内訳は必ず画面に表示され、ブラックボックスの数字は出しません。赤信号のときはスコアに関わらず
「質を入れない」で確定します（RULE-12・SKIP-02と判断が食い違わないようにするため）。

### LT・CV・有酸素処方の根拠

- `FitnessMarker.purpose`で閾値走、テンポ、CV、レース、ロング、イージー、回復、不明を区別する。
  旧データは任意フィールドのまま読み込める。手入力の旧マーカーは低信頼度で互換採用するが、
  `past-fm-*` / `ah-*` の用途不明な自動取込はLTへ採用しない。
- LTは直近8週、半減期14日、3本以上なら中央値±25秒/kmの外れ値除外という既存方式を維持する。
  実測本数と用途の明示数から低・中・高の信頼度を返す。
- CVは直近8週に異なる3000〜5000mのレース/テストが2距離以上ある場合、
  距離-時間直線の傾きから算出する。LT以上に遅い、またはLTより20秒/km超速い結果は
  条件差・入力違いの可能性があるため採用せず、従来のLT−6〜8秒/kmへ戻す。
  20秒は理想差の断定ではなく、異常値を黙って処方へ流さない監査境界。
- 異なる2距離が無くても、CVとして正式保存した直近8週の完遂結果（RPE 8以下、
  暑熱・中止・翌日の重い脚なし、高速区間2400m以上）は、次回の**処方ペース**へ使う。
  これは生理学的CVの断定ではなく、本人が実際に成立させた設定の再利用。LTより遅い、
  またはLTより20秒/km超速い値は採らない。2400mは能力判定の理想量ではなく、
  短い刺激1本をCV根拠へ誤採用しないための入力品質境界。
- CVの初期候補は1000m・800m・600m形式を隔週で決定的に循環し、実施履歴が入った後は
  完遂・未達・RPE・回復とprogression段階を優先する。ランダム選択はしない。
- `Session.aerobicPurpose`で通常有酸素・回復・ロング・イージーを区別する。
  回復日はペースを達成目標にせず、会話可能・RPE 2〜3を優先する。

### ACWRの扱い

ACWRには実施結果、または結果詳細が無い旧`completed`だけを入れ、未実施の予定は入れない。
28日中の記録日数と信頼度を併記する。0.8 / 1.3 / 1.5は危険度や安全域ではなく、
本人の過去28日平均に対する変化を説明する表示境界である。

ACWR単独でプランを軽くしない。1.3超に加え、直近の黄/赤信号、疲労4以上、睡眠2以下、
未達・中止・翌日の重い脚のいずれかがある場合だけ、生成の漸進を止める。

### 高乳酸間隔と個人補正

標準間隔は5日のまま。従来の「モデリング期なら3日間隔を自動許可」は使わない。
4日は両方が高速区間900m以下・完全回復・低リスクで、前回が完遂、RPE 8以下、
翌日の脚が重くなく、間の日次記録にも疲労懸念が無い場合だけWARNの個別検討候補にする。
900mは安全値ではなく、現行標準高乳酸300m×5（1500m）の60%以下を拾う運用境界。
条件が読めない場合や記録不足時は5日へフォールバックする。

同じ暦週に2回あるという理由だけのERRORは出さず、実日付の間隔で判定する。
将来の連日高負荷は従来どおりERRORだが、実施済みの両方が完遂・RPE 8以下・翌日の脚に
重さなしなら、過去の良好な実施反応を否定せずWARNの経過観察へ下げる。
週内集中も全対象で同じ良好反応が確認できた過去実績だけWARNとし、未実施予定・未達・
高RPE・重い脚・日次疲労がある場合はERRORを維持する。カテゴリ名だけで身体ダメージを
断定せず、同じ並びを次週へ自動反復もしないための区別。

設定補正は同カテゴリだけでなく同じ反復距離の直近3回を比較する。締める方向は、
全回達成・RPE 8以下・翌日の重い脚なしが揃う場合だけ。未達・中止・高RPE・重い脚は
緩める材料にし、適用した処方は`userEdited`として再生成から保護する。

### D-3「前回と同じ」の設計

直近の**同じカテゴリ**の記録を初期値として読み込みます。距離や本数が違っていても
「前回の入力値」として使う価値があるので一致条件は厳しくしていません。
代わりに事故を防ぐ仕掛けを2つ入れてあります。

1. **どのセッションから読んだかを必ず画面に出す**（例: 「07-28 高乳酸セッション の内容を読み込みました」）。
   出典が見えないまま登録されると、そのままCFEの更新に流れてしまうため。
2. **実施タイムだけは読み込まない**。本数・距離・レスト・RPEは前回の値を入れますが、
   実施タイムは「前回の結果」であって今日の結果ではないので、必ず空のままにします。

カテゴリが違うものは絶対に候補にしません（高乳酸の記録を経済走に持ってこない）。

### D-3 メニューのテンプレート保存

記録画面の「この内容をメニューとして保存」で、**自作メニュー（3-2）として登録**されます。
テンプレート専用のストアは作っていません。同じ「よく使うメニュー」を2箇所で持つと
どちらが正なのか分からなくなり、生成側がどちらを見るかも曖昧になるためです。
保存したものは「メニュー設定」から確認・一時停止・削除できます。

### 実装できなかった項目

現時点ではありません。指示書のフェーズA〜Eはすべて実装済みです。
アプリ全体としての未実装は、アカウント・クラウド保存（バックエンドが必要）、
Apple Health の自動同期（iOSネイティブアプリが必要）、チーム管理の3つです。

### 設計上の判断（指示が競合した箇所）

FORGEブランド指針は下部タブを Home / Calendar / Analysis / Settings と定義していますが、
改修指示書は 記録タブの再構成（フェーズD）を前提にしています。
両立させるため、**下部タブは ホーム / カレンダー / 記録 / 分析 の4つ**とし、
**設定はヘッダー右のアイコン**（B-1の指示）に置きました。
タブ数は4つのままで、記録への到達がメニュー階層に沈まないことを優先しています。


## 改修指示書v3（F〜I）への対応

### F-1 時間・ペースの相互補完

練習日誌には「51分 平均4:40」のように距離が書かれていない。距離を必須にすると
電卓を叩くか入力を諦めることになるので、**距離・時間・ペースのうち2つあれば
残り1つを埋める**。3つとも入力されている場合は上書きせず、3%以上ずれていれば
警告だけ出す（どれが正しいかはこちらでは判断できないため）。

時間は `51` `51:30` `1:05:00` `51分` を、ペースは `4:40` `4:40/km` `@3:50` を受け付ける。
単位なしの数値は、時間なら「分」、ペースなら「秒/km」として読む（実態に合わせた非対称）。

### F-2 一括入力の解釈規則

完全ルールベース。同じテキストを貼れば必ず同じ解釈になる。
実際の練習日誌（タブ無し・半角スペース1個区切り・実施タイムが次の行・
括弧に設定と区間ラップが混在）をそのまま通せる。

- **行の切り出し**: 先頭トークンだけを日付として切り、残りは本文として扱う。
  タブや2連スペースを列区切りに要求すると、実際の日誌は1列も切り出せない
- **継続行**: 先頭が日付でない行は前の行の続きとして結合する
  （`42 1:26 1:25` のように実施タイムだけの行がよくある）
- **予定と実績の分離**: 本文にタブ・全角空白・2連スペースがあれば後ろを「結果」とみなし、
  そちらを優先する。`ジョグ40〜50分（予定）／51分（実績）` で予定の50分が実績を
  押しのけるのを防ぐ
- **処方の除去**: `300(42)＋600(1:26)` の 300 や 600 は距離であって実施タイムではない。
  除去せずに数値を拾うと、距離と設定が実施タイムの列に紛れ込む
- **レスト記述**: `r15min` `r200jog` `R12min`。r と数字の間に空白を許してはいけない。
  許すと `R12min 41.6` の `R  41` まで飲み込み、実施タイムの1本目が消える
- **カテゴリ**: **設定タイムがあれば一意に決まる**。
  設定ペース ÷ 現在のGRP の比率で分類する
  （〜102% は高乳酸/モデリング、〜112% は経済走、それ超は CV/閾値）。
  同じ 1000m×4 でも設定が3:15/kmならCV、2:50/kmなら高乳酸になるので、
  距離だけでは決まらないが設定があれば決まる。設定が無い場合だけ人間に選ばせる
- **複合区間**: `300(42)＋600(1:26)＋600(1:26)` は本数の多い距離（600m）を代表とし、
  そのぶんだけを能力推定に使う。混在していることは画面に明示する
- **補助の分離**: `8000mペース走＋流し4本` の流しは主セッションから切り離す
- **オフ**: 休養日として記録する。能力推定には使わない
- **レースの括弧**: `1:56.0(56.0-60.0)` の括弧は区間ラップ。
  レース配分シミュレータの唯一の材料なので落とさない

読めなかったものは**空欄のまま**にし、理由を添えて人間に確定させる。
確定していない行は登録経路に乗らない。

### J 読めてしまった間違いの検出（sanity）

読めなかった行は画面に理由が出るので気づける。危ないのは**読めてしまった間違い**で、
これは何も言わずにCFEまで届く。

例: 300mの実施タイム 40.0 を 4.00 と打つ。素直に読めば800m換算は約11秒になり、
承認した瞬間にCFEが飛ぶ。CFEは全カテゴリの設定ペースの親なので、練習全体が壊れる。

`src/lib/core/sanity.ts` が登録前に検査する。error が1つでもあれば登録させない
（画面には「要確認」）、warn は登録できるが表示する（「注意」）。

- 1本のペース 0.095〜0.60秒/m の外（100mを9.5秒／10:00/km相当を超える）は error
- 持続走 2:30〜10:00/km の外、距離0.4〜60km・時間3〜360分の外は error
- 平均心拍 80〜210 の外は error（桁の打ち間違い）
- 400mPBから見て速すぎる1本（200m以上の区間で12%超）は warn
- レース記録がPBを3%以上上回る場合は warn（PB更新か入力ミスかを本人に確認させる）
- 区間ラップの合計が記録と合わない場合は warn
- **本数と実施タイムの数が合わない場合は warn**。パーサは不自然な数値を捨ててから
  渡してくるので、捨てられた事実はここでしか分からない。黙って本数が減ると、
  平均も垂れ幅も別のセッションの数字になる

「ありえないが本当」という値は中距離の練習データには無いので、迷ったら止める側に倒す。

### K 補強の取り込み

実際の日誌には「体幹」「プライオ」「ウェイト」が普通に混ざる。従来はカテゴリ未確定で
全部落ちていた。

補強は `SessionCategory` を増やさず、既存の `StrengthSession` へ流す。
`SessionCategory` はルールエンジン22本・GRP比率・転移度・負荷計算がすべて参照している型で、
ここに `strength` を足すと「補強は質練習に数えるのか」「ACWRにどう乗るのか」を
既存の全ルールで決め直すことになる。補強には接地回数など走練習とは別の規則が既にあるので、
そちらに寄せた。走練習側の経路に入れると ACWR で二重計上される。

判定語は走練習の語より**後ろ**に置いてある。`ジョグ40分＋体幹` を補強として登録すると
ジョグ40分が有酸素量から丸ごと消えるため、走った分を残す方を優先する。
`体幹30分` だけの日は走の語が無いので補強に落ちる。

接地回数（`接地120回` / `120接地`）はプライオの週間管理に使うので拾う。

### L 表記辞書

一括入力が読めない語は必ず出る。所属チーム固有の呼び方があるからで、
組み込みルールをいくら足しても追いつかない。

読めなかった行を人が直したあと、その場で「この書き方を覚えさせる」と押せば
語とカテゴリの対応が保存され、次から自動で通る。
**本人の登録は組み込みルールより優先する**（「セット走」を閾値走と呼ぶチームも
CV走と呼ぶチームもあるので、こちらが決めてはいけない）。
登録済みの語は「覚えた書き方」から確認・削除できる。

LLMは使っていない。同じテキストを貼れば必ず同じ解釈になるという性質を壊さないため。

### G 同一処方の経時比較

カテゴリ・1本の距離・本数が一致したものを同じ処方とみなす（レストは一致条件に含めず、表に併記）。

**平均タイムと垂れ幅を必ず別々に判定する。** 平均が速くなっていても垂れ幅が
広がっていれば、それは1本目を突っ込んだだけで後半維持は悪化している。
耐乳酸型の選手は1本目を速く入りやすいので、この2つを1文にまとめると判断を誤る。

### H CFEの予測レンジ

「1:51.0、信頼度0.48」と出しても、その0.48を使って判断はできない。
`1:50.2 〜 1:51.8` と幅で示す。信頼度が低いほど広く、実測どうしのばらつきが
大きいほど広くする。**表示専用**で、プラン生成や設定ペースの計算には使わない
（計算に使うと「幅のどこを採るか」という新しい恣意性が入る）。

ホームのCFE推移グラフは軸を反転しない（下がるほど良いことは「下がるほど良い」の一文と数値横の矢印で示す）。
分析タブのCFE推移（LineChart）も反転していないため、Sparkline側だけ反転すると同じデータが画面によって上下逆に見えてしまう。見え方が画面ごとに変わる害の方が大きいと判断した。

### I レース配分シミュレータ

目標タイムと**本人の過去レースの実測落ち幅**から3案を出す。
実測どおり／落ち幅を0.5秒詰める／0.5秒広げる、の3つ。

過去レースの区間ラップが2本未満のときは**案を出さない**。
一般論の配分を出しても、本人の落ち幅が分からないまま信じてレースを壊すだけになる。
代わりに「何本必要か」「どこに入れるか」だけを伝える。

## 改修指示書v4（M-1〜M-12）への対応

### M-1 練習結果の保持と上書き

記録画面は保存後も同じセグメントに留まり、入力済みの値を表示したままにする。
既に登録がある場合は初期値として読み込み、ボタンを「上書きして保存する」に変える。

**再保存は上書き。** 新しいidで積むと記録が二重に残り、負荷も達成度も二重に数えられる。
さらに CFE が同じ練習で2回動き、「1回の更新は±1.5秒まで」というガードレールが実質±3秒になる。
そのため `processResult` は既存の記録のidを引き継ぎ、
`revertCfeForSession` で前回この練習が動かしたぶんを取り消してから入れ直す。
取り消しは後続の更新の差分（after − before）を保ったまま行うので、
古い記録を直しても以降の履歴が壊れない。

### M-2 直近の状態に応じた設定の調整

**CFEと設定ペースを分ける。** CFEは「能力の推定」、設定ペースは「今日出せる値」。
実行できなかったことは能力低下とは限らない（暑かった、寝ていない、設定が高すぎた）。
どれも CFE を下げる理由にはならないので、設定だけを動かす。

判断材料は4つとも使う。

- 直近3回の同カテゴリの実行状況（設定との乖離・垂れ幅・打ち切りの有無）
- その日のコンディション（睡眠・疲労・安静時心拍）
- ジョグの心拍。同じペース帯（中央値±20秒/km）で平均心拍が +4bpm 以上なら疲労とみなす。
  ジョグを「消化した記録」ではなく「状態の測定値」として扱う
- ポイント練習の心拍（Q-1）。同じ距離で、直近2本の平均心拍が
  それ以前より +4bpm 以上なら疲労とみなす。こなせてはいても状態は落ちている、を拾う

閾値と上限（`src/lib/core/adaptive.ts`）:

- 直近3回の平均乖離が **+2.0秒/本** を超えたら緩める
- 緩める上限は **3%**、締める上限は **1.5%**。
  締める側を保守的にしているのは、速く走れた事実は能力の主張だから
- その日の状態による調整は最大 **2%**
- 黄信号は既存ルールに合わせ、強度を維持したまま量を30%減らす
- 暑熱フラグの付いた実測は判断材料から外す（環境要因は M-9 が別に扱う）

提案は保存しない。何をどれだけ動かしたかを出して、本人が適用するか辞退するかを決める。
辞退は記録され、同じ提案を出し直さない。

#### S-10 画面で何を言うか

「設定の調整案」と見出しを出して増減の秒数だけ並べても、**何をどうしたいのかが伝わらない**。
差分を読ませるのではなく、次の3つを順に出す。

1. どちらに動かすのか（見出しで言い切る。「今日の設定を ゆるめる提案」）
2. **変更前と変更後の処方を、文面そのままで並べる**（`beforePrescription` / `afterPrescription`）
3. そう判断した材料（`reasons`）と、**CFEには触れないこと**

3つ目は必ず書く。設定とCFEの混同はこのアプリで最も起きやすい誤解で、
「暑かった・寝ていない・設定が高すぎた」はどれも能力が落ちた理由にならない。

ポイント練習の日以外は、その日の枠ではなく**次のポイント練習**の案を出す。
今日の枠に固定していたため、ジョグの日には調整案が一切見えていなかった。
ジョグと休養には設定が無いので、固定しても出るものが無い。

#### Q-1 ポイント練習の心拍の扱い

1本ごとの平均心拍（`RepResult.avgHr`）は**任意項目**。時計から拾える人だけが入れるので、
無いほうが普通という前提で扱う。無くても比較もM-2も今までどおり動く。

- 記録画面では既定で欄を出さない。常時2欄にすると1行に6欄並び、
  iPhone幅（390px）で実施タイムの欄まで潰れる。出すときは3列→2列に落として幅を確保する
  （E2Eが最小幅を実測している）。
- 心拍と「何本目か」の対応は、実施タイムを間引く**前**に取る。
  先に間引くと、途中の本が空のときに心拍が1本ずつずれる。
- **心拍が上がっていても、タイムが 0.3秒/本 以上速くなっていれば疲労とみなさない。**
  速く走れば心拍は上がる。上がったこと自体を悪い材料にすると、
  速く走ったのに疲労と判定されることになる。
- 判定のしきい値は用途で分ける。M-2の疲労判定は **4bpm**、
  同一処方の比較で「傾向あり」とみなすのは **3bpm**。
  比較側が緩いのは、そちらは表示だけで設定を動かさないため。
- 一括入力のパーサには読ませていない。日誌に1本ごとの心拍が書かれることは稀で、
  読める書き方を増やす代償のほうが大きい。

#### R-1 心拍が実際に何に効いているか

**心拍は補助。無くても全機能が動く。** 心拍が無いことを理由に何かを止めたり、
値を推測で埋めたりしない。判定できないものは判定できないと出す。

| 心拍 | 使っている場所 |
| --- | --- |
| ジョグの平均心拍 | `jogEfficiency`（M-2の材料） |
| 1本ごとの平均心拍 | `qualityHrTrend`（M-2）／同一処方の比較の `hrTrend` |
| 暑熱ブロックの心拍 | 順化判定（同一ペースでのHR低下） |
| 最大心拍 | 相対強度の基準（`hrMaxReference`） |
| 心拍の差 | 暑熱の切り分け（`heatHrEvidence`） |

`src/lib/core/heartRate.ts` に置いた判断:

- **最大心拍を年齢の式（220−年齢など）から推定しない。** 個人差が±10拍以上あり、
  推定を基準にすると強度の判定がその誤差ぶん動く。本人が入れた実測値が無ければ
  記録の中の最高値を使い、**それが実測の最高値であること**（本当の最大とは限らない）を明示する。
  どちらも無ければ相対強度を出さない。
- **1本が2分未満の練習では、心拍から強度を判定しない。**
  心拍が定常に達するまで1.5〜2分かかる。300mを42秒で走る練習の平均心拍は
  実際の負荷よりはっきり低く出るので、そのまま読むと「強度が足りていない」と誤読する。
  短い練習の心拍は、同じ設定どうしの比較（`qualityHrTrend`）にだけ使う。
  高乳酸・モデリング・神経系はこの理由で強度帯を持たせていない。
- 暑熱の切り分けは、**同じ設定・同じかそれより遅いペースで心拍が5bpm以上高い**ときだけ
  環境要因の裏づけとして扱う。心拍が変わらなければ「暑さのせいだと言い切る材料は無い」と書く。
  速く走ったことによる上昇は裏づけにしない。

「使われているか」は分析タブの「現在地 → 心拍の使われ方」で実際の記録に対して出している。
保存されているだけで誰も読んでいない項目を作らないための枠でもある。

### M-3 中止基準

処方に必ず打ち切り条件を付ける。

- 高乳酸・モデリング: 許容 +2.0秒、**1本でも**超えたら打ち切り
- それ以外: 許容は設定の1.5%（最低2.0秒）、**2本連続**で超えたら打ち切り

打ち切りは失敗ではない。`SessionResult.aborted` を立て、
CFE の SKIP-06（中断を未達として反映）を**適用しない**。
「2本連続で超えたら止めろ」と指示しておいて、止めたことを未達として響かせるのは筋が通らない。
打ち切りは設定側（M-2）が受け取り、2回続けば設定が高すぎると判断する。

予定した距離の途中で止めた本も捨てない。たとえば `500m×3` の最終本を400mで
止めた場合は、`RepResult.distanceM=400` と実測タイムを保存し、元の予定500mと設定は
`plannedDistanceM` / `plannedTargetSec` に残す。比較・週次レビュー・次回補正では
予定距離相当へ比例換算し、400mの56秒を500mの56秒として扱わない。
FIT等の丸めで中断扱いにならないよう、予定との差が0.5m未満なら同距離とみなす。
これは競技上の許容幅ではなく、保存値のサブメートル誤差を吸収する境界である。

根拠: 設定から大きく外れた本数を消化しても狙った代謝刺激は入らず、疲労だけが残る。
耐乳酸型は1本目を突っ込んで後半が垂れやすく、垂れた状態の消化は糖枯渇練習に変わる。

### M-4 セッション中の入力

`/run?sessionId=...`。1本入れるごとに続行か中止かを返す。
画面に出すのは3つだけ（直近の1本・設定との差・続行か中止か）。
レストの間に読める情報量には限りがある。

入力途中は kv に保存するので、画面を閉じても消えない。
終了時にそのまま `SessionResult` になり、二度打ちにならない。
走行中は誤タップの元になるので FAB を出さない。

### M-5 予定の編集・移動

カレンダーの操作は3つ。

- **日付の行をタップ** → その日の記録画面へ（行全体がリンク）
- **✎** → 編集シート（内容・設定タイム・所要時間・移動・削除）。セッションの長押しでも開く
- **＋** → その日に練習を足す（同じ日に午前・午後の2本を残すときにも使う）

長押しだけにしていない理由: iOSの長押しは取りこぼすことがあり、
リンク上ではプレビューが割り込む。押せる場所を用意しておく。
編集・追加のシートは日付リストの**上**に出し、開くときに画面上部までスクロールする。
日付が何十行も並ぶ画面なので、下に出すと画面外に出てしまい「押しても何も起きない」ように見える。

**確定前に必ずルール検査を通す。** セッションを差し替えた状態でルールエンジンを走らせ、
必ず元に戻してから結果だけを返す。新しく ERROR が出る変更は既定で適用せず、
何が壊れるかと、前後7日で置ける日（最大3件）を出す。
本人が選べば強行できるが、強行したことを変更履歴に残す。

プラン全体は作り直さない。作り直すと手で直した内容が消える。

### M-6 レース前の変則調整（テーパー）

原則は「量を落として強度は維持」。強度まで落とすとレースペース感覚と神経系の出力が落ちる。

| 段階 | 内容 | 週の総量 |
| --- | --- | --- |
| 14日前〜 | 高乳酸の本数を減らす（設定は変えない） | 100% |
| 10日前〜 | ジョグの量を落とす | 80% |
| 7日前〜 | 高乳酸を外す（回復が間に合わない） | 65% |
| 3日前〜 | 刺激のみ | 40% |
| 前日 | 流しと動き作り | 20% |

固定セッション（チーム練習）は動かさない。動かせない前提で他を削る。
調整は差分として出し、適用するまで予定は変わらない。辞退もできる。

**M-2との干渉を切ってある。** テーパー期は「直近の出来が悪いから落とす」のではなく
「意図的に落とす」期間なので、両方を掛けると二重に落ちる。
テーパー期は M-2 の量の調整を止め、設定ペースの調整（実行可能性の担保）だけを残す。

### M-7 制限因子の自動判定

400mPBと1500mPBで800mの現在地を両側から挟む。

- 400m側の妥当域 = 400mPB×2 + 9〜12秒
- 1500m側の妥当域 = (1500mPB − 15〜20秒) ÷ 2

遅れが大きい側が「使い切れていない資源」。差が0.5秒を超えたところで判定する
（1秒にすると両側1秒以内の選手が全員「バランス」になり、判定が働かない）。

伊藤選手（400m 49.0 / 1500m 3:56 / 800m 1:49.51）:
400m側の中央1:48.5に対して1.0秒遅く、1500m側の中央1:49.25に対して0.26秒遅い。
→ **制限しているのは後半の維持**。
目標1:48.90に必要な換算差は10.9秒で標準（9〜12秒）の範囲内なので、
400mを速くする必要はない。

判定は表示だけでなく**生成の配分に反映する**。重み1未満のカテゴリの枠を、
重みが最大のカテゴリに振り替える（維持が制限なら CV → 経済走）。
振り替えた日付・元・先は `limiterSwaps` として返し、必ず本人に見せる。

#### Q-2 足りていないカテゴリの提案

ルールエンジンは「多すぎる・詰まりすぎ」だけを見ていて、
**「足りていない」側は誰も見ていなかった**（RULE-16 の ACWR 低下は総負荷の話で、
カテゴリの偏りは検出しない）。固定曜日設定を使っていると、その枠に収まる範囲でしか
メニューが出ないため、4週まとめて見ると特定のカテゴリが薄いまま進む。

`src/lib/core/trainingBalance.ts` が月曜始まりの現在週と直前3週を共通集計し、
`coverage.ts` がカテゴリ不足の提案と組み合わせる。

- 予定距離/予定負荷と、結果から得た実施距離/実施負荷を別々に持つ。
- 週ごとの高負荷日、高乳酸・解糖系、中距離特異的、有酸素高強度、ロング走、
  完全休養・回復、実施率、変更/中止/期限超過を表示する。
- 実施4件未満では傾向を断定せず、「記録不足」と次の行動だけを出す。
- 前週比急増、高負荷3週連続、高乳酸の直近10日集中、回復不足、実施率低下を
  根拠の件数・日付と一緒に出す。
- 保存カテゴリは変更せず、警告/集計用に
  `高乳酸・解糖系 / 中距離特異的 / 有酸素高強度 / 神経・スプリント /
  低〜中強度有酸素 / 回復 / 筋力・補強` へ写像する。

- **基準の回数は別表で持たない。** 生成器の週テンプレート
  （`categoryCountsPerFourWeeks`）をそのまま4週ぶん数える。
  別表にすると、生成の中身を変えたときに提案の基準だけが古くなる。
- 制限因子（M-7）の重みを掛ける。維持が制限なら経済走の基準が ×1.3 になる。
- **不足2回から提案する。** 1回の差は週テンプレートの巡り合わせで普通に出るので、
  毎週なにか言われる状態になり、提案そのものが読み飛ばされる。
- 数える対象は**実施したものだけ**。過去日に予定のまま残っているものは数えない
  （あるつもりで足りない、を防ぐ）。過去データ入力ぶんは**含める**
  （実際にやった配分を見たいので、入力経路で回数が変わってはいけない）。
- 置き換え候補はジョグの枠から選ぶ。ポイント練習を別のポイント練習に替えると、
  減らした側が今度は足りなくなる。
- **ロングランは他に候補が無いときだけ出し、代償を必ず文章にする。**
  有酸素の土台は数週間かけて落ちるので、連続で潰すと別の問題が出る。
- 固定曜日設定そのものは書き換えない。動かすのはその週の予定1件だけ。
  適用するかは本人が選ぶ（M-2 / M-6 と同じ作法）。
- 置き場所はホームではなく分析タブの「現在地」。4週の振り返りは「今日やること」ではないので、
  ホームの原則を崩さない。

#### S-12 何の画面かを先に書く

表と不足回数だけでは、**何を見て何をすればいいのか分からない**。順番を変えた。

1. 何のための画面か（固定曜日の枠に収まる範囲でしか出ないので、薄いまま進む種類がある）
2. **おすすめを1つだけ**（「経済走を あと3回 増やす」）。表を読んでから考えさせない
3. 内訳の表（「やった / 目安 / 不足」。「実施 / 基準 / 差」から言い換え）
4. 入れ替え候補

**M-2（今日の設定）との違いを画面に書く。** 「今の状況に応じた強度」という同じ言葉で
両方を指せてしまうので、こちらは1か月の組み立ての話だと明記する。

カレンダーにも1行だけ出す（`CoverageStrip`）。予定を組み替えるのはカレンダーなので、
そこで気づけないと意味が無い。内訳と入れ替えは分析タブに任せ、
カレンダーには結論1行と導線だけ置く（表まで置くと日付が画面から押し出される）。

### M-8 600m通過を主指標にする

目標1:48.90の基準線: 400m通過 54.5 ／ 600m通過 1:21.5 ／ 残り200m 27.4。

材料は800mレースの区間ラップ、600m単発、300+500のような分割走。
200m刻みのラップがあれば通過はそのまま足す。400+400しかない場合は
後半400の48%で按分し、**推定であることを画面に出す**（単純な半分では速く出る）。

材料が2本未満のときは指標を出さない。1本しかないものを線にすると、
たまたまの1本が現在地に見える。

### M-9 WBGTから設定を自動で緩める

WBGT区分ごとの基礎補正（注意1% / 警戒2% / 厳重警戒3.5% / 中止5%）に、
暑熱耐性の係数（low ×1.5 / high ×0.7）を掛ける。

補正は**表示上の設定にだけ**掛かる。実測をCFEに戻すときは `normalizeForHeat` で差し引く。
これをやらないと夏場の実測がすべて「能力低下」として記録される。
WBGTも気温・湿度も無ければ補正しない（推測で埋めない）。
有酸素系は設定をCFEから作っていないので対象外。

### M-10 接地時間の疲労指標化

同じペース帯（中央値±20秒/km）で、基準（8日以上前の中央値）から
**+5%以上**の状態が3日続いたら疲労として出す。
主観や安静時心拍より早く出ることがあるので、故障の予兆としても使う。
CSVは列名を見ず「日付, 接地時間(ms), ペース」の位置で読む（時計ごとに列名が違うため）。
データが無ければ何も出さない。

### M-11 週次レビューの自動生成

定型文の組み合わせで作る。LLMは使わない。同じ週の同じデータからは必ず同じ文章が出る。

数字は必ず実測を引用する（「調子が良かった」ではなく
「設定41.5秒に対して平均42.0秒、垂れ幅+1.0秒」）。
平均と垂れ幅は別々に評価する（平均が設定どおりでも垂れているなら入りが速すぎる）。
打ち切りは「中止基準にしたがって止めたもので、失敗ではありません」と書く。

### M-12 データの書き出しと復元

全データをJSON1ファイルに書き出す。復元は「上書き」と「統合」を選べる。
統合はidで突き合わせ（日次コンディションは日付で）、重複を作らない。
14日以上書き出していなければホームで促す。

iPhoneのPWAはストレージが消えることがあり、
数か月ぶんの実測が消えると現在地の推定が全部やり直しになる。
派手さは無いが、失ったときの損失は他のどの機能より大きい。

### v4 で足した保存先

単独のテーブルを立てるほどの構造を持たないものは kv（キー・バリュー）に置く。
セッション途中の入力、辞退した提案、接地時間、最後に書き出した日時。
検索キーが要るものはここに置かない。

### 対象1: PWAの保存保証

以前は `persistState`（`pwa/memory-store.ts`）が `void` を返し、IndexedDBと
localStorageの両方が失敗しても呼び出し側に何も伝わらなかった。画面は
「保存した」つもりのまま、実際は端末に何も残っていないことがありえた。

`persistState` を `Promise<PersistOutcome>` にし、失敗理由（`quota` /
`unavailable` / `unknown`）まで返すようにした。IndexedDBアクセスは
`StateIndexedDb` として注入可能にしてある——IndexedDB自体がテスト環境
（Node/vitest）に存在しないため、`supabase.ts` の `fetchImpl` と同じ形で
「成功」「失敗」を明示的に表現したフェイクを注入し、実際の分岐を検証できる
ようにするため（新しいテスト用ライブラリは入れていない）。

両方失敗した場合は `pwa/entry.tsx` の `PersistFailureBanner` が画面上部に
文言で表示する（色だけに頼らない。`role="alert"` / `aria-live="assertive"`）。

`pagehide` と `visibilitychange`（`hidden`）で `flushPendingState()` を呼び、
250msのデバウンス待ちでアプリ終了直前の更新が失われないようにした。

### 対象2: 安全なバックアップ復元

以前は `isBackupFile` が `format`・`version`・`data` の存在しか見ておらず、
`replace` モードは検証前に `resetAll()` していた。壊れたバックアップで
「全消去してから壊れたデータで復元を試みる」＝データ消失になりえた。

`validateBackup`（`src/lib/core/backup.ts`）を追加し、各コレクションが配列
であること・idキーの型が正しいことを、`resetAll()` より前に確認する。
距離・時間などドメインの値そのものは検証しない——読めなかった値を推測で
埋めないのと同じ理由で、過剰に断定的な検証をすると、将来フィールドが
増えた正常なバックアップまで拒否しかねないため。

さらに実際の書き込み（`resetAll()` を含む）を `Store.transaction()` で包み、
検証をすり抜けた想定外のデータで途中失敗しても、開始前の状態へ完全に戻す。
SQLite（`Repo`）は実際の `BEGIN`/`COMMIT`/`ROLLBACK`（3つの実体すべてが
`exec()` で同じ生SQLに対応するため、新しい抽象を足していない）。IndexedDB
（`MemoryStore`）はJSが単一スレッドであることを利用し、実行前の状態を
スナップショットしておいて例外時に差し戻す方式にした（差し戻し後に
`touch()` を呼び直さないと、差し戻し前の状態を指したままの永続化予約が
そのままIndexedDBへ書き込まれてしまう点に注意）。

実際に確認した効果: `validateBackup` を外した状態で壊れたセッション
（`id` が数値）を復元させると、**IndexedDB側は例外すら出さず、配列へ
そのままpushしてしまう**（配列pushには型チェックが無いため）。検証を
`resetAll()` より前に置くことが、単なる「順序の好み」ではなく、
IndexedDB経路では唯一の防御であることを確認した。

## 改修指示書v5（N-1〜N-3）への対応

### N-1 1文字打つたびにキーボードが消える

`ResultForm` の中でラベル用のコンポーネント `L` を定義していた。

```
function ResultForm(...) {
  const L = ({ label, children }) => (<label>...{children}</label>);   // ← これ
  return (... <L label="RPE"><input .../></L> ...);
}
```

`L` は再描画のたびに別の関数になるので、Reactは「別の種類の要素」とみなして
中身の `<input>` を作り直す。作り直された入力欄はフォーカスを失い、iOSではキーボードが閉じる。
1文字ごとに再描画が走るので、1文字ごとに閉じる。19か所で使っていたため、
練習結果のほぼ全部の欄が該当した。`L` をモジュール直下に出して解決。

**この不具合は画面に何も出ない。** 見た目は正常なので、実機で打ってみるまで気づけない。
そのためE2Eで「1文字ずつ打ってフォーカスが保たれること」を機械的に見張っている。
壊れた状態に戻して、この検証が実際に落ちることも確認済み。

なお `app/setup/page.tsx` の `F` は `{F("名前", "name")}` という**呼び出し**で、
要素の種類が変わらないため同じ問題は起きない。
判定基準は「コンポーネントの中で定義した関数を `<X>` としてJSXで使っていないか」。

### N-3 メニュー本文からカテゴリを判定する

`src/lib/core/prescription.ts` の `parsePrescription`。

**中身は一括入力の `parseRow` に日付を足して渡しているだけ。** 独自に読み直さない。
同じ「300(42)×5 r5min」が一括入力では高乳酸、編集シートでは別の何か、
ということが起きると、どちらの数字を信じればいいのか分からなくなる。
表記辞書も同じものを通す。

判定は断定しない。根拠（「設定 42.0秒/300m はGRPの98%」「表記辞書「セット走」」）を出し、
その場で直せるようにする。設定タイムが書かれていなければカテゴリは一意に決まらないので選ばせる。
保存前に M-5 のルール検査を通すので、カテゴリが変わって高乳酸の間隔に触れれば止まる。

**`@設定` 表記に対応した。** このアプリが生成する処方は
`300m × 5 @40.9〜41.7秒 r5分` と書くので、これを読めないと
自分が出したメニューを自分で「カテゴリ未確定」と判定することになる。
ただし距離×本数が書かれているときだけ設定として扱う。
ジョグの `@5:00〜5:20/km` を1本の設定と読むと種別を取り違えるため。

### N-2 本文に合わせて入力欄を組み立てる

読み取った構造に沿って入力欄そのものを組み替える。
編集シートは1本ごとの**設定タイム**（`300(42)+600(1:26)+600(1:26)` のように
区間ごとに設定が違うメニューがあるので、1つの設定欄では表せない）、
記録画面は1本ごとの**実施タイム**（貼り付け用に、まとめて入れる方式も残して切り替えられる）。

**入力中に欄を作り直さないこと。** 素直に実装すると N-1 と同じ不具合を自分で作る。

- 解釈は入力が止まってから走らせる（300ms のデバウンス）
- 欄の作り直しは `shape`（種別・距離・本数の指紋）が変わったときだけ。
  設定タイムは `shape` に含めない。設定だけ直したときに欄を作り直すと入力中の値が消える
- 本数が増えたら空欄を足すだけ。減っても値は捨てない（`resizeValues`）。
  打ち間違いで一時的に「×3」になったときに4・5本目を消すと、入れ直しになる
- 入力欄の `key` は「何本目か」で固定する。本文や解釈結果を key に使わない
- 本数の上限は30。打ち間違いで「×99」と入っても欄を99個作らない
- 読み取れない本文では欄を変えない。空にもしない

記録画面の欄の数は「処方の本数」「入力した本数」「既に入れた値の数」の最大を採る。
処方が3本でも実際に5本やったなら5本ぶん入れられる必要がある。

#### S-2 距離・時間・平均ペースは2つで足りる

3つのうち2つ入れれば残り1つは決まる。計算は一括入力と同じ `completeRunTriple` を使う
（同じ数字の関係を2か所で実装しない）。以前は「距離＋時間 → ペース」の向きしか無く、
時計で平均ペースを見た人は距離を自分で割る必要があった。

3つとも入っていて食い違うときは、**どれが正しいかを決めずに知らせるだけ**にする。
勝手に上書きすると、どれが実測でどれが計算かが分からなくなる。

`paceOverridden` を立てるのは、距離と時間が揃っているうえで手入力のペースを採ったときだけ。
ペースから距離を出した場合、そのペースは上書きではなく実測そのもの。

#### S-4 レストは本ごとに違うことがある

`IntervalDetail` のレストはセッションに1つしか持てないが、
`300+600+300` のような複合セッションでは区間ごとにレストが違う（300のあと6分、600のあと10分）。
`RepResult.restAfterSec` に**その本のあとの**レストを持たせた。任意項目で、
全部同じなら入れなくてよい。表示は `perRepRestNote` が違うときだけ並べる。

`400(56)+300(42)+200(24) r次の距離walk` は3本の別区間として扱い、設定を
56秒・42秒・24秒、区間後の距離レストを300m walk・200m walkとして展開する。
距離レストは既存の`RepResult.restAfterDistanceM`へ保存するためmigrationは不要。
結果保存後に実際のカテゴリを直した場合は`Session.category`を同じ保存処理で更新し、
CFE・負荷・4週間集計・警告・次回処方を新しい分類から再計算する。

心拍と同じく、**実施タイムを間引く前に「何本目か」で対応させる**。
先に間引くと、途中の本が空のときにレストが1本ずつずれる。

入力欄は既定では出さない。3欄（タイム・心拍・レスト）を横に並べると
iPhone幅で潰れるので、**3欄になったら1本1行に落とす**（E2Eが最小幅を実測。105px）。

#### S-3 メニューの入力方法を1つにする

自作メニューの登録だけ本文のテキスト1つで、1本の距離を手で入れ直す作りだった。
記録画面・編集シート・追加シートと同じ `PrescriptionFields` を使うようにして、
**本文を打てば欄が組み上がり、距離・本数・レストは解釈から取る**。
同じ「メニューを打ち込む」操作が画面によって違う手数になるのをやめた。

**編集シート・追加シート・ホームのTODAYは実装を共有する。**
本文に合わせた入力欄は `app/components/prescription-fields.tsx`、
メニューの変更シートそのものは `app/components/session-edit-sheet.tsx` が唯一の実装。
画面の外枠（ヘッダー・タブバー・FAB・下端の余白）は `app/components/app-shell.tsx` で、
Next.js の `layout.tsx` と PWA の `entry.tsx` の両方がこれを使う。
以前は枠を2か所に書いていたので、片方だけ直しても片方の実行環境では直らなかった。

同じ組み替え規則を2か所に書くと、片方だけ直したときに同じ本文が画面によって違う欄になり、
どちらの数字を信じればいいのか分からなくなる（解釈を `parseRow` の1か所に集めているのと同じ理由）。
共有できていることはE2Eで確認している。組み替え規則を1つ壊すと両方の画面のE2Eが同時に落ちる。

### P-4 下端の余白（タブバー・FABに隠れない）

下部タブバーとFABは `position: fixed` なので、スクロール領域が自分でそのぶんの
余白を持たないと、最下部の要素が裏に入る。**スクロールしきったように見えるので気づけない。**

余白は `--main-bottom-pad`（globals.css）で1回だけ計算し、`app-shell.tsx` の `main` が
それだけを見る。画面ごとに padding を足して回ると、足し忘れた画面だけ隠れる。
内訳はタブバーの高さ（セーフエリア＋55px）＋FABの逃げ（78px）。
**セーフエリアを定数で見込まないこと。** iPhoneでは34px あるので、
「だいたい96px」と置くと実機だけ足りなくなる。

`calc()` をユーティリティ側（`pb-[calc(...)]`）に直接書かないこと。
Tailwind がクラスを生成しないことがあり、生成されなくても画面には出ず、
最下部が隠れるだけなので気づけない。CSS変数にしてから `pb-[var(--main-bottom-pad)]` と書く。

E2Eの「P-4」が全画面で最下部の要素とタブバー上端を実測して比べている。

### ConfirmDialogのアクセシビリティ

破壊的操作の前に出る`ConfirmDialog`（`app/components/ui.tsx`）に、モーダルとしての
基本的な振る舞いが無かった:

- `role="dialog"` / `aria-modal="true"` / `aria-labelledby`（タイトルとの関連付け）
- 開いた瞬間にダイアログ内へフォーカスを移す
- **Escapeキーで閉じる**（`onCancel`を呼ぶ）
- **Tabキーがダイアログの外へ抜けない**（フォーカストラップ。最後の要素でTabすると
  先頭へ、先頭でShift+Tabすると最後へ戻る）
- 閉じたときに、開く前にフォーカスがあった要素（呼び出し元のボタン等）へ戻す

`onCancel`はほとんどの呼び出し元がインライン関数で渡すため、`useEffect`の依存配列に
そのまま入れると親の再描画のたびにeffectが走り直し、開いている間もフォーカスが
先頭ボタンへ引き戻されてしまう。**最新の関数はrefで保持し、effectの依存は`open`だけ**
にした（値が変わるたびに走ってほしいのは開閉のタイミングだけで、関数の中身の
変化には反応しなくてよい）。

`ConfirmButton`はこの`ConfirmDialog`を内部で使っているため、修正は自動的に反映される。

**検証**: 単体テストの土台（jsdom・testing-library）がこのプロジェクトには無く、
既存のテスト方針が「コアロジックは単体テスト・画面はE2E」で統一されているため、
E2E（`pwa/e2e.mjs`。自作メニュー削除の確認ダイアログを流用）でrole/aria-modal・
Escape・フォーカス復帰・フォーカストラップの4点を実際のキーボード操作で確認。
T-4で以下を個別に壊し、それぞれ赤に戻ることを確認して復元:
role/aria-modal属性の削除、Tabのラップアラウンド処理の無効化。

### iOSキーボード対策（interactive-widget=resizes-content）

編集フォーム（`SessionEditSheet`・カレンダーの追加シート）を調べたところ、
保存ボタンは`position: fixed`ではなく通常のドキュメントフロー内にあり、
ネイティブのフォーカス時スクロールで対応できる作りだった——**固定位置の保存
ボタンがキーボードに隠れる、という当初想定した形の問題は無かった。**

一方、下部タブバー・FABは`position: fixed`で、iOSはキーボード表示中も
レイアウトビューポートを縮めない（`visualViewport`は縮むがレイアウトは
縮まない）ため、固定要素がキーボードの裏に取り残われる可能性がある。
`visualViewport`を監視する独自JSを書く代わりに、**標準の
`interactive-widget=resizes-content`をviewport metaに追加**した
（iOS 17.4+ / Chrome 108+。対応していないブラウザは未知のトークンとして
無視するだけなので安全）。これによりキーボード表示中はレイアウト
ビューポート自体が縮み、`position: fixed`要素も自動的にキーボードの上に
再配置される。

`pwa/index.html`と`app/layout.tsx`（Next.jsの`viewport`export。
`viewportFit: "cover"`も併せて追加——PWA版には元々あったが、Next.js側に
無かった既存の抜けだったため揃えた）の両方に追加。

**検証**: E2Eでmetaタグの内容を確認（`interactive-widget=resizes-content`
が含まれること）。**実機での最終確認は別途必要**（Chromiumはキーボードに
よるビューポート縮小を再現しないため）。

赤・amber文字で警告・エラーを示す箇所（17ファイル・85箇所）のうち、

## 実運用で見つかった5件の修正（2026-07-31）

利用者が実際に使っていて見つけた5件。着手前に各項目を実コード調査で
裏付けてから修正した（推測で直さない）。

### 1. カレンダーの✎ボタンが2件目以降のセッションに届かない

`app/calendar/page.tsx`の`DayRow`は、1日に複数セッションがあるとき
`editable = sessions.find((s) => !s.isFixed)`で**最初の1件しか**✎ボタンの
対象にしていなかった。長押しは行ごとに正しく対象を拾えていたが、iOSでは
長押しが取りこぼされることがあるとコード内に既にコメントがあり、
確実な代替導線（✎ボタン）がここだけ効かなかった。

`editableSessions = sessions.filter((s) => !s.isFixed)`に変え、非固定
セッションの数だけ✎ボタンを出す（複数あるときはカテゴリ色をボーダーに
つけて、どの行に対応するか分かるようにする）。1件のときの見た目は変わらない。

### 2. 実施タイム（カンマ区切り）欄でカンマが打てない

`app/results/page.tsx`の「実施タイム（本数分をカンマ区切り）」欄に
`inputMode="decimal"`が付いていた。JS側の文字除去処理は無く、原因は
iOS等の数値専用キーボード（カンマキーが無い）だった。この欄はカンマ区切りの
**文字列**を受け取る欄で単一の小数ではないため、`inputMode="decimal"`の
指定自体が誤りだった。属性を外して通常のテキストキーボードにした。

### 3. FIT取込でランニングダイナミクスを取得する

`src/lib/core/fitParse.ts`は心拍以外（ピッチ・ストライド・上下動・
接地時間・気温）を一切読んでいなかった。`fit-file-parser`の生成プロファイル
（`node_modules/fit-file-parser/dist/garmin_profile.generated.js`）を実際に
確認し、session/lap/recordメッセージのフィールド番号・スケール・単位を
特定した上で追加（`avg_cadence`=session18/lap17、`avg_temperature`=
session57/lap50、`avg_vertical_oscillation`=session89/lap77(scale10=mm)、
`avg_stance_time`=session91/lap79(scale10=ms)、`avg_step_length`=
session134/lap120(scale10=mm)。record単位は`cadence`=4、`temperature`=13、
`vertical_oscillation`=39、`stance_time`=41、`step_length`=85）。

**cadenceは片脚分（rpm）で記録される**というGarmin FIT SDKの既知の仕様に
従い、2倍して歩数/分（spm）として持つ（`RUNNING_CADENCE_LEGS`）。湿度は
FITの標準recordフィールドとして存在しないため対象外（引き続き手入力のみ）。

集計は`fitToSession.ts`の`deriveFitActuals`で、インターバルは**「メイン」
区間だけ**の平均、持続走は**セッション全体**（無ければlap平均）を使う——
ウォームアップ・クールダウンの遅いピッチを混ぜると実際の巡航ピッチより
低く出るため。温度は既存の`SessionResult.weatherTempC`に載せ、暑熱判定
（WBGT・`heatFlagged`）にもFIT由来の気温がそのまま使えるようにした
（新しい重複フィールドを作らない）。表示はFIT取込確認カードと同一処方
比較表（ピッチのみ、列を増やしすぎない）に留め、新しい分析画面は作っていない。

**検証**: `tests/fitParse.test.ts`・`tests/fitToSession.test.ts`に
先に赤→ 実装 → 緑。cadenceの2倍処理・メイン区間限定平均をそれぞれ
T-4で無効化し赤に戻ることを確認して復元。E2Eにも実際のFITメッセージで
ピッチ・気温が表示されることの確認を追加。

### 4. 「ジョグ＋坂ダッシュ」等の複合メニューを自動生成の時点で分割する

`src/lib/core/periodization.ts`の`hillSprints()`・`strides()`・テーパー期の
「刺激入れ（流し）」は、ジョグと刺激（坂ダッシュ／流し）を**1つの
prescription文字列**に結合していた。以前の対応（forge-v40）は複合本文の
検出・警告表示だけで、生成そのものは直していなかった。

週生成ループ（`generatePlan`）は1日につき`sessions.push`を1回しか呼ばない
設計だが、カレンダー側（`sessionsByDate`）・保存層は元々1日に複数
セッションを問題なく扱える（手動追加の「同じ日に午前と午後」機能が
既に動いている）。そこで`DayTemplate`に`combinedJogMin?: number`を追加し、
設定されていれば（かつ自作メニューを使っていない日は）ジョグ部分を
`jog()`の別セッション（`timeOfDay`を主セッションと分ける）として自動生成

ジョグの記述を削除し、別セッションの文言と役割が重ならないようにした。

**曜日の優先設定で「神経系」を固定する場合も同じ経路を通る**

ユーザーから「曜日設定でジョグ＋神経系のような複数種目に対応してほしい」

**検証**: `tests/periodization.test.ts`・`tests/weekTemplate.test.ts`に

## リファレンスUI刷新（forge-v45 / 2026-08-01）

`FORGE_UI_IMPLEMENTATION_BUNDLE.zip`（指示書＋リファレンス画像13点）に基づく

### なぜカード内のトラックはSVGなのか

リファレンスの光跡は写実的なレンダリング（モーションブラー・ブルーム・
アスファルトの粒状感）で、これをSVGフィルタで描き起こすのは以前失敗している。
そこで最初は**アプリアイコンの実素材をカードに敷いた**が、文字が読めなくなった。

拡大して確認したところ、**リファレンスのカード内トラックは写真ではなく
細い光の弧**だった。アイコンやスプラッシュの写実的な絵とは別物。
そのため用途で分けている。

- カード・セッション実行画面 → `app/components/brand/forge-track.tsx`（SVG）
- アプリアイコン → リファレンス画像そのもの（`pwa/icon-master.png`）
- スプラッシュのワードマーク → リファレンスから字形を抽出（後述）

### 画像パスをCSSに寄せている理由

`app/globals.css` の `url("./brand-wordmark.png")` で参照している。
JS側でパスを組み立てていないのは、**Next.jsとPWAでURLの基準が違う**ため。

CSSの `url()` は「そのCSSファイルの位置」を基準に解決されるので、
Next.js（`app/globals.css` 基準）でもPWA（`pwa-dist/styles.css` 基準）でも
同じ記述で正しく解決される。JS側で組み立てると必ずどちらかで壊れる
（PWAはハッシュルーティングで配信先がサブパス、Next.jsは絶対パス）。

実体は `app/` と `pwa/` の2箇所に置く。`scripts/build-static.mjs` の
コピー配列と `pwa/sw.js` の `ASSETS` の**両方**に登録が要る。
片方だけだとオフラインで画像が出ない。

### ワードマークを画像にしている理由

指示書が「斜体をかけた普通のテキストを最終実装にしないこと」と明示している。
実際、リファレンスの字形（幅広・角落とし）はフォント指定では再現できない。
`00-app-icon.jpeg` から白い字形だけを `alpha = min(R,G,B)` で抜き出している
（緑の光条はB成分が低いので、この式で消える）。CSSの `mask` として使うので
色は `currentColor` に従う。

**副作用**: 文字としての「FORGE」が画面から消える。読み上げと自動確認のために
見えないテキストを別に残してある（この後退はE2Eが検出した）。

呼び分けている（`src/lib/core/sessionSummary.ts`）。

### 視覚回帰（`npm run visual`）

8画面 × 3幅（390/393/430）＝24枚を `visual/baseline/` と比べる。

**判定はハッシュ比較。** 時刻（2026-08-15＝レースまで41日）・データ・
アニメーションを固定してあるので、同じ実装からはバイト単位で同じPNGが出る
（実測済み）。そのため pixelmatch のような画像差分ライブラリを入れていない。
どこが変わったかは `visual/current/` と `visual/baseline/` を並べて見るほうが速い。

**忠実度は自動判定できない。** リファレンスはベゼル入りの合成モックアップで
解像度も縦横比も違うため、実装スクショとピクセル比較しても意味のある差分に
ならない。自動化できるのは「前と変わっていないか」だけ。

ハマりどころが2つある。スプラッシュはReactがマウントすると自分で消えるので
`bundle.js` を読ませずに撮る。また「アプリを準備しています」が無限に点滅し、
撮るたびに不透明度が変わって毎回違うPNGになるので、撮る直前に**その要素だけ**
アニメーションを止めている（全部止めると `forwards` で最終状態を保持している
入場アニメが初期状態に戻ってしまう）。

### 届いていない点

スプラッシュのトラックは、リファレンスでは遠近のついた楕円で左へ光跡の尾が
抜けていく。こちらは正面から見た楕円で尾は無い。写実的なレンダリングの再現は
SVGの範囲を超えるため、差が残っている。

## 実運用で見つかった4件の修正（forge-v46 / 2026-08-01）

利用者からの報告4件。FITの本数の数え違いが1件、カレンダーの操作が2件、
分析タブの読みにくさが1件。

### 1. 1本の中を刻んだlapを別々の本と数えていた

報告: `1000m×4 r200jog`（実測 3:16.1 / 3:14.9 / 3:14.2 / 3:14.7）が
**`396m×12`** として読み取られる。

原因は `deriveFitActuals`（`fitToSession.ts`）が **lap 1つ＝1本** と数えていたこと。
時計で1000mの中を 400m / 400m / 200m と刻んで押すと、FITには本のlapが3つ入る。
これを別々の本と数えると、4本のはずが12本になり、
距離は最頻値（`mode`）を取るので400m側の396mが代表になっていた。

`groupIntoReps` を足して、**間に休みのlapが無く、かつ時刻が連続している**
メインlapを1本にまとめるようにした。休み無しで次の本が始まることはありえないので、
この並びは別々の本ではなく1本の中の通過。

まとめる条件を2つにしているのは、記録を止めて再開した場合を切り分けるため。
FITの `total_elapsed_time` は一時停止も含んだ実時間なので、
「前のlapの終わり ＝ 次のlapの始まり」なら、その間に休みは無いと言い切れる
（`SAME_REP_GAP_SEC = 2` は1秒刻みの丸めぶんだけを許す幅）。
時刻が読めないFITでは隣接だけで判断する——間にlapが無い以上、
休みが記録されていないことは確かなので、これは推測ではない。

まとめると通過の内訳が消えるので、`RepResult.splitsSec` に残して
記録サマリー画面（`/summary`）に `1:18.9 - 1:18.5 - 38.7` として出す。
本人はこの形で見ているし、合計だけでは前半で突っ込んだのか最後に落ちたのかが
分からなくなる。合計は必ず `actualSec` に一致する。

### 距離はトラックの距離に丸める（forge-v48で変更）

まとめた実測は 990m（396+396+198）になる。当初はこれをそのまま出していたが、
**丸めるように変えた**（本人の判断）。理由は、同じ 1000m×4 が日によって
990 / 991 / 989 と違う距離で記録され、`samePrescription`（同一処方の経時比較）が
別の練習として扱ってしまうため。GPSの誤差ぶんで比較が切れるのは実害が大きい。

`snapToTrackDistance` が、実測が `TRACK_DISTANCES_M` のどれかから
**3%以内**（`SNAP_TOLERANCE`）ならその距離として記録する。
3%は400mなら±12m、1000mなら±30m。トラックのGPSはカーブで内側を結ぶぶん
1%前後短く出るので、その誤差は吸収しつつ隣の距離には届かない幅にしてある——
一番狭い 1500m と 1600m でも6.7%離れているので、両方の範囲が重なることはない。
どれにも近くなければ**丸めずに実測を残す**（350mは300mとも400mとも言えないので、
350mのまま記録する）。

**丸めたときは必ず警告に出す**（`990m→1000m／ずれは最大1.1%`）。
距離は本数と並んで記録の骨格になる値なので、黙って書き換えると
あとで数字を疑うときに追えなくなる。元の実測は `FitImportRecord.parse` に
そのまま残っているので、解析を変えたときに読み直せる。

### 2. 固定枠をやらなかったときにカレンダーから外せない

固定枠（チーム練習等）は RULE-15 で変更も移動も禁止されており、
カレンダーでは長押ししても断られるだけで、✎ボタンも出ていなかった。
そのため**流れたチーム練習が予定として残り続け**、カレンダーが
これからやることの一覧ではなくなっていた。

RULE-15 が守っているのは「予定の組み替え」であって、
やらなかったという事実の記録ではない。固定枠にもシートを開けるようにし、
中身は変えられないと断ったうえで「やらなかった」だけを記録できるようにした。

**消すのではなく中止（`status: "skipped"`）にする。** 理由は2つ。

- 実施率・中止回数（4週間のバランス）に残る。消すと実施率が黙って上がる
- 消すと次のプラン再生成で復活する。`regeneratePlan` は
  `occupiedSlots`（日付＋時間帯）が埋まっていない枠に生成分を入れるので、
  中止として枠に残っていれば作り直されない

固定枠は後ろ倒ししない（`processSkip`）。日時が決まっているから固定枠なので、
2日ずらした「チーム練習」は実在しない予定になる。理由が「予定」でも
その日のまま中止にする。

中止した予定はカレンダーの一覧から外れ、行の下に取り消し線つきで
`中止 <名前> [戻す]` として残る。`restoreSkippedSession`（`DELETE /api/skip`）で
予定に戻せる——固定枠は手で作り直せないので、押し間違いを戻せないと詰む。
記録が入っているものは戻さない（中止なのに結果がある状態を作らない）。

### 3. カレンダーの表示期間が覚えられない

既定を2週間から**1週間**に変えた。1週間ぶんが1画面に収まって
「今週なにをやるか」が最初に目に入る。長い範囲は見たいときに選ぶ。

そのうえで、選んだ期間を端末に覚えさせる（`app/components/view-pref.ts`）。
これまでは画面の `useState` に持っていたので、記録タブに行って戻ると既定に戻っていた。

Store（練習データ）には入れない。これは「どう見たいか」であって練習の記録ではないし、
端末ごとに違ってよい。書き出し・同期の対象からも外れるべきもの。
読み込みはマウント後の `useEffect` でやる——`useState` の初期値で
localStorage を読むと、Next.js側（サーバーで一度描く）と食い違って
hydration エラーになる。保存された値が許可されている値でなければ既定に戻す
（想定外の値を近いものに寄せない）。

### 4. 分析タブが文字の壁になっていた

同じ言い回しの一文が日数ぶん縦に並び、どこを見ればいいのか分からない状態だった。
**文を消してはいない。** 判断に使う部分を図にし、文は畳んで残した。

**心拍の使われ方**: 「平均心拍 157bpm は最大の 79%（狙いは 65〜78%）。
狙いより強く走っています。…」という一文が8日ぶん並んでいた。
狙いの帯を線で描き、その上に実測の位置を打つ形にした（`HrRow`）。
外れている日は目で分かる。軸は %HRmax の 60〜100 だけを描く——
0から描くと帯（65〜97%）が右端に潰れて、外れているかどうかが見えない。
判定できない日は理由だけを短く出す（`blockedReason`）。文は行を開くと出る。

**制限因子**: 「400mから見た妥当域 1:48.00〜1:51.00」という数字が2つ並び、
その下に同じ数字を言い直した長い文があった。数字の並びからは、
PBがその域のどこにいるのか、目標が域の内側なのかが読み取れない。
2つの妥当域とPB・目標を**同じ数直線**に置いた（`LimiterScale`）。
軸は表示する値の実測の最小・最大から取る——妥当域は数秒の幅しかないので、
固定幅にすると全部が同じ位置に潰れる。根拠の文は畳んだ。

**週次レビュー**: 指導者に渡すための文章なので、この画面で毎回読むものではない。
畳んで、開かずに「コピーする」だけで用が足りるようにした。

### RULE-06が常時点灯していた問題（2026-08-04）

RULE-06（VLaMax上昇リスクの警告）は、21日間に高乳酸系セッションが**3回以上**あると

警告は、本人が慣れて無視するようになるだけで、頻度が本当に積み上がったときの
シグナルを埋もれさせる。

閾値を**4回以上**（`RULE06_THRESHOLD`）に変更した。週1を続ける限り3週の窓は
常に3回で止まるので、4回に達するのは「どこかで週1を超えて詰め込まれた」場合
（自作メニューの重複・生成側の不具合・本人が手で追加した場合など）だけになる。
週1を6週続けても鳴らないこと、3週で4回（週の途中にもう1本入る）はWARNになることを
テストで確認した。

他のルールにも同じ構造（閾値が生成エンジン自身の意図した値と一致していて
常時点灯する）が無いか、一巡だけ機械的に確認する余地がある

### ルール評価の重複計算（forge-v56 / 2026-08-04）

**症状**: 記録が増えるほどホームと分析タブが重くなる。実測（デスクトップ）:

|---|---|---|
| 150 | 11ms | 25ms |
| 400 | 63ms | 206ms |
| 800 | 250ms | 750ms |

件数5.3倍でdashboardが30倍。ルール評価がセッション数に対しておよそ**二次**で

ルールは ctx の純関数で、ctx は `buildRuleContext` で組み立てたあと変更されない

ctxが不要になればキャッシュも一緒に回収されるようにするため。

返すのは毎回**複製**。キャッシュした配列をそのまま返すと、呼び出し側が

実測（800件・デスクトップ）:

| 経路 | 前 | 後 |
|---|---|---|
| ホーム（dashboard） | 750ms | 521ms |
| 分析タブ（4週サマリー） | 1000ms超 | 251ms |

**検証**: メモ化を外すと落ちるテストを置いた（`tests/ruleEngineMemo.test.ts`）。
挙動が同じことだけを見るテストはメモ化を外しても通ってしまい、
あとで誰かがキャッシュを消しても気づけない（待ち時間が戻るだけで画面に何も出ない）。
初回と2回目の時間差で判定するが、実測で1000倍以上開くので境界は5倍と緩くしてある。

**残っている課題**: `runRuleEngine` 自体が二次で伸びる点は直していない。
多くのルールがセッション列を入れ子で走査しているためで、20以上のルールを
横断する変更になる。安全側の判定ロジックなので、必要になってから
（記録が500件を超えて体感に出てから）まとめて扱う。
現在の実データは137件（約25ms）なので急がない。

値（`forge.view.calendar.weeks`）はそのまま残るので、コードの既定を変えても
端末は4週間で開き続ける。保存キーを `calendar.weeks.v2` に変えて一度だけ
既定に戻した。変えたあとの選択はこれまで通り覚える。

**月送り**は日数計算が原因。`addDays(monthStart(a), dir * 30)` は
8月1日 + 30日 = 8月31日 で、その monthStart がまた8月1日になる。
31日ある月（8月・10月・12月など）では「→」を押しても永久に進まなかった。
`addMonths` を足して、日数ではなく月そのものを動かす。
戻る方向は -30日で前月に入れてしまうため、症状が出ておらず気づきにくかった。

## 確定範囲 — メニュー生成をどこまで「決まったこと」として出すか（forge-v59 / 2026-08-11）

### 何が問題だったか

生成はレース日まで全週を一度に作る（`periodization.ts` の `while (w <= raceDate)`）。
そのとき設定ペースは**生成した瞬間のCFE**で焼き込まれる。ところが更新は
M-2 が14日先までしか届かず、再生成は手動なので、2か月先のセッションは
古いCFEで作った数字を持ったまま残り、それが明日の練習と同じ顔で表示されていた。

これは「読めなかったものを推測で埋めない」に反する。
2か月先の設定ペースは推測なのに、決定事項として出ていた。

さらに悪いことに、更新側にズレがあった。`repaceFutureSessions` は
`targetPaces` だけを書き換えて処方の文面を放置していた。文面には
`400m × 3 @400m 52.5〜53.6秒 r6分` のように設定ペースが埋まっているので、
**CFEが2.5秒動いたとき34枠すべてで「画面には52.5秒、実際の設定は51.6秒」**という
状態になっていた。1秒近い差を、本人が気づけない形で持っていたことになる。

### なぜ「1〜2週ずつ生成する」ではないのか

未来の予定が存在することを前提に動いている機能が、実際に効いている。

- ルールエンジンの事前警告（「次の高乳酸は間隔を空け」は未来の予定を見ている）
- Q-2 の入れ替え候補（未来のジョグ枠から選ぶ）
- テーパー計画は21日先、統合タイムラインは28日先を読む

生成を短く切るとこれらが材料切れで黙る。**レース直前ほど効く機能**なので、
切るのは生成範囲ではなく**確定範囲**にした。骨組みは長いまま残す。

なおピリオダイゼーション自体は都度生成でも壊れない。フェーズはレース日からの
逆算（`phaseForDate`）なので、いつ生成しても同じ位置に入る。判断の分かれ目は
そこではなく、上に挙げた「未来の予定を材料にしている機能」のほうだった。

### 決めたこと（`src/lib/core/horizon.ts`）

**確定範囲は14日**。M-2（`adaptiveProposals` の既定 days=14）と揃えた。
M-2 は直近の実行状況とその日の状態から設定ペースを調整する仕組みで、つまり
14日先までは設定に手を入れられる。**手を入れられない範囲の数字に責任を持つとは
言えない**ので、責任範囲＝調整できる範囲にする。
ここを動かすときは `adaptiveProposals` の既定日数も一緒に見ること。
片方だけ伸ばすと「確定と言っているのに誰も更新しない範囲」が生まれる。

**判定は保存しない。** 日付から毎回計算する。保存フラグにすると、日が進んで
確定範囲に入っても古い印が残り、明日の練習が素案のまま表示される事故が起きる。

**素案では本数もレストも出さない。** 設定ペースだけ隠せば済む話ではなかった。
本数とレストは `buildSessionSpec` が直近の実行状況・疲労
（trend / loadHigh / recentFatigueSignal）から決めているので、2か月先の
「400m × 3」も同じく推測でしかない。半分だけ本当の文章を出すと、
どこまでが決まっているのか判別できなくなる。
残すのは種目・狙い・volume（週テンプレートとフェーズから決まり、CFEでは動かない）。

**本人が書いたものは素案にしない**（`userEdited` / `origin`）。
確定範囲が守っているのは「生成が推測で置いた数字を決定事項として見せない」ことで、
本人が決めた内容はそもそも推測ではない。ここを分けずに実装したところ、
2か月先の予定に自分でメニューを書くと定型文に差し替わって消えたように見え、
既存のE2E（カレンダーで保存したメニュー本文が一覧へ反映される）が落ちた。

### 更新は生成と同じ経路を通す（`refreshNearHorizon`）

文面側の数字を置換して辻褄を合わせることも考えたが、採らなかった。
処方の文面は `progression.ts` / `periodization.ts` が組み立てており、
表示のためにもう1か所で解釈すると「同じ文字列が場所によって違う意味になる」。
**生成と同じ経路で作り直す**ことにして、文面と設定が構造的にズレないようにした。
`repaceFutureSessions` は廃止し、呼び出し元3か所を差し替えている。

作り直すのは確定範囲だけ。その先は素案として設定ペースを出さないので、
古い数字を持っていても表示されず、確定範囲に入る前にここで作り直される。
触らないものは `regeneratePlan` と同じ（実施済み・中止済み・本人編集・固定枠・
自動生成でないもの）。**片方を直したらもう片方も確認すること。**

負荷条件（`loadSensitivity`）を生成と作り直しで共有しているのは、条件が違うと
同じ日付なのに作り直すたびに内容が変わってしまうため。

### 検証

- `tests/horizon.test.ts` … 境界・素案の中身・本人編集の除外・日が進めば確定に変わること
- `tests/nearHorizon.test.ts` … 文面と設定ペースの一致、触ってはいけないものを触らないこと
- E2E … 素案の詳細画面に設定ペースが出ないこと、素案から開始できないこと、
  確定範囲の中で文面と設定が食い違わないこと

**壊した状態で落ちることまで確認済み。**
処方の更新を止めると `tests/nearHorizon.test.ts` が「222 と 217.0 が一致しない」で落ちる。
詳細画面の素案判定を外すとE2Eが3件（ペースが出ている／いつ決まるか出ていない／
そのまま開始できる）で落ちる。

なお最初に書いたE2Eはカレンダー本文を読む形で、**壊しても通ってしまった**。
カレンダーの既定が1週間表示なので、14日より先の枠はそもそも描画されていなかった。
日付に依存しないセッション詳細を読む形に変えている。

### 画面側のワードマークもロゴに揃える（forge-v61 / 2026-08-12）

アイコンだけ新ロゴにすると、アプリ内のワードマークと字形が食い違う。揃えた。

**ワードマークはCSSの mask として使う**（色は `currentColor`）。つまり必要なのは
シルエットで、白＝不透明・黒＝透明のアルファ画像。したがって
**緑のタグライン `800M PERFORMANCE` は画像に含められない**——マスクでは色が
失われ、ワードマークと同じ色で塗られてしまう。ロゴのうちワードマークだけを
切り出し（実測 bbox x316..822 / y614..797、緑を除いた白画素のみ）、
輝度をアルファに変換して作った。JPEGのノイズで黒地にも輝度5〜20が乗るので、
下40・上215で切ってから伸ばしている（そのままだとマスク全体が薄く霞む）。
ロゴの斜めの切れ込みは元画像で黒なので、そのまま「抜け」になる。

タグラインは元から**テキストとして**存在していた（スプラッシュの `.tag`、
ヘッダーの副題）ので、そちらに任せればロックアップとして成立する。

**縦横比が変わるので定数も直す。** 旧 1120x205（比5.46）から
新 1012x366（比2.77）へ。`forge-logo.tsx` の高さ計算と `pwa/index.html` の
`aspect-ratio` の両方にある。スプラッシュの幅を430px→360pxに下げたのは、
幅を据え置くと高さが約2倍になり画面の中で浮くため。

**ヘッダーは skewX をかけた太字テキストをやめ、`ForgeLogo`（マスク）にした。**
以前のコメントには「アイコンのワードマークが斜体なので画面側も同じ傾きにする」
とあったが、新しいロゴは斜めに切れ込みが入った専用の字形なので、
テキストを傾けても似せられない。`ForgeLogo` は実装だけあって未使用だった。

**検査を足した理由。** テキストだったころは崩れても文字は出ていた。
画像に変えたことで、マスクのURLが解決できないと**正しい大きさの空の箱**になる。
エラーも出ないので画面を見ないと気づけない。要素の大きさだけを見る検査では
これを通してしまうので、ワードマークの範囲を切り出して
**明るい画素の割合**を数えている（実測約33%、空欄なら0%）。

壊した状態で落ちることは確認済み。`styles.css` のマスクURLを存在しない名前に
差し替えると `FAIL: R-3: ヘッダーのワードマークが空欄（明るい画素 0.0%）` で落ちる。
なお `brand-wordmark.png` を配信物から消す壊し方だと、Service Worker の
install が先に失敗してオフライン検査が落ちる（原因が分かりにくいだけで、
配信物から漏れること自体は検出される）。

### ロード表示を線と3点にする（forge-v62 / 2026-08-12）

400mトラックを1.45秒かけて描き、ゴールにフレアを出す演出をやめた。
細い線と3つの点だけにして、点を順に光らせる。

**理由。** 毎日開く道具に、起動のたび2.5秒の見せ場を入れるのは重い。
FORGEの原則は「数値を主役にする」で、起動画面の主役は演出ではなく
**レースまでの日数と目標との差**（R-2）のほうだった。
線は「ここまでが読み込みの枠」、点は「まだ生きている」ことだけを示す。

あわせて次を直した。

- **最低表示時間を2800ms→2000ms。** 2800msだったのは描画1.45秒＋フレア1.68秒を
  途中で切らないため。演出を変えたので、その値を守る理由が消えた。
  一度1200msまで詰めたが、実機で「速すぎて何が出ていたか分からない」となったので
  2000msに戻している。ワードマークと情報が出そろうのが約0.85秒なので、
  そこから約1.15秒は動かない画面が残る（点の点滅は1周1.35秒なので1周半ぶん）。
  0にしないのは、読み込みが速いときに一瞬光って消えるチラつきになるため。
- **出だしの遅延を詰めた**（ワードマーク1.78s→0.12s、情報2.18s→0.42s）。
  どちらもトラックが描き終わるのを待つ値だった。
- **背景の緑のにじみを外して黒一色に。** あれはトラックの発光を受けるための
  ものだったので、演出と一緒に落とす。
- **Next.js側（`launch-splash.tsx`）も同じ形にした。** 片方だけ変えると、
  同じアプリなのに実行環境で起動画面が変わる。ついでにこちらだけ残っていた
  skewXの太字テキストのワードマークも、画像（マスク）に揃えた。

**検査。** R-2はトラックのレーン本数を数えていたので、線と点を見る形に変えた。
要素の有無だけでは「3つ並んでいるが全部潰れている」を通してしまうので、
線の幅と点の大きさまで見る。点を消すと
`FAIL: R-2: 読み込み表示の点が3つでない` で落ちることを確認済み。

## 時間が経ってから開くと白飛び→かくかく（forge-v64 / 2026-08-12）

実機で「ちょっと時間たってから開くと、画面が白くなってからカクつく」。
原因は3つ別々にあり、どれも**コールド起動のときだけ**出る。
メモリに残っている間の再開ではリロードが起きないので、普段は気づけない。

### 1. iOSの起動画像が無い（白飛びの本体）

`manifest.webmanifest` に `background_color: #0a0a0a` は入っているが、
**これを見るのはAndroid/Chromeで、iOSは見ない。**
iOSのホーム画面PWAは `apple-touch-startup-image` を使い、無いと白い画面を出す。

`scripts/build-splash-screens.mjs` で12機種ぶん生成した。
**実物のスプラッシュをそのまま撮っている**（bundle.jsを止め、reduced-motionで
フェードの途中を撮らないようにして開く）。静止画を別に組むと本物とわずかにズレて、
「起動画像 → 本体」の切り替わりで画がガタつくため。
iOSはサイズが完全一致したときだけ使うので、機種ごとに1枚要る。

### 2. アプリ本体がネットワーク優先（白飛びが長引く原因）

`sw.js` は `index.html` / `bundle.js` / `styles.css` をネットワーク優先で返していた。
手元のキャッシュに完動品があっても、まず通信を試して、失敗して初めてキャッシュに落ちる。
`bundle.js` は約1MBあるので、電波が悪いと起動のたびに白い時間が数秒伸びる。

**stale-while-revalidate に変えた。** キャッシュを即返し、取得した新版はキャッシュへ入れて
次回起動で反映する。

ネットワーク優先だったのには理由があって、**VERSIONを上げ忘れて再配信しても届く**
という保険だった（`e2e-update.mjs` が見張っている）。この保険は1回遅れで残る。
VERSIONを上げた場合は install が新しいキャッシュを作るので、これまで通り即座に切り替わる。

`e2e-update.mjs` の契約もそれに合わせた。1回目のリロードで**旧版が出ること**まで
見ているのは速さの回帰を防ぐため——ここで新版が出るなら、キャッシュを即返さず
通信を待っている証拠になる。

### 3. 点のアニメが色を動かしていた（かくかくの原因）

```css
@keyframes splash-dot { 0%,60%,100% { background: rgba(...) } 25% { background: var(--forge) } }
```

**色のアニメーションはコンポジタに乗らない。** 毎フレーム、メインスレッドでの
描き直しが要る。ところがこの画面が出ている最中のメインスレッドは、約1MBの
bundle.js の解析と最初の描画で埋まっている。結果、点だけが取り残されてカクついた。

点を2層にして、上に重ねた緑の層の `opacity` だけ動かす形にした。
opacity なら合成側で回るので、メインスレッドが詰まっていても滑らかに動く。
同じ画面の `.brand` / `.info`（opacity・transform）と `.wait`（opacity）が
滑らかだったのは、元からコンポジタで動いていたため。

### 検証

壊した状態で落ちることまで確認済み。

- 起動画像を1枚消す → `FAIL: R-3: 起動画像 ./splash-1170x2532.png が配信物に無い`
- 1回目のリロードで新版が出る（＝通信待ちに戻る）→ `FAIL: 1回目のリロードで新版が出た`
- 2回目でも旧版のまま（＝裏の更新が効かない）→ `FAIL: 2回目のリロードでも旧版のまま`

### ヘッダーの400mトラックのマークを外す（forge-v65 / 2026-08-12）

ヘッダー左上にあった緑の400mトラック（`ForgeMark`）を削除し、ワードマークだけにした。

**理由。** アプリアイコンを新しいロゴに差し替えたとき、新ロゴが**文字だけの構成**に
なり、対応するシンボルが存在しなくなった。無いものに形を寄せることはできない。
トラックを残すと「アイコンには無い記号がアプリの中だけにある」状態になる。
緑はタブと数値の側に集約する（黒白グレー90%・アクセント10%の配分に沿う）。

下タブの TODAY アイコンは同じトラックの形のまま残している。あちらは
ブランドの記号ではなく**タブの機能を示すアイコン**（カレンダー・同心円・棒グラフと
同じ役割）なので、ロゴの変更とは切り離す。

**E2Eの検査はここで消した。** 以前は `header svg path` を4本数えていたが、
マークを外したあともヘッダーには設定の歯車のSVGが残る。検査を残すと
**歯車を掴んで通ってしまい、マークが消えていても気づけない**。
代わりにワードマークの有無を見る（描画の中身は既存の画素チェックが見ている）。
ワードマークをただの太字テキストに戻すと
`FAIL: R-3: ヘッダーにワードマークが無い` で落ちることを確認済み。

### ロゴを差し替え、ワードマークをマスクから画像に変える（forge-v66 / 2026-08-12）

アプリアイコン・ロード画面・ヘッダーのワードマークを、新しい角落としのロゴに差し替えた。

**マスクをやめた。** これまでワードマークはCSSの `mask` で使い、色は `currentColor` に
従わせていた。新しいロゴは**緑の縦線がロゴの一部**なので、マスクにすると緑が
白に潰れる。実際の使用箇所（ヘッダー・スプラッシュ）は全部白で、色を変えている
場所は無かったので、色を持った透過PNGをそのまま出す形にした。
**色を変えたくなったら画像を分けること**（もう currentColor では変わらない）。

透過への戻し方は、元画像が黒地に描かれた（＝黒に合成済みの）JPEGなので

```
a   = max(R,G,B)
RGB = 元の色 / a
```

で非合成化する。輝度をアルファにすると緑が薄く出るので max を使う。
割り戻さないと、文字の縁が灰色に濁る。

**縦横比が毎回変わるので、寸法は全部見直す。**

| | 比 | スプラッシュ幅 | ヘッダー幅 |
| --- | --- | --- | --- |
| 1120x205 | 5.46 | 430px | — |
| 1012x366 | 2.77 | 360px | 46px |
| 1124x918 | **1.22** | **260px** | **34px** |

ほぼ正方形になったので、幅を据え置くと高さが約3倍になる。
`forge-logo.tsx`（高さ計算）・`pwa/index.html`（`aspect-ratio`）・
`globals.css`（`.launch-wordmark`）・`nav.tsx`（ヘッダー幅）の4か所にある。
**ロゴを差し替えたら4か所とも直す。**

**起動画像も作り直す。** `splash-*.png` は実物のスプラッシュを撮ったものなので、
ワードマークが変われば中身が古くなる。`npm run build:splash` → `npm run build:all` の順。

**検査。** ヘッダーの画素チェック（明るい画素の割合）はマスクでも画像でも同じように
効く。`styles.css` の画像URLを存在しない名前に差し替えると
`FAIL: R-3: ヘッダーのワードマークが空欄（明るい画素 0.0%）` で落ちることを確認済み。

## CFEを実測タイム基準に作り直す（forge-v67 / 2026-08-12）

本人から「CFE（推定800mタイム）が感覚とかなりズレる」。計測したら**構造的な偏り**だった。

### 何が起きていたか

旧式は `暗黙の800m = 現CFE + ΔRPE×0.4 + 未達幅` で、未達幅は

```js
shortfall = Math.max(0, (actualPerM - targetPerM) * 800);
```

**速く走った分は `Math.max(0, ...)` で捨てていた。** つまりタイムが速いことはCFEに
一切入らず、改善が入る経路はRPE（主観）だけだった。CFE 1:51.0 / 設定 400m×3 @55.5秒
で実測したところ:

| 実測 | RPE | 旧 | 新 |
| --- | --- | --- | --- |
| 52.0秒（設定より3.5秒/本 速い） | 6 | −0.17秒 | **−0.38秒** |
| 52.0秒（同じタイム） | 9 | **+0.08秒（悪化）** | **−0.32秒（改善のまま）** |
| 55.5秒（設定どおり） | 8 | 0 | 0 |
| 58〜59秒（未達） | 9 | +1.34秒 | +1.50秒 |

改善と悪化で効き方が8倍違い、**同じタイムでもRPEの入れ方で符号が反転していた**。
続けるほど遅い側へ寄る作りで、初期値も `PB + 1.5秒`（12週以内にレースが無い場合）。
感覚と合わなくなるのは当然だった。

### 直し方

`impliedFromInterval`（過去データからの現在地測定で既に使っている実装）を
通常の練習結果にも使う。実測平均 ÷ カテゴリのGRP比率 × 800 で800m相当を出す。
**換算をCFE側に書き直さない**——同じ実測から画面ごとに違う推定が出てはいけない。

- **速い側・遅い側が対称に効く**
- **RPEは補助に降格**（係数 0.4 → 0.15）。符号を反転させない。
  0にしないのは、レストを削った・向かい風だった等がRPEにしか出ないため
- **RPE6未満（全力でない）の実測は使わない**。能力の下限しか分からないため
- **設定ペースを一切見なくなった。** 副次効果として「目標タイムが設定に混ざって
  CFEに逆流する」問題（`goalTargetTimeSec` で打ち消していたもの）が構造的に消えた
- **中断は値を盛らず、その結果の信頼度を半分にする**。実測基準では完走した本の
  タイムがそのまま入るので、未達を足すと二重に罰することになる

**いちばん大事な性質**: 生成器の設定どおりに走ると implied = CFE ちょうど（delta 0）。
生成と推定が同じ比率表（`GRP_RATIOS`）を使っているため。ここがずれると
全セッションでCFEが漂流するので、テストで固定してある。

ガードレールは全部そのまま（±1.5秒／レースは±3.0秒／暑熱・疲労時は反映しない／
14日で鈍化／aerobic・neuralは使わない）。

**実測が無い記録ではCFEは動かない。** RPEだけ入れても動かないので、
既存テストで `actualLapsSec: []` のまま「RPEでCFEが悪化する」を見ていたものは
実測を入れる形に直した。

## 午前枠の助言（forge-v72 / 2026-08-13）

- 2部にしていない
- PBが足りず制限因子を判定できない（推測で言わない）

- 「維持が制限」のとき——増やしたいのは経済走・モデリングだが、どちらも高負荷なので

  すぐリロードしていたため、助言が出ない側に倒れていた。待ってから読み直し、
  さらに**PBが実際に保存されたか**を先に確認してから助言を判定するようにした
  （書き込みが消えたのか助言が壊れたのかを区別できないと、原因を追えない）。

E2Eは黙る側と出す側の**両方**を通す。出さないことだけ確認して終わると、

`assessFitness` は `repo.listPastEntries()` だけを読んでいた。
記録タブで入れた結果（`SessionResult`）は入っていない。つまり

> 同じ高乳酸のセッションでも、**過去データ画面から入れたか記録タブから入れたかで
> 現在地の測定に入るかどうかが変わっていた**

同じ入力から同じ結果が出るという原則に反する。実機では直近3週間ぶんが
測定の材料から丸ごと落ちていた。

記録タブの結果も同じ材料として扱うようにした（`resultsAsPastEntries`）。

- **過去データ由来の結果は除く。** `addPastEntry` は PastEntry と SessionResult の

- 暑熱の除外が効くように環境も引き継ぐ。`SessionResult` 側は `weatherTempC`

片方だけ直っている**という誤りが4回続けて出た。
`GRP_RATIOS` を持たないカテゴリの扱いと、距離が混ざったときの代表距離の決め方は、

- `updateCfeFromResult`（cfe.ts）
- `impliedFromInterval` / `assessCurrentFitness`（backfill.ts）
- `resultsAsPastEntries`（service.ts）
- `parseRow` の複合セット処理（bulkImport.ts）

## 処方の土台をPBより速くしない（forge-v75 / 2026-08-13）

現在地の測定をやったら 1:54.2 → **1:48.3**。800mPB（1:49.51）より1.2秒速い。
本人が「少し速すぎる気もする」。調べたら**ガードが無かった**。

### 何が起きていたか

材料が1件のとき、推定値はその1件の換算結果**そのもの**になる。

```js
estimated = Σ(implied × weight) / Σweight   // 1件なら = implied
```

`weight`（信頼度×直近性）は**信頼度の表示にしか効かず、値には効かない**。
さらに `applyAssessedCfe` はその値をそのまま保存する。上限も収縮も無い。

そして設定ペースはCFEから計算されるので、**信頼度が低くても処方はその速さで組まれる**。
信頼度は表示されるだけで、何も守っていなかった。

### 直し方（CFEは触らない）

FORGEには元から「CFEは能力の推定、設定ペースは今日出せる値」という分離がある。
今回の問題はその分離が基準タイムのところで効いておらず、推定がそのまま処方へ流れていたこと。
**守るのは処方のほう**にした。

`guardedBaseTime` に800mPBを渡し、土台がPBより速くならないように頭打ちにする。

- CFEは「練習からは1:48.3と出ている」と正直に持つ（情報を殺さない）
- 実際に出す設定はPBペースを超えない
- **PBは定義上「これまでで一番速く走れた記録」**。それを超えるペースはまだ一度も
  出したことがない速さなので、そこを土台に処方を組むと実行できない設定が出続ける
- レースかTTでPBを更新すれば上限も上がる。自己修正する
- 速い側へ寄せるのは目標タイムの寄与が担当する（そちらには非現実的な目標を弾く判定が
  別にあるので、二重に効かせない）

頭打ちにしたことは必ず理由で言う（黙って遅くしない）。
文面は生成の `selectionReasons` に乗るので、セッション詳細から追える。

```
推定（1:48.3）が800mPB（1:49.5）より速いため、処方の土台はPBで頭打ちにしています。
PBを超える設定は、レースかTTでその速さを出してから使います
```

**検証**: CFE 1:48.3 と PB 1:49.51 で生成した計画が、CFE=PB で生成した計画と
同じ設定（200m 26.01秒）になることを確認。頭打ちを外すとテスト2件が落ちる。

### 採らなかった案

- **件数に応じて現CFEへ収縮**: 寄せる先（1:54.2）が鈍化で汚れていたので逆効果
- **1件では適用させない**: 正しいが「直せない期間」が生まれる
- **幅で出して選ばせる**: 原則には合うが、毎回の判断コストが釣り合わない

## アプリの中で相談できるようにする（forge-v77 / 2026-08-13）

「なんでCFEがこの値なの」「なんで今日これなの」は、これまで**開発側に聞くしかなかった**。
アプリはその答えを全部持っている（CFEの更新履歴・生成器が残した選定理由・ルールエンジンの判定）が、
画面のあちこちに散っていて、本人が自分で組み立てて読むのは現実的でなかった。

設定 → 分からないとき → 相談（AI）に置いた。

### LLMに数値を触らせない

CLAUDE.md の「LLMを使わない。同じ入力からは必ず同じ結果が出ること」は**変えていない**。
変えると、あとで数値を疑ったとき、どこまでがルールでどこからがLLMか追えなくなる。

```
決定的なコア（これまでのまま）
  CFE・設定ペース・ルール判定・メニュー解釈
       ↓ 読むだけ
コンテキスト生成（`src/lib/core/assistantContext.ts` 純関数・テスト済み）
       ↓ これだけを送る
LLM ── 応答は文章のみ。数値を書き戻す経路を実装していない
```

`buildAssistantContext` は純関数で、時刻もランダムも読まない。
同じ入力からは必ず同じ文字列が出るので、あとで答えを疑ったときに何を渡したか再現できる。

### 画面に出す文字列と送る文字列を同じ実体にした

データが端末の外へ出る。「何が出ていくか」を本人が確認できないまま送ってはいけない。
ただし「送る前に見せます」と書くだけでは、実装がズレたときに誰も気づけない。

そこで `AssistantContext.text` を **`sections` から組み立てる形にした**。
画面は `sections` を出し、送信は `text` を送るので、片方だけ変えることが構造的にできない。
`tests/assistantContext.test.ts` がこの一致を固定しており、
`text` を別に作るように壊すと19件中8件が落ちる（確認済み）。

送るのは訓練の数値だけ。氏名は `AssistantContextInput` に項目そのものが無い。

### 同意は鍵の設定とは別に取る

APIキーを入れることは「使えるようにする」操作でしかなく、
**何が出ていくかを把握したこと**とは別。チェックボックスを分けた。
同意が無い間は1文字も送らない（E2Eが見張っている）。

### SDKを入れずRESTを直接叩く

`app/components/supabase.ts` と同じ判断。理由も同じで、
PWAのバンドルに数百KBのSDKを入れると起動時間に直接効く（`ci:perf-budget` が見張っている）。
使うのは `POST /v1/messages` 1本だけで、SDKの大半が要らない。

ブラウザから直接叩くので `anthropic-dangerous-direct-browser-access: true` が要る。
GitHub Pages配信でサーバを持たないため、他に経路が無い。
このヘッダが落ちると本番で全滅するので、E2Eで実際の送信を横取りして確認している。

### オフラインでは機能ごと出さない

押しても何も起きないボタンを残すと、壊れているのか通信が無いのかを本人が区別できない。
相談だけを畳み、他の画面はこれまでどおりオフラインで動く。

### 失敗を種類で分ける

「エラーが出ました」だけでは本人が直せない。
401＝鍵、429＝待てば直る、500＝向こうの問題、時間切れ、接続不能、断られた、を別々に出す。
`stop_reason: "refusal"` は**中身を読む前に**判定する。断られた応答は途中まで文が入っていることがあり、
そのまま出すと「短い答えが返ってきた」ようにしか見えない。

`fallbacks`（断られたときに別モデルへ回す機能）は入れていない。
走練習の相談で安全分類に触れることは実質なく、
使えない鍵・使えないベータで毎回400になるほうが、この1人用アプリでは損が大きいと判断した。

### 次にやること

写真からの入力の転記（写真 → テキスト → 既存の `parseRow` → 本人が確認して確定）。
解釈はこれまでどおり `bulkImport.ts` の `parseRow` が唯一の実装で、LLMは文字起こしまでしかやらない。

過去データ → まとめて入力に、写真から文字を起こす経路を足した。

```
写真 → （LLM）文字起こし → 本人が目で直す → parseRow が解釈 → 本人が確定
```

### LLMにやらせるのは文字起こしだけ

意味を読み取らせない。`bulkImport.ts` の `parseRow` が唯一の解釈という前提を崩さない。

これは妥協ではなく、こうしないと成立しない。
「300(42)×3」が高乳酸なのかCVなのかは**今のCFEに対する比率**で決まるので、
写真を見ただけのLLMには本来決められない。決められないものを決めさせると、
あとで数値を疑ったときに、どこで曲がったのか追えなくなる。

指示で禁じているのは、推測での穴埋め・表記の整形・並べ替え・種類の判定。
読めない箇所は `【読めず】` と書かせる。`?` にしないのは、日誌そのものに
本人が `?` を書くこと（「1:26?」）があり、区別できなくなるため。

`cleanTranscription` がやるのは**取り除くことだけ**（コードフェンス・前後の空行）。
中身を直したら、それはもう文字起こしではなく解釈になる。

### 起こした文字は入力欄に入るだけ

保存までに本人が2回見る（起こした文字／解釈結果）。文字起こしは必ず間違うので、
この2回を飛ばさない。E2Eで「転記しただけでは1件も保存されない」ことを見張っている。

既に書いてある内容は消さずに足す。手で打った途中の行を写真1枚で消されると打ち直しになる。

### 送る前に縮める

撮ったままは4000px近くあり、そのまま送ると通信も費用も無駄に増える。
小さくしすぎると手書きが潰れ、読めない箇所が増えて直す手間が本人に返ってくるだけ。
長辺2576pxで止める（Anthropicの高解像度の上限。超えて送っても向こうで縮められる）。
大きさの計算は純関数（`fitWithin`）にしてテストしてある。canvas を使う部分は判断を持たない。

## 表記辞書の候補出し（forge-v79 / 2026-08-14）

一括入力で読めなかった行について、辞書に入れる語の案を出せるようにした。
設定 → 過去データの一括入力 → 解釈する → 読めなかった行に「読み方の候補を出す」。

### なぜこれを選んだか

**使うほどAIを呼ばなくなる**方向に働く唯一の案だったから。

辞書は一度登録すれば以降 `bulkImport.ts` が決定的に読む。だから候補出しが動くのは
「まだ知らない書き方に初めて出会ったとき」だけで、同じ語には二度と呼ばれない。
チーム固有の呼び方は有限なので、使い続けると呼び出しは自然に減っていく。

これまでの `guessPhrase()` は「数値を落とした残りで一番長い語」を拾うだけだった。
組み込みの語彙をこちらで足し続けてもチーム固有の呼び方には追いつかない、
という元々の問題は変わっていない。追いつかせる側を本人＋AIに寄せた。

### 出すだけ。登録するのは本人

押しても入力欄が埋まるだけで、辞書は増えない。
これまでどおり「この書き方を覚えさせる」を押して初めて登録される。
E2Eで「埋めただけでは辞書が増えない」ことを見張っている。

行ごとの分類はさせていない。させると同じ文字列が日によって違う意味になりうる状態ができ、
`parseRow` が唯一の解釈という前提が壊れる。ここで作るのは辞書の1エントリだけで、
中身は画面で確認・編集でき、あとから一覧で消せる。

### 入口の検査を厳しくした（`phraseSuggestion.ts`）

辞書は一度入ると効き続ける。妙な語が入ると以降その語を含む行が全部そう読まれ、
しかも本人は「なぜこう読まれたのか」を辞書まで遡らないと分からない。
入口で止めるほうが安いので、少しでも怪しければ案にしない。

通さないもの:

| 条件 | 理由 |
| --- | --- |
| その行に書かれていない語 | 言い換え・要約を辞書にしない（「読めなかったものを推測で埋めない」と同じ考え） |
| 2文字未満 | どの行にも当たってしまう |
| 数字・記号だけ | 同上 |
| 決められた種類・カテゴリの外 | 画面の選択肢とずれる |
| 理由が無い | 却下する材料が本人に残らない |

種類と合わないカテゴリ（休養なのに高乳酸など）は黙って捨て、案そのものは活かす。

「行に書かれていない語を通さない」が一番効く検査で、これを外すとE2Eが落ちることを確認した。

### 送る内容

読めなかった**1行**と、すでに覚えている語の一覧だけ。相談（AI）より大幅に少ない。
鍵と同意は相談（AI）と共通で、未設定・オフラインならボタンそのものを出さない。

## 起動時に読む量を半分にする（forge-v80 / 2026-08-14）

`bundle.js` が予算の96%まで来ていた。相談・写真・辞書を足した結果だが、
これらは**起動時には要らない**。それでも毎回全部読まれていた。

TODAY以外の画面を遅延読み込みにした。

| | 前 | 後 |
| --- | ---: | ---: |
| bundle.js（起動のたびに読む） | 1,035,868 | **550,588** |
| 配信物のJS全体 | 1,463,911 | 1,476,122 |

全体は少し増えている（分割の境界ぶん）。**減らしたいのは起動時に読む量**で、
そこが半分になった。JSは読むだけでなく解析・実行に時間がかかるので、
iOSでアプリがメモリから落とされたあとの起動に直接効く。

分割の仕組み自体は既にあった（FIT解析が遅延読み込み済み）。実証済みの経路に乗せただけ。

### chunkをプリキャッシュするようにした（既存の穴）

`pwa/sw.js` の `ASSETS` は静的な一覧だが、chunkのファイル名にはハッシュが入るので
そこに書けない。**書いていなかったので、chunkはプリキャッシュされていなかった。**

これまでは遅延読み込みがFIT解析だけだったので実害が小さかったが、
画面を分けるならここを直さないと「インストール直後にオフラインへ入ると、
一度も開いていない画面が開けない」ことになる。

`scripts/build-static.mjs` が、配られた `chunk-*.js` の実体名を
`pwa/sw.js` の `const CHUNKS = [];` へ差し込む。差し込み先が無ければビルドを止める
（sw.js を書き換えたときに黙って素通りしないように）。

## 処方の文面を自分で読み違えていた（forge-v82 / 2026-08-14）

結果入力の画面で、次の3つが同時に起きていた（本人の指摘）。

```
処方:  300m × 3 @300m 38.7〜39.5秒 r207秒（jog）
欄:    設定(秒) 300 / レスト(秒) 300
```

1. レストが207秒という、なぜその数字か説明できない値
2. 処方は207秒なのに、欄は300秒
3. 300mの設定が300秒（実際は38.7〜39.5秒）

### 原因1: `@` の直後の距離ラベルを設定タイムとして読んでいた

`parseAtTarget` の正規表現が `@300m 38.7〜39.5秒` の **300** を拾っていた。

これは表示だけの問題ではない。設定300秒/300m はGRPの721%なので、
**パーサはこの日をCVと判定していた**。画面には「高乳酸」と「設定300秒」が同時に出ていて、
どちらが本当か本人に判断できない状態だった。

`describeSpec` のコメントには「一括入力が読み取れる書き方に揃える（同じ解釈を通すため）」と
書いてあったが、**成立していなかった**。自分が出したメニューを自分で読み違えていた。

数字の直後が `m` ならラベルとみなして飛ばすようにした。`@300`（m無し）は従来どおり300秒。

### 原因2: レストが漸進の掛け算で端数になっていた

3週目の密度上げで `restSec * 0.8` を掛けて207秒になっていた。
トラックで秒単位に刻む値ではないので精度に意味が無く、読んでも理由が分からない。

5秒刻みに丸める（`roundRestSec`）。**丸めるのは表示ではなく値そのもの。**
表示だけ丸めると、文面の210秒と保存された207秒が食い違って、どちらが本当か分からなくなる。

### 原因3: 結果入力のレストが処方を見ずに既定値へ落ちていた

`useState(String(ex?.restSec ?? ex?.restDistanceM ?? 300))` — 過去の結果が無ければ **300固定**。
処方を一切見ていなかった。

`PrescriptionStructure` に `restSec` / `restDistanceM` / `restType` を持たせ、
初回入力では処方から入れるようにした。読み取れなかったときだけ従来どおり既定値にする。

あわせて、レストの種類が括弧で後置される形（`r207秒（jog）`）をパーサが読めるようにした。
読めないままだと「完全休息」がjogとして扱われる。

### 検証: 生成器とパーサを突き合わせる（`prescriptionRoundTrip.test.ts`）

片方だけのテストではこの食い違いは見つからない。生成した処方を全部パーサに通し、
カテゴリ・設定タイム・反復距離・レストが一致することを見る。
`@` の修正を戻すと4件落ちる（確認済み）。

E2Eにも「処方の文面と結果入力の欄が同じ値」を足した。
レストの初期値を処方から入れる処理を外すと落ちる（確認済み）。

### 見つけたが直していないもの

この突き合わせで**同じ型の食い違いが2つ**見つかった。どちらも別の判断が要るので今回は直さず、
現状をテストで固定した（直したらそのテストが落ちるので気づける）。

| 食い違い | なぜ今回直さないか |
| --- | --- |
| 閾値の設定（GRPの160%）がパーサのCV帯に入る | 帯の再調整は競技的な判断を含む。片方に寄せると練習の意味が変わる |
| 複合（`500m + 300m`）の処方を持続走として読む＝欄が組み上がらない | パーサの複合対応が要る。モデリングの日の結果入力に影響するので別途 |

流し（`150m流し × 6本`）は設定が書かれていないので判定できず、パーサは
`categoryCertain: false` を返している。これは「分からない」と言えているので正しい振る舞い。

## 複合（モデリング）の処方を自分で読めなかった（forge-v83 / 2026-08-14）

forge-v82 で生成器とパーサを突き合わせたときに見つけた2件のうち、実害が明確なほう。

```
生成: 500m + 300m @500m 68.7〜69.4秒 / 300m 41.2〜41.6秒 r1分（walk）
解釈: kind=continuous, slots=[]   ← 持続走として読む
```

**モデリングの日に結果入力の欄が組み上がらない。** 距離も設定も出ないので、
レースの形を再現する練習をやったのに、その中身を記録できない状態だった。

### 直し方: 生成器を、本人が書く形に寄せた

パーサは元から `300(42)＋600(1:26)＋600(1:26)` の形を読める。
これは本人が日誌に書いている形そのもの（一括入力の例文にも載っている）。
生成器がそれと違う形を出していたことが原因なので、生成器側を寄せた。

```
500m(68.7〜69.4)＋300m(41.2〜41.6) r1分（walk）
```

距離と設定が並ぶので人にも読みやすい。本数ぶんは繰り返して書く
（`×2` はパーサが本数として数えないため、まとめると区間が減って伝わらない）。

パーサ側に旧形式の読み方を足す案は採らなかった。
唯一の解釈場所に、もう生成されない形式のための分岐を永久に残すことになるため。

### 端末に残っている旧形式の予定について

すでに生成済みのモデリングの予定は旧形式のままで、読めない。
ただし遠い日の予定は確定範囲（14日）の外＝素案なので、近づけば作り直される。
すぐ揃えたい場合は目標・レース画面から再生成する（手で編集した予定は保護される）。

旧形式が読めないこと自体はテストで固定してあるので、状態は追える。

### カテゴリの食い違いが1件増えた（想定どおり）

複合が区間に割れるようになったことで、パーサがモデリングを高乳酸と読むようになった。
これは**設定ペースの比率からは区別できない**もので、文面の問題ではない。
モデリングは「レースの形を再現する」構造で決まる種目なので、
区間ごとのペースだけ見れば高乳酸と同じに見える。既知として固定した。

残る既知の食い違いは2件（どちらもペース比からカテゴリを復元できない性質のもの）:

| 食い違い | 性質 |
| --- | --- |
| threshold → cv | 閾値の設定がパーサのCV帯（GRPの160%）に入る。帯の再調整は競技的な判断を含む |
| modeling → high_lactate | モデリングは構造で決まる種目。ペース比からは判定できない |
