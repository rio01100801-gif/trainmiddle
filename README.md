# FORGE — 800m Performance System

**Built Through Training.**

800m専門ランナーが目標タイムと現在地を入力すると、生理学的根拠に基づいた練習メニューを自動生成し、練習結果のフィードバックによって以降のメニューを自動補正するツールです。

中核は**ルールエンジンによる制約チェック**（RULE-01〜22）です。メニューを「出す」ことではなく、危険な・非効率な組み方（高乳酸の過頻度、質練習の過密、有酸素偏重、テーパー破壊など）を機械的に検出して弾くことを最優先に設計されています。コアロジックは完全ルールベースで、同じ入力に対して常に同じ出力を返します。

> **手元のPCに移す場合は `MIGRATION.md` を参照。作業時の約束事は `CLAUDE.md` にまとめてある。**

### PWAのビルドに bun が要る理由

`app/` 配下の画面は Next.js と PWA の両方で使い回している。
そのため import は `next/link` / `next/navigation` のままにしてあるが、
PWA は Next.js のサーバーを持たないので本物の Next.js は動かない。
`scripts/build-pwa.mjs` がビルド時だけ `pwa/shims/` の実装に差し替える。

tsconfig の `paths` で解決していないのは、Next.js 側のビルドにも効いてしまい、
`npm run dev` で本物の `next/link` が使われなくなるため。
差し替えは「PWAをビルドするときだけ」に限定する必要がある。

データは `data/train800.db`（SQLite）に保存されます。

ヘッダーのマークは400mトラック。走路2本と、中央の切れ目（スタート／フィニッシュ）だけで構成します。
アプリアイコンは別用途なので、黒背景・白いFORGEワードマーク・蛍光グリーンのトラック光跡を使います。

（画像ライブラリを増やすとネイティブビルドが要るものが混ざり、Windowsで入らないことがあります）。

| 原本 | 書き出し | 用途 |

| `pwa/icon-master.png` | `icon-32.png` | favicon |

左右2本のパスに分けて描いています。

**iOSのホーム画面アイコンは、追加した時点で焼き付けられます。**
アイコンはアプリの一部ではなくショートカットの一部なので、
配信を差し替えても Service Worker を更新しても、既に置いてあるアイコンは変わりません。
**一度削除して追加し直す以外に方法がありません。**

そのうえ Safari は `icon-180.png` 自体もキャッシュしているため、追加し直しても
古い画像のままになることがあります。これを避けるため、`build-static.mjs` が
`index.html` と `manifest.webmanifest` のアイコン参照に `?v=<VERSION>` を付けます。
手で書くと上げ忘れるので `sw.js` の `VERSION` から自動で入れています。
`sw.js` の precache も同じクエリ付きURLにしてあります
（素のファイル名のままだと、オフライン時にアイコンだけ取れなくなる）。

デザイントークンは `app/globals.css` の `:root` に集約してあるので、
色を変えたい場合はそこだけ触れば全画面に反映されます。

`design/mockup.html` と `design/screens.html` は実際にブラウザでレンダリングして確認した
デザイン仕様です（ダブルクリックで開けます）。実装の参照元であり、アプリの動作には不要です。

全9画面はPC幅(1280px)とスマホ幅(390px)の両方で、**実際のReactコンポーネントを実データで
レンダリングして検証済み**です（`harness/` が検証用ハーネス。開発補助であり配布物の動作には不要）。
検証内容: JSランタイムエラーゼロ / 横スクロールはみ出しゼロ / 全ページ描画成功。

配色の設計方針:

- カテゴリの識別は**文字（A/H/R/N/T/C/M）が主エンコード**で、色は補助。色覚特性に依存しません。

### 過去データの遡り入力（現在地の再測定）

CFEの初期値は「800mPB + 1.5秒」で置かれる。PBが古く走力が落ちている場合、
基準タイム = CFE×(1−w) + 目標×w が全ペースの親であるため、
設定ペース全体が実力を上回る。これを実測で測り直すのが `/past` 画面。

入力できるもの:

- レース / タイムトライアル（400・600・800・1000・1500・3000m）
- ポイント練習（カテゴリ・1本の距離・各本のタイム・レスト）
- ジョグ・持続走（距離・時間・平均HR）

換算の考え方（`src/lib/core/backfill.ts`）:

- 他距離 → 800m は**本人のPB関係**を優先する。
  400m は「800m = 400m×2 + 本人の換算差」、1500m は「800m = (1500m − 本人の差) ÷ 2」。
  一般式（Riegel）は本人PBが無い場合のフォールバック。800m選手は同じ800mタイムでも
  型によって400m/1500mとの関係が大きく違うため、一般式を当てると型の分が丸ごと誤差になる。
- ポイント練習 → 800m は生成側の式（距離 × GRP × カテゴリ比率）を逆算する。
  RPE6未満は「全力ではない」として能力推定に使わない（負荷には反映する）。
  標準より長いレストは過大評価になるため穏やかに割り引く。
- ジョグ・持続走は**800m能力の推定には使わない**。LT推定とACWRの下地になる。
- 重み = 信頼度 × 直近性（半減期28日）。12週より古いデータは対象外。
- 暑熱下のデータは実力を過小評価するため除外する。ただし判定は件数ではなく
  **重みの合計**で行う（件数で見ると、涼しい日の800mレース1本が
  暑熱下の練習からの外挿と同列に扱われ、平均に引きずられる）。

守っている制約:

- 過去データを通常の結果記録ループ（`processResult`）に流さない。
  CFE更新は1回±1.5秒（レース±3秒）のガードレールを持つため、
  過去3ヶ月ぶんを順に流すとガードレールが件数ぶん適用されて意味を失う。
  現在地の算出は全件を入れ終えてから1回だけ行う。
- 算出結果は自動適用しない。どの実測が何秒として効いたかの内訳を出し、
  本人が承認して初めてCFEに反映する。
- 過去データから作られたセッションはルールエンジンの評価対象外
  （過ぎた日の構成は今から直せない）。ただし負荷（ACWR）には算入し、
  過去の構成そのものは `diagnosePastStructure` が別枠で診断する。

#### 一括入力ぶんが「入るところ」と「入らないところ」（P-2 / P-3）

一括入力から作られた `SessionResult` に構造化記録（`interval` / `continuous`）が
入っていなかったため、**それを前提にした下流が、エラーも出さずに空になっていた**。
消費側で条件を緩めるのではなく、`backfill.ts` の `toSessionAndResult` が
通常の記録と同じ構造を持たせるように直した。1か所直せば下流はすべて直る。

あわせて `rowToPastEntry` が落としていた設定タイムとレストも運ぶようにした。
設定タイムが無いと「設定に対してどうだったか」が出せず、
本数だけ数えても週次レビューにもM-2にもならない。

| 消費側 | 一括入力ぶん | 理由 |
| --- | --- | --- |
| 週次レビュー（M-11） | **含める** | その週にやったことの要約。入力経路で変わってはいけない |
| 同一処方の経時比較 | **含める** | 同じ処方を何回こなしたかの比較。過去ぶんが無いと2回に届かない |
| 設定の調整（M-2 / executionSamples） | **含める** | 直近3回の実測が材料。過去ぶんを外すと材料が空になる |
| ジョグの心拍（M-2 / jogEfficiency） | **含める** | 同じペース帯の心拍比較。ベースライン側はほぼ過去ぶん |
| 負荷・ACWR | **含める**（従来どおり） | 体にかかった負荷は入力経路と無関係 |
| 600m通過（M-8） | **含める**（従来どおり） | `PastEntry` を直接見ているので元から効いていた |
| 制限因子（M-7） | 影響なし | プロフィールとPBから判定しており、結果を見ていない |
| ルールエンジンの評価 | **外す**（意図的） | 過ぎた日の構成は今から直せない。診断は `diagnosePastStructure` が別枠で行う |
| CFEの逐次更新 | **外す**（意図的） | ガードレールが件数ぶん適用されて意味を失う。`assessFitness` で1回だけ算出する |

「外す」の2つは設計判断なので変えない。それ以外で空になっていたら不具合。
`tests/backfillStructured.test.ts` が **実際に一括入力を通してから** 下流を確かめている
（コードがあるかではなく、実データで発火するかを見る）。

#### 変換を直しても、既に入っているデータは直らない（Q-3）

`toSessionAndResult` は**取り込んだ瞬間にしか走らない**。
セッションと結果は取り込み時に作って保存するので、変換の中身を直しても
すでに端末に入っているぶんは古い形のまま残る。
上の修正を入れたあとも「週次レビューが0本のまま」だったのはこれが理由で、
コードは直っていたが、既存データには届いていなかった。

`rebuildPastDerived` が、保存済みの `PastEntry` からセッションと結果を作り直す。

- ホームを開いたときに1度だけ自動で走る（KVの `migration:past-derived` で管理）。
  本人が設定画面を開くまで壊れたままなのは、直っていないのと同じなので自動にした。
  実測値を書き換えないので、この作り直しについては確認を取らない。
- 「データ管理」からいつでも実行できる。何件作り直したかを出す。
- **設定タイムだけは戻らない。** 取り込み時に捨てていたので、元の本文が残っていない。
  推測で埋めないため、戻せない件数を数えて画面に出す。
  設定に対する評価が要る練習は入れ直してもらう。

変換の中身を変えたときは `PAST_REBUILD_VERSION` を上げること。上げないと作り直しが走らない。

### S-7 / S-8 生成の漸進モデル

**以前はカテゴリごとに固定の文面を返していた。** 高乳酸なら常に `300m × 5 r5分` で、
変わるのは設定タイムだけ。週が進んでも、直近の出来がどうでも同じ内容が出ていた。
`src/lib/core/progression.ts` が内容そのものを組み立てる。

採用した原則（出典ではなく、このアプリが採る方針）:

1. **量 → 密度 → 強度 の順に上げる。** 3つを同時に上げると、
   何が効いたのかも何がきつかったのかも分からなくなる
2. **3週上げて1週落とす（3:1）。** 4週目は本数を戻す
3. **レースに近づくほど特異的にする。** 高乳酸は Base で200m、Build以降で300m。
   レストは Build 5分 → Specific 4分と詰め、レース終盤の状況に近づける
4. **土台期に高乳酸を積まない。** 深く入る種目なので、Base では短く少なく

直近の実行状況を**内容そのもの**に反映する（M-2は設定タイムだけを動かす）:

| 直近の傾向 | 生成の動き |
| --- | --- |
| 設定より遅い（ease） | 本数 −1・レスト +15%。**量を増やさず実行できる形に戻す** |
| 設定より速い（tighten） | 有酸素高強度は本数 +1。高乳酸・中距離特異的は本数を据え置く |
| ACWR > 1.3 ＋ 疲労・未達の実測あり | 本数を戻す。ACWR単独では内容を変えない |

**テーパー期は漸進モデルの対象外。** レース前の量は M-6 と RULE-09 が決めており、
ここで別の根拠から本数を動かすと、2つの仕組みが同じ週の量を取り合う。

#### 同じ刺激内のセッション形式

`threshold / cv / high_lactate / race_economy / modeling` は、カテゴリごとに複数の
決定的な候補を持つ。ランダムには選ばず、フェーズ、進行段階、選手タイプ、
直近28日の同カテゴリ履歴、完遂・RPE・翌日の脚、直近負荷を点数化して選ぶ。
選手タイプは候補を除外する固定ラベルではなく、同程度の候補を並べる小さな重みだけに使う。

同一テンプレートの14日以内の再使用には減点を付けるが、比較や進行確認に同じ処方が必要なら
理由つきで再使用できる。14日・28日は安全性の理想値ではなく、短期の単調な反復を避けつつ
4週間の履歴を判断材料にする運用窓である。同形式で未達・RPE 9以上・翌日の脚が重い状態が
2回続けば、段階を上げず別形式を優先する。安定完遂が2回続いた場合だけ次段階を優先する。
形式を切り替えた週は、本数・速度・レストの漸進を同時に掛けない。一度に変える変数を
原則1つにして、次の実施結果から何が影響したかを追えるようにする。

選択結果は `Session.generation` にテンプレートID、`variationGroup`、進行段階、理由、
代替候補、信頼度として保存する。任意フィールドなので旧データをそのまま読め、
SQLite / IndexedDB / exportBackup / Supabase snapshot に同じSession JSONとして流れる。
セッション詳細は保存された理由を表示するため、説明文と実際の判定がずれない。

### S-9 進め方を2案出す

次のポイント練習について、**どちらも成立する2案**を出して選ばせる。
片方が明らかに劣る案だと選ぶ意味が無く、「おすすめ」を押すだけの操作になる。
状態によって2案の中身そのものを変える:

| 直近の傾向 | 2案 |
| --- | --- |
| 守れていない | 「本数を減らす」／「レストを伸ばす」（どちらも引く方向） |
| ちょうど良い | 「量を増やす」／「密度を上げる」 |
| 余裕がある | 「1本増やす」／「レストを詰める」 |

推奨は制限因子（M-7）で決める。後半の維持が課題なら密度側
（不完全回復での反復が終盤に直接効く）、そうでなければ量側（失敗しにくい）。
**推奨しない側も理由つきで出す。**

**案そのものは保存しない。** 選んだ結果を既存の `Session` に書き込むだけにする。
案を保存すると「どの案が生きているか」という状態が増え、
M-2・M-6・ルールエンジンと取り合いになる。書き込みは `editSession` を通すので、
ルール検査は従来どおり効く。

「量を増やす」は選択日から**14日間**を対象にし、最大3件までの未実施・自動生成メニューへ
保存反映する。ジョグ/ロング走はペースを変えず5分追加し、CV・閾値・神経系は
本文から本数を確実に読める場合だけ1本追加する。週全体の距離・時間増加は10%以内に抑える。
14日は次の2週間へ行動を反映しつつ、次の回復週やフェーズまで設定を持ち越さないため。
10%は「安全な理想比」の断定ではなく、既存RULE-17の15%注意域へ一度の操作で入らないための
操作上限である。完了済み、過去、手動変更、固定、回復、Taper、
`high_lactate / modeling / race_economy` は対象外。高乳酸・中距離特異的の本数は
「量を増やす」で機械的に増やさない。

置き場所はTODAY。今日がポイント練習でなければ次のポイント練習を対象にし、
対象の決め方は「設定の調整案」と同じにする（別々に決めると2枚のカードが
違うセッションの話を並べることになる）。

### S-6 他の選手のメニューを取り込む

トップ選手のメニューをそのまま真似ると、**構造は正しいのに設定だけ速すぎる**という
一番まずい形になる。守れない設定を繰り返しても、狙った刺激は入らない。

`src/lib/core/athleteConvert.ts` が、その選手の**相対強度**を自分に当て直す。

```
自分の設定 = 相手の設定 × (自分のCFE ÷ 相手の800mPB)
```

カテゴリの標準比（`GRP_RATIOS`）を使わないのはなぜか。
標準比は「そのカテゴリなら普通このくらい」という一般値で、
その選手が実際にどの強度でやっていたかは分からない。
他人のメニューを借りる目的は**その人の組み立てを再現すること**なので、
実際にやっていた相対強度を保つほうが目的に合う。
換算した設定は `CustomMenu.targetSec` に入れ、生成時は標準比より優先する。

**限界を隠さない。** 次の場合は必ず画面に出す。

- 800mPBの差が10秒を超える（タイプも練習の意味も変わってくる）
- 100m未満・1200m超（800mから離れるほど比が当てにならない）
- 設定が書かれていない（構造だけ取り込む。**推測で埋めない**）

換算値は実測ではないことも併記する。1回やってみて合わなければ動かす前提の値。
誰のメニューかは `sourceAthlete` に残す。残さないと、あとで数字の出どころが分からなくなる。

### プラン再生成と予定の識別

自動生成セッションは `s-plan-YYYY-MM-DD-am|pm` の安定IDを使い、
`origin: "generated"` を保存する。ラウンド間回復もレースIDと日付からIDを決める。
毎回時刻ベースのIDを作ると、端末内のupsertにもスナップショット同期にも同じ予定だと
伝わらず、再生成のたびに別レコードとして増えるため。

再生成で置き換えるのは、本人が編集していない自動生成の未実施予定だけ。
`origin: "manual"`、`userEdited: true`、完了・中止済み、過去入力、旧固定枠は残す。
旧データには `origin` が無いため、`s-user-*` は手動として保護し、
それ以外の非固定 `planned` だけを旧自動生成予定として置き換える。
残した手動・本人編集予定と同じ日・時間帯には、新しい自動予定を重ねない。

目標とレースはサービス層で1つの保存単位として扱い、保存後にStoreから読んだ実体を
画面へ返す。通過点レースのIDは配列位置ではなく、追加時に決めたIDを維持する。
RaceのJSONには着順ボーダー `borderPlace` とタイムボーダー `borderTimeSec` を保存する。
どちらも任意フィールドなのでDB migrationは不要で、旧Race JSONもそのまま読める。

ボーダーの正規化（`normalizeRaceBorders`）は着順 `>= 1`・タイム `> 0` だけを残し、
それ以外は未入力に戻す。`Number.isFinite` は 0 と負を通すため、これが無いと 0 が保存される。
0 が入ると `planHeatPace` の `race.borderTimeSec ?? goalTargetSec + 2` が
0 を nullish と見なさず、予選の通過目安が0秒基準（−0.5秒）になる。
画面には値が出たまま中身だけ壊れるので気づけない。
着順を `Math.max(1, ...)` で1着へ丸めないのは、丸めると「0が入ってきた」のか
「1着通過」なのかが後から区別できなくなるため（読めなかったものは推測で埋めない）。

同じ規則を `importBackup` の races にも通す。復元は `saveGoalAndRaces` を経由せず
`repo.saveRace` を直接呼ぶので、他端末が書いた壊れた値やSupabaseのpullが素通りするため。

### 統合（merge）で本人のデータを守る

`mergeById` は同じIDを無条件で上書きしていた。同期のpullも競合時の「両方を残す」も
この経路を通るので、クラウドに残っていた古い自動生成予定が、この端末の
完了済み・本人編集・固定枠・手動追加・遡り入力を消していた。
「両方を残す」と書いてあるボタンが片方を消すのは、表示と挙動の食い違いでもある。

`mergeById` に `keepExisting` を渡せるようにし、`importBackup` の sessions では
`isOwnedByAthlete`（`completed` / `skipped` / `userEdited` / `isFixed` / `backfilled` /
`origin === "manual"` / `s-user-*`）に当たるものを残す。判定の材料は `regeneratePlan` の
置き換え判定と同じで、旧データに `origin` が無いため `s-user-*` を手動として保守的に扱う。
**迷ったら守る側に倒す。** 消えたデータは取り返せないが、残ったものは後から消せる。

`replace` では保護しない。本人が競合画面で「クラウドを優先」を選んだ経路だから。

残した件数は `RestoreReport.kept` で返し、`warnings` にも文章で入れる。
**守ったことを黙っていると「同期したのに反映されない」ように見える。**
データ管理画面と同期画面の両方で表示する（`/api/backup` の応答は `{ ok, report }` の形で、
`report.warnings` を取り違えると黙って空になる）。

### OAuth 復帰は `?sync=1` の残存を前提にしない

実機で「サインインは成功するがホーム画面に戻ったまま同期画面へ遷移しない」を確認した。
`app-shell.tsx` の受け取りは、戻り先の `?sync=1` というクエリが残っていることを前提に
同期画面へ戻す判断をしていたが、このクエリは自前では守れない。
Supabase の **Redirect URLs** にこのアプリのURLを登録していないと、Supabase は
指定した `redirect_to` を無視して **Site URL** へ飛ばすため、クエリごと落ちる
（横取り耐性のための仕様で、FORGE側の不具合ではなく設定依存の外部要因）。
結果、トークンは保存されるのに画面だけホームに居座っていた。

`captureAuthRedirect` が何か拾えた時点で、それは必ず `signInWithGoogle` が発行した
`redirect_to` からの戻りである（他にこのURLへ来る経路が無い）。したがって
`?sync=1` の有無を問わず同期画面へ戻してよい。判断を `sync.ts` の
`authRedirectLanding` という純関数に集約し、`app-shell.tsx` はそれを呼ぶだけにした
（判断を通信・DOM操作から切り離してテストできるようにするため）。

### Supabase Storage の保存先を利用者ごとに分ける

以前は全利用者が同じ `forge/snapshot.json` を共有していた。Google OAuthでサインイン
できる者（想定外の第三者を含む）が同じファイルを読み書きできてしまうため、
利用者ごとに `forge/<uid>/snapshot.json` へ分ける。

`uid` はセッションの `accessToken`（Supabaseが発行したJWT）の `sub` クレームから
取り出す（`sync.ts` の `jwtSubject`）。署名検証はしない。ここでの用途は保存先パスの
組み立てだけで信頼境界には使わないため——実際の可否は Storage 側の RLS
（`(storage.foldername(name))[1] = auth.uid()`）が、リクエストごとに検証済みの
トークンで判断する。改ざんされた `sub` を渡されても、他人のフォルダには RLS が拒否する。

`accessToken` から `uid` が取り出せない場合（壊れたセッション等）は、通信せず
明確なエラーにする。共有パスへの黙ったフォールバックは、分離の意味を失わせるため
絶対にしない。

RLSポリシー（Supabase側で適用）は `docs/FORGE_REQUIREMENTS.md` の 2.2.4 を参照。

#### 「未作成」判定は複数のコードを受け入れる

新しい個人用パス（`forge/<uid>/snapshot.json`）への初回push（実機・2026-07-30）で、
実際のSupabaseは `code: "NoSuchKey"`（S3互換のオブジェクト未存在コード）を含む本文を
返した。`isMissingSnapshot` は `payload.code` を最優先で見て `"not_found"` とだけ
比較していたため、`"NoSuchKey"` と一致せず「初回同期」ではなく本物のエラーとして
扱ってしまっていた（`error` フィールドには従来どおり `"not_found"` が入っていたが、
`code` を優先していたため見なかった）。

`code` と `error` のどちらかが未存在を示していれば十分とし（`isNotFoundCode` が
`"not_found"` と `"nosuchkey"` の両方を認める）、`message`（`"Object not found"`）を
主な決め手として残した。テスト環境で使っていた仮のレスポンス形（`code`フィールドが
無い）では気づけなかった不具合で、実機での初回pushで初めて顕在化した。

### 3-1 曜日の優先・固定設定

既存の `slots` と `enabled` を残したまま、曜日ごとの `modes` を追加する。
旧データに `modes` が無い指定枠は従来どおり `fixed` として読む。

1. レースと競技日程
2. 故障・体調・安全性
3. テーパーと回復
4. 高負荷練習の間隔
5. 週全体の負荷
6. `fixed`
7. `preferred`
8. 自動生成

`preferred` は週のメニュー数を増やさず、同じ週の既存枠と交換する。
交換後に高負荷が連日になる場合は希望を見送り、自動配置を残す。
`fixed` は原則その曜日を保持し、生成したSessionにも固定元を残すが、
レース前・テーパーの安全処理で内容が変わった場合は固定扱いにしない。
固定同士が安全ルールを破る場合は、設定画面とルールエンジンが警告・変更案を出す。

### 高負荷分類と「質練習」の扱い

「質練習」は画面上のポイント練習という総称に留め、安全判定では一括カテゴリとして
使わない。保存形式の `SessionCategory` は後方互換性のため維持し、
`trainingClassification.ts` で次の主負荷へ変換する。

- `high_lactate` → 高乳酸・解糖系
- `race_economy` / `modeling` → 中距離特異的
- `cv` / `threshold` → 有酸素高強度
- `neural` → 神経・スプリント
- `aerobic` → 低〜中強度有酸素
- `off` → 完全休養・回復
- 補強は `StrengthSession` のまま筋力・補強として別管理

通常週は「2回まで」と一律に止めない。高乳酸・中距離特異的が週3日以上、
または全高負荷が週4日以上ならERROR、全高負荷が週3日ならWARNとする。
同日の複数セッションは週回数を水増しせず、高負荷「日」で数える一方、
同日・連日の配置はRULE-03で個別に検出する。

RULE-04の回数・レベルは予定構成から決めるが、実施済みの対象セッションがある場合は、
RPE・主観強度・未達/中止・翌日の脚の状態と、その週の日次疲労シグナルを警告理由へ
併記する。未実施の予定を実績として扱わない。RPE 8と疲労4/5は新しい理想値ではなく、
既存の設定調整・伝播処理と同じ運用境界であり、警告回数の基準自体は変えない。

短い完全回復の坂ダッシュ・流しは高負荷日に数えない。ただし `neural` として
保存されていても、300m反復、合計1200m超、10秒超の反復、または完全回復でない
10本超が本文から明示的に読める場合は、カテゴリ名だけで軽負荷にせず警告対象にする。
200m・1200m・10秒・10本は安全な理想値ではなく、自動生成している短い神経刺激と
スピード持久系の取り違えを検出するための運用境界である。

## Apple ヘルスケア連携

HealthKit の API は iOS ネイティブアプリ専用で、Safari / PWA からは呼び出せません
（プラットフォームの制約であり、コードで回避できません）。そのため本アプリでは
iPhone 標準の「すべてのヘルスケアデータを書き出す」で出力されるファイルを取り込む方式です。

取り込んだデータは表示のためではなく、次の変換のために使われます:

- 睡眠・安静時心拍・HRV → 疲労シグナル（4-5-8）
- ランニング（3km以上）→ 用途不明のFitnessMarkerとして保存（LTへは自動採用しない）

主観入力（脚の疲労・モチベーション）はセンサー値で上書きしません。
自転車・水泳などランニング以外のワークアウトはFitnessMarkerにしません。
ランニングもHealthKitだけでは閾値走・回復ジョグを区別できないため、距離だけでLT走と推測しません。

### R-2 起動画面

起動時の約2.8秒に、読める情報を**1つだけ**出します。
出すのは目標までの距離（レースまでの日数と、目標タイムとの差）。
起動のたびに見る場所なので、毎日少しずつ動く値が向いています。
蛍光グリーンの軌道が800mの2周を描き、ゴール発光、FORGE、サブタイトル、
動的なレース情報の順に出ます。発光はゴールの1回だけで反復させません。

技術的な制約が2つあります。

- **スプラッシュは `bundle.js` の読み込み前に描画されるので、その場ではDBを読めません。**
  前回の起動時に `app/components/splash-cache.ts` が localStorage へ書いた値をまず読みます。
  React起動後は `/api/dashboard` の最新値を同じ画面へ通知して差し替えます。
  文字列の組み立てはTS側（テストあり）に置き、`index.html` でやるのは
  「保存したレース日から今日までの日数を引く」だけにしています。
  何日も開かなかったときに古い日数をそのまま出さないためです。
- **`index.html` のスクリプトは `bundle.js` と同じスコープです。**
  どちらもクラシックスクリプトなので、トップレベルの `let/const` を共有します。
  素で `const t` と書くと minify後の1文字変数と衝突し、
  スクリプト全体が落ちてスプラッシュが消えなくなります（アプリは動いているのに真っ暗に見える）。
  必ずIIFEで囲み、変数名も1文字を避けます。

初回起動（保存が無い）では「データ読込中」、読込後もレースが無ければ「レース未設定」と出します。
E2Eが保存あり・なしの両方を確認しています
（`bundle.js` を止めてスプラッシュを固定し、スクリーンショットを `shots/` に残します）。

**アニメーション完了とアプリ初期化完了の両方を待ちます（S-1）。**
PWAはIndexedDB読込・API shim・React描画後に `forge:app-ready` を通知し、
通常時は最低2800msを確保します。4500msを超えたら認証・保存データを読込中だと明示し、
9000msで再読込ボタンを出すため、無言の永久ロードにはなりません。
初期化失敗時はエラー画面と再読込操作を出し、オフラインならその状態を説明します。
`prefers-reduced-motion` では軌道アニメーションを止め、650msの短い静止表示に切り替えます。
Next.js版は `LaunchSplash` が同じ表示とdashboard読込を担当します。

### 重なりの規則（z-index）

| 層 | z |
| --- | --- |
| 下部タブバー | 30 |
| FAB（＋） | 50 |
| 確認ダイアログ | **60** |

**確認ダイアログは必ずFABより上に置くこと（S-5）。**
同じ z だと、DOMで後に来るFAB（`AppShell` が `main` の後に描画する）が上に乗ります。
スマホではダイアログが下寄せなので、画面の高さとセーフエリアの組み合わせによっては
確認ボタンとFABが重なり、**見えているのに押せなくなります**。

E2Eは「ボタンが覆われているか」ではなく
**「ダイアログを開いている間、FABが暗幕の裏に回っているか」**を見ています。
実際に重なるかは端末ごとに変わるので、座標の重なりを条件にすると
E2Eの画面幅でたまたま重ならないときに素通りするためです。

## S-11 同期（Googleログイン＋Supabase）と Appleヘルス

**設定しなければ何も起きません。** アプリはこれまでどおり端末の中だけで動きます。
同期は足すだけの機能で、使わない選択がそのまま成立します。

### 方式: スナップショット同期

M-12 の書き出し（`BackupFile`）をそのままクラウドに置きます。
レコード単位の同期にしないのは、全エンティティに更新時刻と削除の墓標が要り、
`Store` の51メソッド × 2実装に同じ変更を入れることになるためです。
利用者は1人・端末は1〜2台なので、そこまでの精度に見合いません。

**黙って上書きしません。** どちらが動いたかは「前回同期した状態」から判断します。
時刻の新しさだけで決めると、時計がずれた端末の古いデータで新しいデータを潰します。
両方が動いていたら必ず選ばせます（統合／この端末を優先／クラウドを優先）。
判断は `src/lib/core/sync.ts` にあり、**ネットワークを持ち込んでいません**（テスト可能）。

SDKを入れず REST を直接叩いています。使うのは「サインイン」と
「1つのファイルの読み書き」だけで、数百KBのSDKは起動時間に直接効くためです。

### Supabase の準備（1回だけ）

1. https://supabase.com でサインアップ → **New project**（無料枠で足ります）
   - Region は **Northeast Asia (Tokyo)**
2. **Storage** → New bucket → 名前を `forge`（Private のまま）
3. bucket のポリシーを追加（自分のファイルだけ読み書きできるようにする）
   - Storage → forge → Policies → New policy → *For full customization*
   - 対象roleは `authenticated`
   - `SELECT`: `using (bucket_id = 'forge')`
   - `INSERT`: `with check (bucket_id = 'forge')`
   - `UPDATE`: `using (bucket_id = 'forge')` と `with check (bucket_id = 'forge')`
   - 初回アップロードにも、Storage APIが保存した行を返すための`SELECT`が必要。
     `INSERT`だけでは「new row violates row-level security policy」で失敗する。
   - 上書き保存（`x-upsert: true`）には`SELECT`・`INSERT`・`UPDATE`の3つが必要。
4. **Authentication → Providers → Google** を有効化
   - Google Cloud Console で OAuth クライアントID（ウェブ）を作る
   - 承認済みリダイレクトURIに、Supabaseが表示する
     `https://xxxx.supabase.co/auth/v1/callback` を登録
   - クライアントIDとシークレットを Supabase に貼る
5. **Authentication → URL Configuration** を設定
   - Site URL: `https://rio01100801-gif.github.io/trainmiddle/`
   - Redirect URLsには、アプリの **設定 → 同期 → 接続診断** に表示される
     `OAuth redirectTo` をそのまま追加する
   - 現在のPWAでは、起動URLに応じて次のどちらかになる
     - `https://rio01100801-gif.github.io/trainmiddle/?sync=1`
     - `https://rio01100801-gif.github.io/trainmiddle/index.html?sync=1`
   - Next.js版も使う場合は、そのoriginの `/sync` も追加する
     （開発時の例: `http://localhost:3000/sync`）
   - Supabaseは許可されていない `redirect_to` を使わずSite URLへ戻すため、
     ここが不足するとサインイン後にFORGEホームへ戻る
6. **Settings → API Keys** から次の2つを控える
   - Project URL（`https://xxxx.supabase.co`）
   - **Publishable Key**（`sb_publishable_...`）

アプリの **設定 → 同期** に6の2つを入れて保存し、Googleでサインインします。

⚠️ **Secret Key / service_role キーは絶対に入れないこと。**
あればRLSを迂回してデータを読めます。Publishable Key（旧anon key）は
公開クライアント用なので端末に置いて構いません。

設定は練習データとは別に、現在の実行環境の `localStorage` へ保存します。
保存時に空白・改行・全角英数記号・URL末尾スラッシュを正規化し、
書いた値を再読込して一致した場合だけ成功表示にします。
接続先を変えた場合は、別プロジェクトのユーザーJWTを再利用しないよう、
サインイン状態と最終同期情報を解除します。REST通信は操作ごとに最新設定から作るため、
module scopeに古いSupabaseクライアントを保持しません。

「接続をテスト」は `/auth/v1/settings` のHTTP成功だけでなく、
Supabase Auth設定のJSONであることまで確認します。画面にはキーを出さず、
使用中ホスト・HTTP status・タイムアウト・CORS・DNS/通信失敗の種別を表示します。

⚠️ iOSのホーム画面から起動したPWAでは、サインインの遷移先がSafariで開いて
**PWAに戻ってこないことがあります**。PWAとSafariはストレージが別なので、
その場合はPWA側でもう一度設定・サインインが要ります。
Safariタブとホーム画面PWAの両方で **接続診断の実行環境・origin・使用中ホスト**
を確認してください。

URLを間違えたあとも古い値が疑われる場合は、**設定 → 同期 → 接続設定を消す**
を1回実行し、PWAを完全に閉じて開き直してから正しい値を保存します。
この操作が消すのはSupabase設定・サインイン状態・最終同期情報だけで、
IndexedDB内の練習データは消しません。Service Worker cacheにも設定値は入りません。

認証はクライアントだけで完結するSupabaseのimplicit flowです。
成功時のaccess token / refresh tokenはURL fragmentから受け取って直ちにURLから除きます。
PKCEの認可コードを使っていないため、サーバー側のcode交換処理はありません。

## 設計上の重要な仕様

- **ペースはすべて内部で秒として保持**し、表示時に整形します。
- **有酸素系の設定は実測（FitnessMarker）から算出**します。実測が無い間は「推定値」と明示されます。閾値走やペース走の結果を入力すると精度が上がります。
- **CFE（推定800mタイム）がすべてのペースの親**です。結果を入れるとCFEが更新され、未実施の全特異的セッションのペースが基準タイム（CFEと目標の中間・フェーズで重み変化）から自動で組み直されます。
- **下げる方向の指示は常に上げる方向に優先**します（オーバーリーチの代償 > 機会損失の代償）。
- **固定セッション（チーム練習等）はルールエンジンが動かしません**。回避不能な違反は「当日の対処案」つきで警告のみ出します。
- 疲労・赤信号・故障による質練習のスキップは**後ろ倒しせず削除**します（負債の二重化防止）。
- 「きつい練習＝良い練習」という評価軸は実装していません。経済走は「同じ設定でより楽になったか」で評価します。

### セッション準備度スコア（仕様書外の追加機能）

ダッシュボードの「今日のメニュー」に出る0〜100のスコアです。**その練習がどれだけキツいかではなく、
設定どおりの質を出せる条件が揃っているか**を表します。100点からの減点方式で、加点要素はありません
（RPEの高さや達成感を加点しない、という仕様書8の原則を崩さないため）。

減点は 疲労シグナル（黄 −10 / 赤 −45）、ACWR（1.3超 −4 / 1.5超 −10）、前回質練習からの間隔
（中1日未満 −15 / 中1日 −5）、直近3本の未達（各 −3〜−6）、暑熱（−8）、ERROR級違反（−25）。
内訳は必ず画面に表示され、ブラックボックスの数字は出しません。赤信号のときはスコアに関わらず
「質を入れない」で確定します（RULE-12・SKIP-02と判断が食い違わないようにするため）。

### LT・CV・有酸素処方の根拠

- `FitnessMarker.purpose`で閾値走、テンポ、CV、レース、ロング、イージー、回復、不明を区別する。
  旧データは任意フィールドのまま読み込める。手入力の旧マーカーは低信頼度で互換採用するが、
  `past-fm-*` / `ah-*` の用途不明な自動取込はLTへ採用しない。
- LTは直近8週、半減期14日、3本以上なら中央値±25秒/kmの外れ値除外という既存方式を維持する。
  実測本数と用途の明示数から低・中・高の信頼度を返す。
- CVは直近8週に異なる3000〜5000mのレース/テストが2距離以上ある場合、
  距離-時間直線の傾きから算出する。LT以上に遅い、またはLTより20秒/km超速い結果は
  条件差・入力違いの可能性があるため採用せず、従来のLT−6〜8秒/kmへ戻す。
  20秒は理想差の断定ではなく、異常値を黙って処方へ流さない監査境界。
- `Session.aerobicPurpose`で通常有酸素・回復・ロング・イージーを区別する。
  回復日はペースを達成目標にせず、会話可能・RPE 2〜3を優先する。

### ACWRの扱い

ACWRには実施結果、または結果詳細が無い旧`completed`だけを入れ、未実施の予定は入れない。
28日中の記録日数と信頼度を併記する。0.8 / 1.3 / 1.5は危険度や安全域ではなく、
本人の過去28日平均に対する変化を説明する表示境界である。

ACWR単独でプランを軽くしない。1.3超に加え、直近の黄/赤信号、疲労4以上、睡眠2以下、
未達・中止・翌日の重い脚のいずれかがある場合だけ、生成の漸進を止める。

### 高乳酸間隔と個人補正

標準間隔は5日のまま。従来の「モデリング期なら3日間隔を自動許可」は使わない。
4日は両方が高速区間900m以下・完全回復・低リスクで、前回が完遂、RPE 8以下、
翌日の脚が重くなく、間の日次記録にも疲労懸念が無い場合だけWARNの個別検討候補にする。
900mは安全値ではなく、現行標準高乳酸300m×5（1500m）の60%以下を拾う運用境界。
条件が読めない場合や記録不足時は5日へフォールバックする。

設定補正は同カテゴリだけでなく同じ反復距離の直近3回を比較する。締める方向は、
全回達成・RPE 8以下・翌日の重い脚なしが揃う場合だけ。未達・中止・高RPE・重い脚は
緩める材料にし、適用した処方は`userEdited`として再生成から保護する。

### D-3「前回と同じ」の設計

直近の**同じカテゴリ**の記録を初期値として読み込みます。距離や本数が違っていても
「前回の入力値」として使う価値があるので一致条件は厳しくしていません。
代わりに事故を防ぐ仕掛けを2つ入れてあります。

1. **どのセッションから読んだかを必ず画面に出す**（例: 「07-28 高乳酸セッション の内容を読み込みました」）。
   出典が見えないまま登録されると、そのままCFEの更新に流れてしまうため。
2. **実施タイムだけは読み込まない**。本数・距離・レスト・RPEは前回の値を入れますが、
   実施タイムは「前回の結果」であって今日の結果ではないので、必ず空のままにします。

カテゴリが違うものは絶対に候補にしません（高乳酸の記録を経済走に持ってこない）。

### D-3 メニューのテンプレート保存

記録画面の「この内容をメニューとして保存」で、**自作メニュー（3-2）として登録**されます。
テンプレート専用のストアは作っていません。同じ「よく使うメニュー」を2箇所で持つと
どちらが正なのか分からなくなり、生成側がどちらを見るかも曖昧になるためです。
保存したものは「メニュー設定」から確認・一時停止・削除できます。

### 実装できなかった項目

現時点ではありません。指示書のフェーズA〜Eはすべて実装済みです。
アプリ全体としての未実装は、アカウント・クラウド保存（バックエンドが必要）、
Apple Health の自動同期（iOSネイティブアプリが必要）、チーム管理の3つです。

### 設計上の判断（指示が競合した箇所）

FORGEブランド指針は下部タブを Home / Calendar / Analysis / Settings と定義していますが、
改修指示書は 記録タブの再構成（フェーズD）を前提にしています。
両立させるため、**下部タブは ホーム / カレンダー / 記録 / 分析 の4つ**とし、
**設定はヘッダー右のアイコン**（B-1の指示）に置きました。
タブ数は4つのままで、記録への到達がメニュー階層に沈まないことを優先しています。


## 改修指示書v3（F〜I）への対応

### F-1 時間・ペースの相互補完

練習日誌には「51分 平均4:40」のように距離が書かれていない。距離を必須にすると
電卓を叩くか入力を諦めることになるので、**距離・時間・ペースのうち2つあれば
残り1つを埋める**。3つとも入力されている場合は上書きせず、3%以上ずれていれば
警告だけ出す（どれが正しいかはこちらでは判断できないため）。

時間は `51` `51:30` `1:05:00` `51分` を、ペースは `4:40` `4:40/km` `@3:50` を受け付ける。
単位なしの数値は、時間なら「分」、ペースなら「秒/km」として読む（実態に合わせた非対称）。

### F-2 一括入力の解釈規則

完全ルールベース。同じテキストを貼れば必ず同じ解釈になる。
実際の練習日誌（タブ無し・半角スペース1個区切り・実施タイムが次の行・
括弧に設定と区間ラップが混在）をそのまま通せる。

- **行の切り出し**: 先頭トークンだけを日付として切り、残りは本文として扱う。
  タブや2連スペースを列区切りに要求すると、実際の日誌は1列も切り出せない
- **継続行**: 先頭が日付でない行は前の行の続きとして結合する
  （`42 1:26 1:25` のように実施タイムだけの行がよくある）
- **予定と実績の分離**: 本文にタブ・全角空白・2連スペースがあれば後ろを「結果」とみなし、
  そちらを優先する。`ジョグ40〜50分（予定）／51分（実績）` で予定の50分が実績を
  押しのけるのを防ぐ
- **処方の除去**: `300(42)＋600(1:26)` の 300 や 600 は距離であって実施タイムではない。
  除去せずに数値を拾うと、距離と設定が実施タイムの列に紛れ込む
- **レスト記述**: `r15min` `r200jog` `R12min`。r と数字の間に空白を許してはいけない。
  許すと `R12min 41.6` の `R  41` まで飲み込み、実施タイムの1本目が消える
- **カテゴリ**: **設定タイムがあれば一意に決まる**。
  設定ペース ÷ 現在のGRP の比率で分類する
  （〜102% は高乳酸/モデリング、〜112% は経済走、それ超は CV/閾値）。
  同じ 1000m×4 でも設定が3:15/kmならCV、2:50/kmなら高乳酸になるので、
  距離だけでは決まらないが設定があれば決まる。設定が無い場合だけ人間に選ばせる
- **複合区間**: `300(42)＋600(1:26)＋600(1:26)` は本数の多い距離（600m）を代表とし、
  そのぶんだけを能力推定に使う。混在していることは画面に明示する
- **補助の分離**: `8000mペース走＋流し4本` の流しは主セッションから切り離す
- **オフ**: 休養日として記録する。能力推定には使わない
- **レースの括弧**: `1:56.0(56.0-60.0)` の括弧は区間ラップ。
  レース配分シミュレータの唯一の材料なので落とさない

読めなかったものは**空欄のまま**にし、理由を添えて人間に確定させる。
確定していない行は登録経路に乗らない。

### J 読めてしまった間違いの検出（sanity）

読めなかった行は画面に理由が出るので気づける。危ないのは**読めてしまった間違い**で、
これは何も言わずにCFEまで届く。

例: 300mの実施タイム 40.0 を 4.00 と打つ。素直に読めば800m換算は約11秒になり、
承認した瞬間にCFEが飛ぶ。CFEは全カテゴリの設定ペースの親なので、練習全体が壊れる。

`src/lib/core/sanity.ts` が登録前に検査する。error が1つでもあれば登録させない
（画面には「要確認」）、warn は登録できるが表示する（「注意」）。

- 1本のペース 0.095〜0.60秒/m の外（100mを9.5秒／10:00/km相当を超える）は error
- 持続走 2:30〜10:00/km の外、距離0.4〜60km・時間3〜360分の外は error
- 平均心拍 80〜210 の外は error（桁の打ち間違い）
- 400mPBから見て速すぎる1本（200m以上の区間で12%超）は warn
- レース記録がPBを3%以上上回る場合は warn（PB更新か入力ミスかを本人に確認させる）
- 区間ラップの合計が記録と合わない場合は warn
- **本数と実施タイムの数が合わない場合は warn**。パーサは不自然な数値を捨ててから
  渡してくるので、捨てられた事実はここでしか分からない。黙って本数が減ると、
  平均も垂れ幅も別のセッションの数字になる

「ありえないが本当」という値は中距離の練習データには無いので、迷ったら止める側に倒す。

### K 補強の取り込み

実際の日誌には「体幹」「プライオ」「ウェイト」が普通に混ざる。従来はカテゴリ未確定で
全部落ちていた。

補強は `SessionCategory` を増やさず、既存の `StrengthSession` へ流す。
`SessionCategory` はルールエンジン22本・GRP比率・転移度・負荷計算がすべて参照している型で、
ここに `strength` を足すと「補強は質練習に数えるのか」「ACWRにどう乗るのか」を
既存の全ルールで決め直すことになる。補強には接地回数など走練習とは別の規則が既にあるので、
そちらに寄せた。走練習側の経路に入れると ACWR で二重計上される。

判定語は走練習の語より**後ろ**に置いてある。`ジョグ40分＋体幹` を補強として登録すると
ジョグ40分が有酸素量から丸ごと消えるため、走った分を残す方を優先する。
`体幹30分` だけの日は走の語が無いので補強に落ちる。

接地回数（`接地120回` / `120接地`）はプライオの週間管理に使うので拾う。

### L 表記辞書

一括入力が読めない語は必ず出る。所属チーム固有の呼び方があるからで、
組み込みルールをいくら足しても追いつかない。

読めなかった行を人が直したあと、その場で「この書き方を覚えさせる」と押せば
語とカテゴリの対応が保存され、次から自動で通る。
**本人の登録は組み込みルールより優先する**（「セット走」を閾値走と呼ぶチームも
CV走と呼ぶチームもあるので、こちらが決めてはいけない）。
登録済みの語は「覚えた書き方」から確認・削除できる。

LLMは使っていない。同じテキストを貼れば必ず同じ解釈になるという性質を壊さないため。

### G 同一処方の経時比較

カテゴリ・1本の距離・本数が一致したものを同じ処方とみなす（レストは一致条件に含めず、表に併記）。

**平均タイムと垂れ幅を必ず別々に判定する。** 平均が速くなっていても垂れ幅が
広がっていれば、それは1本目を突っ込んだだけで後半維持は悪化している。
耐乳酸型の選手は1本目を速く入りやすいので、この2つを1文にまとめると判断を誤る。

### H CFEの予測レンジ

「1:51.0、信頼度0.48」と出しても、その0.48を使って判断はできない。
`1:50.2 〜 1:51.8` と幅で示す。信頼度が低いほど広く、実測どうしのばらつきが
大きいほど広くする。**表示専用**で、プラン生成や設定ペースの計算には使わない
（計算に使うと「幅のどこを採るか」という新しい恣意性が入る）。

ホームのCFE推移グラフは軸を反転しない（下がるほど良いことは「下がるほど良い」の一文と数値横の矢印で示す）。
分析タブのCFE推移（LineChart）も反転していないため、Sparkline側だけ反転すると同じデータが画面によって上下逆に見えてしまう。見え方が画面ごとに変わる害の方が大きいと判断した。

### I レース配分シミュレータ

目標タイムと**本人の過去レースの実測落ち幅**から3案を出す。
実測どおり／落ち幅を0.5秒詰める／0.5秒広げる、の3つ。

過去レースの区間ラップが2本未満のときは**案を出さない**。
一般論の配分を出しても、本人の落ち幅が分からないまま信じてレースを壊すだけになる。
代わりに「何本必要か」「どこに入れるか」だけを伝える。

## 改修指示書v4（M-1〜M-12）への対応

### M-1 練習結果の保持と上書き

記録画面は保存後も同じセグメントに留まり、入力済みの値を表示したままにする。
既に登録がある場合は初期値として読み込み、ボタンを「上書きして保存する」に変える。

**再保存は上書き。** 新しいidで積むと記録が二重に残り、負荷も達成度も二重に数えられる。
さらに CFE が同じ練習で2回動き、「1回の更新は±1.5秒まで」というガードレールが実質±3秒になる。
そのため `processResult` は既存の記録のidを引き継ぎ、
`revertCfeForSession` で前回この練習が動かしたぶんを取り消してから入れ直す。
取り消しは後続の更新の差分（after − before）を保ったまま行うので、
古い記録を直しても以降の履歴が壊れない。

### M-2 直近の状態に応じた設定の調整

**CFEと設定ペースを分ける。** CFEは「能力の推定」、設定ペースは「今日出せる値」。
実行できなかったことは能力低下とは限らない（暑かった、寝ていない、設定が高すぎた）。
どれも CFE を下げる理由にはならないので、設定だけを動かす。

判断材料は4つとも使う。

- 直近3回の同カテゴリの実行状況（設定との乖離・垂れ幅・打ち切りの有無）
- その日のコンディション（睡眠・疲労・安静時心拍）
- ジョグの心拍。同じペース帯（中央値±20秒/km）で平均心拍が +4bpm 以上なら疲労とみなす。
  ジョグを「消化した記録」ではなく「状態の測定値」として扱う
- ポイント練習の心拍（Q-1）。同じ距離で、直近2本の平均心拍が
  それ以前より +4bpm 以上なら疲労とみなす。こなせてはいても状態は落ちている、を拾う

閾値と上限（`src/lib/core/adaptive.ts`）:

- 直近3回の平均乖離が **+2.0秒/本** を超えたら緩める
- 緩める上限は **3%**、締める上限は **1.5%**。
  締める側を保守的にしているのは、速く走れた事実は能力の主張だから
- その日の状態による調整は最大 **2%**
- 黄信号は既存ルールに合わせ、強度を維持したまま量を30%減らす
- 暑熱フラグの付いた実測は判断材料から外す（環境要因は M-9 が別に扱う）

提案は保存しない。何をどれだけ動かしたかを出して、本人が適用するか辞退するかを決める。
辞退は記録され、同じ提案を出し直さない。

#### S-10 画面で何を言うか

「設定の調整案」と見出しを出して増減の秒数だけ並べても、**何をどうしたいのかが伝わらない**。
差分を読ませるのではなく、次の3つを順に出す。

1. どちらに動かすのか（見出しで言い切る。「今日の設定を ゆるめる提案」）
2. **変更前と変更後の処方を、文面そのままで並べる**（`beforePrescription` / `afterPrescription`）
3. そう判断した材料（`reasons`）と、**CFEには触れないこと**

3つ目は必ず書く。設定とCFEの混同はこのアプリで最も起きやすい誤解で、
「暑かった・寝ていない・設定が高すぎた」はどれも能力が落ちた理由にならない。

ポイント練習の日以外は、その日の枠ではなく**次のポイント練習**の案を出す。
今日の枠に固定していたため、ジョグの日には調整案が一切見えていなかった。
ジョグと休養には設定が無いので、固定しても出るものが無い。

#### Q-1 ポイント練習の心拍の扱い

1本ごとの平均心拍（`RepResult.avgHr`）は**任意項目**。時計から拾える人だけが入れるので、
無いほうが普通という前提で扱う。無くても比較もM-2も今までどおり動く。

- 記録画面では既定で欄を出さない。常時2欄にすると1行に6欄並び、
  iPhone幅（390px）で実施タイムの欄まで潰れる。出すときは3列→2列に落として幅を確保する
  （E2Eが最小幅を実測している）。
- 心拍と「何本目か」の対応は、実施タイムを間引く**前**に取る。
  先に間引くと、途中の本が空のときに心拍が1本ずつずれる。
- **心拍が上がっていても、タイムが 0.3秒/本 以上速くなっていれば疲労とみなさない。**
  速く走れば心拍は上がる。上がったこと自体を悪い材料にすると、
  速く走ったのに疲労と判定されることになる。
- 判定のしきい値は用途で分ける。M-2の疲労判定は **4bpm**、
  同一処方の比較で「傾向あり」とみなすのは **3bpm**。
  比較側が緩いのは、そちらは表示だけで設定を動かさないため。
- 一括入力のパーサには読ませていない。日誌に1本ごとの心拍が書かれることは稀で、
  読める書き方を増やす代償のほうが大きい。

#### R-1 心拍が実際に何に効いているか

**心拍は補助。無くても全機能が動く。** 心拍が無いことを理由に何かを止めたり、
値を推測で埋めたりしない。判定できないものは判定できないと出す。

| 心拍 | 使っている場所 |
| --- | --- |
| ジョグの平均心拍 | `jogEfficiency`（M-2の材料） |
| 1本ごとの平均心拍 | `qualityHrTrend`（M-2）／同一処方の比較の `hrTrend` |
| 暑熱ブロックの心拍 | 順化判定（同一ペースでのHR低下） |
| 最大心拍 | 相対強度の基準（`hrMaxReference`） |
| 心拍の差 | 暑熱の切り分け（`heatHrEvidence`） |

`src/lib/core/heartRate.ts` に置いた判断:

- **最大心拍を年齢の式（220−年齢など）から推定しない。** 個人差が±10拍以上あり、
  推定を基準にすると強度の判定がその誤差ぶん動く。本人が入れた実測値が無ければ
  記録の中の最高値を使い、**それが実測の最高値であること**（本当の最大とは限らない）を明示する。
  どちらも無ければ相対強度を出さない。
- **1本が2分未満の練習では、心拍から強度を判定しない。**
  心拍が定常に達するまで1.5〜2分かかる。300mを42秒で走る練習の平均心拍は
  実際の負荷よりはっきり低く出るので、そのまま読むと「強度が足りていない」と誤読する。
  短い練習の心拍は、同じ設定どうしの比較（`qualityHrTrend`）にだけ使う。
  高乳酸・モデリング・神経系はこの理由で強度帯を持たせていない。
- 暑熱の切り分けは、**同じ設定・同じかそれより遅いペースで心拍が5bpm以上高い**ときだけ
  環境要因の裏づけとして扱う。心拍が変わらなければ「暑さのせいだと言い切る材料は無い」と書く。
  速く走ったことによる上昇は裏づけにしない。

「使われているか」は分析タブの「現在地 → 心拍の使われ方」で実際の記録に対して出している。
保存されているだけで誰も読んでいない項目を作らないための枠でもある。

### M-3 中止基準

処方に必ず打ち切り条件を付ける。

- 高乳酸・モデリング: 許容 +2.0秒、**1本でも**超えたら打ち切り
- それ以外: 許容は設定の1.5%（最低2.0秒）、**2本連続**で超えたら打ち切り

打ち切りは失敗ではない。`SessionResult.aborted` を立て、
CFE の SKIP-06（中断を未達として反映）を**適用しない**。
「2本連続で超えたら止めろ」と指示しておいて、止めたことを未達として響かせるのは筋が通らない。
打ち切りは設定側（M-2）が受け取り、2回続けば設定が高すぎると判断する。

根拠: 設定から大きく外れた本数を消化しても狙った代謝刺激は入らず、疲労だけが残る。
耐乳酸型は1本目を突っ込んで後半が垂れやすく、垂れた状態の消化は糖枯渇練習に変わる。

### M-4 セッション中の入力

`/run?sessionId=...`。1本入れるごとに続行か中止かを返す。
画面に出すのは3つだけ（直近の1本・設定との差・続行か中止か）。
レストの間に読める情報量には限りがある。

入力途中は kv に保存するので、画面を閉じても消えない。
終了時にそのまま `SessionResult` になり、二度打ちにならない。
走行中は誤タップの元になるので FAB を出さない。

### M-5 予定の編集・移動

カレンダーの操作は3つ。

- **日付の行をタップ** → その日の記録画面へ（行全体がリンク）
- **✎** → 編集シート（内容・設定タイム・所要時間・移動・削除）。セッションの長押しでも開く
- **＋** → その日に練習を足す（同じ日に午前・午後の2本を残すときにも使う）

長押しだけにしていない理由: iOSの長押しは取りこぼすことがあり、
リンク上ではプレビューが割り込む。押せる場所を用意しておく。
編集・追加のシートは日付リストの**上**に出し、開くときに画面上部までスクロールする。
日付が何十行も並ぶ画面なので、下に出すと画面外に出てしまい「押しても何も起きない」ように見える。

**確定前に必ずルール検査を通す。** セッションを差し替えた状態でルールエンジンを走らせ、
必ず元に戻してから結果だけを返す。新しく ERROR が出る変更は既定で適用せず、
何が壊れるかと、前後7日で置ける日（最大3件）を出す。
本人が選べば強行できるが、強行したことを変更履歴に残す。

プラン全体は作り直さない。作り直すと手で直した内容が消える。

### M-6 レース前の変則調整（テーパー）

原則は「量を落として強度は維持」。強度まで落とすとレースペース感覚と神経系の出力が落ちる。

| 段階 | 内容 | 週の総量 |
| --- | --- | --- |
| 14日前〜 | 高乳酸の本数を減らす（設定は変えない） | 100% |
| 10日前〜 | ジョグの量を落とす | 80% |
| 7日前〜 | 高乳酸を外す（回復が間に合わない） | 65% |
| 3日前〜 | 刺激のみ | 40% |
| 前日 | 流しと動き作り | 20% |

固定セッション（チーム練習）は動かさない。動かせない前提で他を削る。
調整は差分として出し、適用するまで予定は変わらない。辞退もできる。

**M-2との干渉を切ってある。** テーパー期は「直近の出来が悪いから落とす」のではなく
「意図的に落とす」期間なので、両方を掛けると二重に落ちる。
テーパー期は M-2 の量の調整を止め、設定ペースの調整（実行可能性の担保）だけを残す。

### M-7 制限因子の自動判定

400mPBと1500mPBで800mの現在地を両側から挟む。

- 400m側の妥当域 = 400mPB×2 + 9〜12秒
- 1500m側の妥当域 = (1500mPB − 15〜20秒) ÷ 2

遅れが大きい側が「使い切れていない資源」。差が0.5秒を超えたところで判定する
（1秒にすると両側1秒以内の選手が全員「バランス」になり、判定が働かない）。

伊藤選手（400m 49.0 / 1500m 3:56 / 800m 1:49.51）:
400m側の中央1:48.5に対して1.0秒遅く、1500m側の中央1:49.25に対して0.26秒遅い。
→ **制限しているのは後半の維持**。
目標1:48.90に必要な換算差は10.9秒で標準（9〜12秒）の範囲内なので、
400mを速くする必要はない。

判定は表示だけでなく**生成の配分に反映する**。重み1未満のカテゴリの枠を、
重みが最大のカテゴリに振り替える（維持が制限なら CV → 経済走）。
振り替えた日付・元・先は `limiterSwaps` として返し、必ず本人に見せる。

#### Q-2 足りていないカテゴリの提案

ルールエンジンは「多すぎる・詰まりすぎ」だけを見ていて、
**「足りていない」側は誰も見ていなかった**（RULE-16 の ACWR 低下は総負荷の話で、
カテゴリの偏りは検出しない）。固定曜日設定を使っていると、その枠に収まる範囲でしか
メニューが出ないため、4週まとめて見ると特定のカテゴリが薄いまま進む。

`src/lib/core/trainingBalance.ts` が月曜始まりの現在週と直前3週を共通集計し、
`coverage.ts` がカテゴリ不足の提案と組み合わせる。

- 予定距離/予定負荷と、結果から得た実施距離/実施負荷を別々に持つ。
- 週ごとの高負荷日、高乳酸・解糖系、中距離特異的、有酸素高強度、ロング走、
  完全休養・回復、実施率、変更/中止/期限超過を表示する。
- 実施4件未満では傾向を断定せず、「記録不足」と次の行動だけを出す。
- 前週比急増、高負荷3週連続、高乳酸の直近10日集中、回復不足、実施率低下を
  根拠の件数・日付と一緒に出す。
- 保存カテゴリは変更せず、警告/集計用に
  `高乳酸・解糖系 / 中距離特異的 / 有酸素高強度 / 神経・スプリント /
  低〜中強度有酸素 / 回復 / 筋力・補強` へ写像する。

- **基準の回数は別表で持たない。** 生成器の週テンプレート
  （`categoryCountsPerFourWeeks`）をそのまま4週ぶん数える。
  別表にすると、生成の中身を変えたときに提案の基準だけが古くなる。
- 制限因子（M-7）の重みを掛ける。維持が制限なら経済走の基準が ×1.3 になる。
- **不足2回から提案する。** 1回の差は週テンプレートの巡り合わせで普通に出るので、
  毎週なにか言われる状態になり、提案そのものが読み飛ばされる。
- 数える対象は**実施したものだけ**。過去日に予定のまま残っているものは数えない
  （あるつもりで足りない、を防ぐ）。過去データ入力ぶんは**含める**
  （実際にやった配分を見たいので、入力経路で回数が変わってはいけない）。
- 置き換え候補はジョグの枠から選ぶ。ポイント練習を別のポイント練習に替えると、
  減らした側が今度は足りなくなる。
- **ロングランは他に候補が無いときだけ出し、代償を必ず文章にする。**
  有酸素の土台は数週間かけて落ちるので、連続で潰すと別の問題が出る。
- 固定曜日設定そのものは書き換えない。動かすのはその週の予定1件だけ。
  適用するかは本人が選ぶ（M-2 / M-6 と同じ作法）。
- 置き場所はホームではなく分析タブの「現在地」。4週の振り返りは「今日やること」ではないので、
  ホームの原則を崩さない。

#### S-12 何の画面かを先に書く

表と不足回数だけでは、**何を見て何をすればいいのか分からない**。順番を変えた。

1. 何のための画面か（固定曜日の枠に収まる範囲でしか出ないので、薄いまま進む種類がある）
2. **おすすめを1つだけ**（「経済走を あと3回 増やす」）。表を読んでから考えさせない
3. 内訳の表（「やった / 目安 / 不足」。「実施 / 基準 / 差」から言い換え）
4. 入れ替え候補

**M-2（今日の設定）との違いを画面に書く。** 「今の状況に応じた強度」という同じ言葉で
両方を指せてしまうので、こちらは1か月の組み立ての話だと明記する。

カレンダーにも1行だけ出す（`CoverageStrip`）。予定を組み替えるのはカレンダーなので、
そこで気づけないと意味が無い。内訳と入れ替えは分析タブに任せ、
カレンダーには結論1行と導線だけ置く（表まで置くと日付が画面から押し出される）。

### M-8 600m通過を主指標にする

目標1:48.90の基準線: 400m通過 54.5 ／ 600m通過 1:21.5 ／ 残り200m 27.4。

材料は800mレースの区間ラップ、600m単発、300+500のような分割走。
200m刻みのラップがあれば通過はそのまま足す。400+400しかない場合は
後半400の48%で按分し、**推定であることを画面に出す**（単純な半分では速く出る）。

材料が2本未満のときは指標を出さない。1本しかないものを線にすると、
たまたまの1本が現在地に見える。

### M-9 WBGTから設定を自動で緩める

WBGT区分ごとの基礎補正（注意1% / 警戒2% / 厳重警戒3.5% / 中止5%）に、
暑熱耐性の係数（low ×1.5 / high ×0.7）を掛ける。

補正は**表示上の設定にだけ**掛かる。実測をCFEに戻すときは `normalizeForHeat` で差し引く。
これをやらないと夏場の実測がすべて「能力低下」として記録される。
WBGTも気温・湿度も無ければ補正しない（推測で埋めない）。
有酸素系は設定をCFEから作っていないので対象外。

### M-10 接地時間の疲労指標化

同じペース帯（中央値±20秒/km）で、基準（8日以上前の中央値）から
**+5%以上**の状態が3日続いたら疲労として出す。
主観や安静時心拍より早く出ることがあるので、故障の予兆としても使う。
CSVは列名を見ず「日付, 接地時間(ms), ペース」の位置で読む（時計ごとに列名が違うため）。
データが無ければ何も出さない。

### M-11 週次レビューの自動生成

定型文の組み合わせで作る。LLMは使わない。同じ週の同じデータからは必ず同じ文章が出る。

数字は必ず実測を引用する（「調子が良かった」ではなく
「設定41.5秒に対して平均42.0秒、垂れ幅+1.0秒」）。
平均と垂れ幅は別々に評価する（平均が設定どおりでも垂れているなら入りが速すぎる）。
打ち切りは「中止基準にしたがって止めたもので、失敗ではありません」と書く。

### M-12 データの書き出しと復元

全データをJSON1ファイルに書き出す。復元は「上書き」と「統合」を選べる。
統合はidで突き合わせ（日次コンディションは日付で）、重複を作らない。
14日以上書き出していなければホームで促す。

iPhoneのPWAはストレージが消えることがあり、
数か月ぶんの実測が消えると現在地の推定が全部やり直しになる。
派手さは無いが、失ったときの損失は他のどの機能より大きい。

### v4 で足した保存先

単独のテーブルを立てるほどの構造を持たないものは kv（キー・バリュー）に置く。
セッション途中の入力、辞退した提案、接地時間、最後に書き出した日時。
検索キーが要るものはここに置かない。

## 改修指示書v5（N-1〜N-3）への対応

### N-1 1文字打つたびにキーボードが消える

`ResultForm` の中でラベル用のコンポーネント `L` を定義していた。

```
function ResultForm(...) {
  const L = ({ label, children }) => (<label>...{children}</label>);   // ← これ
  return (... <L label="RPE"><input .../></L> ...);
}
```

`L` は再描画のたびに別の関数になるので、Reactは「別の種類の要素」とみなして
中身の `<input>` を作り直す。作り直された入力欄はフォーカスを失い、iOSではキーボードが閉じる。
1文字ごとに再描画が走るので、1文字ごとに閉じる。19か所で使っていたため、
練習結果のほぼ全部の欄が該当した。`L` をモジュール直下に出して解決。

**この不具合は画面に何も出ない。** 見た目は正常なので、実機で打ってみるまで気づけない。
そのためE2Eで「1文字ずつ打ってフォーカスが保たれること」を機械的に見張っている。
壊れた状態に戻して、この検証が実際に落ちることも確認済み。

なお `app/setup/page.tsx` の `F` は `{F("名前", "name")}` という**呼び出し**で、
要素の種類が変わらないため同じ問題は起きない。
判定基準は「コンポーネントの中で定義した関数を `<X>` としてJSXで使っていないか」。

### N-3 メニュー本文からカテゴリを判定する

`src/lib/core/prescription.ts` の `parsePrescription`。

**中身は一括入力の `parseRow` に日付を足して渡しているだけ。** 独自に読み直さない。
同じ「300(42)×5 r5min」が一括入力では高乳酸、編集シートでは別の何か、
ということが起きると、どちらの数字を信じればいいのか分からなくなる。
表記辞書も同じものを通す。

判定は断定しない。根拠（「設定 42.0秒/300m はGRPの98%」「表記辞書「セット走」」）を出し、
その場で直せるようにする。設定タイムが書かれていなければカテゴリは一意に決まらないので選ばせる。
保存前に M-5 のルール検査を通すので、カテゴリが変わって高乳酸の間隔に触れれば止まる。

**`@設定` 表記に対応した。** このアプリが生成する処方は
`300m × 5 @40.9〜41.7秒 r5分` と書くので、これを読めないと
自分が出したメニューを自分で「カテゴリ未確定」と判定することになる。
ただし距離×本数が書かれているときだけ設定として扱う。
ジョグの `@5:00〜5:20/km` を1本の設定と読むと種別を取り違えるため。

### N-2 本文に合わせて入力欄を組み立てる

読み取った構造に沿って入力欄そのものを組み替える。
編集シートは1本ごとの**設定タイム**（`300(42)+600(1:26)+600(1:26)` のように
区間ごとに設定が違うメニューがあるので、1つの設定欄では表せない）、
記録画面は1本ごとの**実施タイム**（貼り付け用に、まとめて入れる方式も残して切り替えられる）。

**入力中に欄を作り直さないこと。** 素直に実装すると N-1 と同じ不具合を自分で作る。

- 解釈は入力が止まってから走らせる（300ms のデバウンス）
- 欄の作り直しは `shape`（種別・距離・本数の指紋）が変わったときだけ。
  設定タイムは `shape` に含めない。設定だけ直したときに欄を作り直すと入力中の値が消える
- 本数が増えたら空欄を足すだけ。減っても値は捨てない（`resizeValues`）。
  打ち間違いで一時的に「×3」になったときに4・5本目を消すと、入れ直しになる
- 入力欄の `key` は「何本目か」で固定する。本文や解釈結果を key に使わない
- 本数の上限は30。打ち間違いで「×99」と入っても欄を99個作らない
- 読み取れない本文では欄を変えない。空にもしない

記録画面の欄の数は「処方の本数」「入力した本数」「既に入れた値の数」の最大を採る。
処方が3本でも実際に5本やったなら5本ぶん入れられる必要がある。

#### S-2 距離・時間・平均ペースは2つで足りる

3つのうち2つ入れれば残り1つは決まる。計算は一括入力と同じ `completeRunTriple` を使う
（同じ数字の関係を2か所で実装しない）。以前は「距離＋時間 → ペース」の向きしか無く、
時計で平均ペースを見た人は距離を自分で割る必要があった。

3つとも入っていて食い違うときは、**どれが正しいかを決めずに知らせるだけ**にする。
勝手に上書きすると、どれが実測でどれが計算かが分からなくなる。

`paceOverridden` を立てるのは、距離と時間が揃っているうえで手入力のペースを採ったときだけ。
ペースから距離を出した場合、そのペースは上書きではなく実測そのもの。

#### S-4 レストは本ごとに違うことがある

`IntervalDetail` のレストはセッションに1つしか持てないが、
`300+600+300` のような複合セッションでは区間ごとにレストが違う（300のあと6分、600のあと10分）。
`RepResult.restAfterSec` に**その本のあとの**レストを持たせた。任意項目で、
全部同じなら入れなくてよい。表示は `perRepRestNote` が違うときだけ並べる。

心拍と同じく、**実施タイムを間引く前に「何本目か」で対応させる**。
先に間引くと、途中の本が空のときにレストが1本ずつずれる。

入力欄は既定では出さない。3欄（タイム・心拍・レスト）を横に並べると
iPhone幅で潰れるので、**3欄になったら1本1行に落とす**（E2Eが最小幅を実測。105px）。

#### S-3 メニューの入力方法を1つにする

自作メニューの登録だけ本文のテキスト1つで、1本の距離を手で入れ直す作りだった。
記録画面・編集シート・追加シートと同じ `PrescriptionFields` を使うようにして、
**本文を打てば欄が組み上がり、距離・本数・レストは解釈から取る**。
同じ「メニューを打ち込む」操作が画面によって違う手数になるのをやめた。

**編集シート・追加シート・ホームのTODAYは実装を共有する。**
本文に合わせた入力欄は `app/components/prescription-fields.tsx`、
メニューの変更シートそのものは `app/components/session-edit-sheet.tsx` が唯一の実装。
画面の外枠（ヘッダー・タブバー・FAB・下端の余白）は `app/components/app-shell.tsx` で、
Next.js の `layout.tsx` と PWA の `entry.tsx` の両方がこれを使う。
以前は枠を2か所に書いていたので、片方だけ直しても片方の実行環境では直らなかった。

同じ組み替え規則を2か所に書くと、片方だけ直したときに同じ本文が画面によって違う欄になり、
どちらの数字を信じればいいのか分からなくなる（解釈を `parseRow` の1か所に集めているのと同じ理由）。
共有できていることはE2Eで確認している。組み替え規則を1つ壊すと両方の画面のE2Eが同時に落ちる。

### P-4 下端の余白（タブバー・FABに隠れない）

下部タブバーとFABは `position: fixed` なので、スクロール領域が自分でそのぶんの
余白を持たないと、最下部の要素が裏に入る。**スクロールしきったように見えるので気づけない。**

余白は `--main-bottom-pad`（globals.css）で1回だけ計算し、`app-shell.tsx` の `main` が
それだけを見る。画面ごとに padding を足して回ると、足し忘れた画面だけ隠れる。
内訳はタブバーの高さ（セーフエリア＋55px）＋FABの逃げ（78px）。
**セーフエリアを定数で見込まないこと。** iPhoneでは34px あるので、
「だいたい96px」と置くと実機だけ足りなくなる。

`calc()` をユーティリティ側（`pb-[calc(...)]`）に直接書かないこと。
Tailwind がクラスを生成しないことがあり、生成されなくても画面には出ず、
最下部が隠れるだけなので気づけない。CSS変数にしてから `pb-[var(--main-bottom-pad)]` と書く。

E2Eの「P-4」が全画面で最下部の要素とタブバー上端を実測して比べている。
